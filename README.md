# hubflow · 高铁站外交通疏导智能平台

在站前围栏内，**先按"时段容量预约"给每辆车把将来要走的每一段路留好位子，再在"不让任何一辆已安排的前车变慢"的前提下，给这位司机一条说得通、走得快的路线**。

> **一期是"双数据源"（D1′）**：**视频感知链路**（**项目核心的 YOLO 在一期就跑在 6 段真实样本视频上**：检测 → 跟踪 → 透视标定 → 四项指标 → 判级，`source: "video"`）**+ 孪生链路**（SUMO 里的"虚拟检测器"，`source: "twin"`）。两条链路**字段逐字段一致、共用同一套下游**，并**用视频实测标定孪生的边界条件**（手册 10.13）。
> **而且，视频链路的实测值会做「数据同化」——通过 SUMO `calibrator` 回灌到孪生的边界断面，等于"给孪生接一只真实的眼睛"**（每 60 s 一次，带置信度门控，手册 10.14）；**但站前内部路段不灌**（只灌 `role: "boundary"` 的上游边界断面），否则孪生变成"录像回放"、推荐再也改变不了路况，**保证推荐仍然有效**（验收 **TC-20 / M1-10**；二期全部边界断面在线闭环 **M2-9**）。
> **引擎是同一套，二期只换两个源、不改下游**：① **视频源由 6 段离线样本视频换成现场实时摄像头流**（`source` 仍是 `"video"`，**字段不变**）；② **车辆位置由孪生真值换成 App 定位 + 地图匹配**。差别是**数据虚拟还是真实**、**场景在单机还是现场**。
> ⚠️ 但**能力清单不是"完全相同"**：二期还要新增**车流量预测（L0→L1→L2）**、**按路段参数自适应与定期重标定**、**用车站真实画面微调视觉模型**、**数据同化的在线闭环与熔断（M2-9）**——这四项里，前三项一期只留接口或保底实现，数据同化一期只做到"边界断面回灌（M1-10 / TC-20）"这一步（详见 [全流程计划](docs/全流程计划.md) 与手册 2.5 节）。

## 这是什么

三个部分，共用**同一套数据**：

- **一个能力** —— 可被日常导航软件调用的站外疏导能力（不做"又一个要司机专门下载的 App"）；
- **一个 App** —— 给司机用的鸿蒙 App：推荐路线 + 至少两条备选 + **送完人之后怎么走**（离站路线）+ 停在哪里；
- **一个平台** —— 给管理者的可视化监控平台：路网四级色、拥挤度热力、因素与预测展示、告警、方案下发、处置回写、效果对比。

**核心机制**：不是"给每个人此刻最快的那条路"（那条路会被自己的推荐压垮），而是**三件事一起做**——① 给每辆车预约它将来经过的各路段**1 分钟时段容量**；② 新车的安排**不得让任何已登记的前车变慢**（≤ 30 s【待标定】）、任何时段饱和度不超 0.85【待标定】；③ 前车前方变堵时**提前再疏导**（每车最多 2 次），给后车腾容量。**前后车都不受影响**，都放不下时输出 `capacity_shortage` 建议外围等待，**不硬塞**。系统不记录你是谁、你开什么车、你的车牌。

## 定位：怎么知道"你在哪条路上"（两期口径）

| 项 | 一期（虚拟） | 二期（真实） |
|---|---|---|
| 车辆位置从哪来 | **孪生里直接读**（TraCI：所在路段、车道、离路段起点多少米），`location.source = "twin"` | **App 定位**（北斗 / GNSS），进入站前围栏后每 5–10 秒上报，`location.source = "app_gnss"` |
| "在哪条路上"怎么判断 | 直接已知（**真值**），`match_confidence = 1.0` | **地图匹配**：把定位点吸附到路网，得出路段 + 路段内位置 + 行驶方向 |
| 精度 | 真值 | 站前高楼区误差 10–30 m，靠地图匹配与行驶方向纠正 |
| 一期为二期做的准备 | 用真值**加噪声**（σ = 10–30 m）生成假定位，提前把地图匹配模块测出来 | 直接换输入 |

> **统一接口一期就按二期形状做**：`locate(session_id, position, heading, ts) → { segment_id, offset_m, direction, route_progress, match_confidence }`。
> **摄像头 / 虚拟检测器只数车、不认车**；**App 定位只为你本人这次行程服务**；**两条数据线不做任何关联**。用户拒绝定位时降级为"手动选所在道路 / 只看路况"，流程不中断。

## 技术栈

**全栈华为（基础设施与 AI）+ 通用应用框架**

| 层 | 选型 | 期次 |
|---|---|---|
| 数字孪生 | **SUMO + 自研司机行为体（TraCI）** | **一期主力** |
| 服务器 / 操作系统 | 华为服务器 · openEuler（欧拉） | 二期部署 |
| AI 框架 / 视觉模型 | MindSpore · MindYOLO | **一期（视频感知链路）**——用现成 `.ckpt` 跑 6 段真实样本视频；微调属二期 |
| 边缘部署 / 推理硬件 | MindSpore Lite / Atlas · 昇腾 | 二期 |
| 数据库 | openGauss（一期 demo 用本地文件 / SQLite） | 二期切 openGauss |
| 后端 | FastAPI（REST + SSE） | 一期接口层 |
| 前端 | Vue 3 + Vite + Element Plus | 一期管理端 |
| 司机端 | 鸿蒙（ArkTS / DevEco Studio） | 一期绑演示车 |
| 地图 | 高德 / 百度开放平台 API —— **一期只用于在线底图核对与管理端渲染**（**不缓存、不落盘、不截图**），路网拓扑走 OSM + netconvert。**条款已核实**：见 [`docs/条款核实.md`](docs/条款核实.md) | 一期 |

> **一期与硬件的边界**：一期是**单机演示**，**在 CPU 上跑通即可**，不依赖 Atlas 加速卡，也不需要服务器与 openGauss 实例——这三项二期部署时落地。
> **`.ckpt` 权重与 MindSpore 推理链路已验证通过**，按 **D1′ 一期即投入使用**（**视频感知链路**，输入是 6 段真实样本视频）；二期把视频源换成现场实时流、并用车站真实画面微调模型（证据见 [`work/assembly/现状核实.md`](work/assembly/现状核实.md)）。

## 数据声明

一期是**双数据源**：**视频感知链路**由 6 段**真实拍摄的样本视频**经 YOLO 算出（`source: "video"`），**孪生链路**由**数字孪生虚拟司机与虚拟检测器**生成（`source: "twin"`）。两条链路全部路况、指标、等待时长与告警数值**均为演示数据（模拟）**（`is_simulated: true`），**不代表任何真实时段的实测值**。一期尚未取得任何真实数据授权，**视频也不是肇庆东站现场**。

**全部演示物料（截图 / 录屏 / PPT）必须带角标「演示数据（模拟）· 双数据源（视频链路 + 孪生链路）」。**

演示物料中**不涉及车牌、人脸、个人定位轨迹**——摄像头（一期是样本视频与虚拟检测器）只数车不认车，App 定位只服务用户本人本次行程、行程结束即删。
