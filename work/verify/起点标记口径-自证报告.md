# 起点标记偏移口径 —— 机器证据报告（L4 判据）

- 日期：2026-10-29
- 范围：大屏「本次起点」标记与路线起点的落点口径（`offset_m` 从 `coords[0]` 量起，reverse 段不做镜像）
- 被测代码：`work/frontend/ui-vue/src/shared/demoNetwork.ts:166 pointAtOffset(coords, offsetM)`
- 复现命令：`cd D:/hubflow/_arrows && node --experimental-strip-types work/verify/verify-offset-caliber.mjs`（只读接口，无副作用）

## 1. 为什么不用 `/locate` 对坐标

`POST /api/traffic/locate` **不返回 `lon/lat`**，只回
`{segment_id, offset_m, match_confidence, source, …}`（实测：
`{"segment_id":"SZ-004","offset_m":0.0,"match_confidence":1.0,"source":"twin",…}`）。
因此"标记点与 `/locate` 的经纬度两点距离 < 2 m"这条判据无法直接执行。

## 2. 采用的判据（更硬）：`/route/snap` 往返

后端 `POST /api/traffic/route/snap` 用自己的几何 + 自己的偏移口径，把经纬度吸附回段上并回显
`segment_id / offset_m / lon / lat`。于是可以反向验证前端的 `offset → 经纬度` 映射：

1. 取段几何（`src/station-packs/stationZ.network.ts`）；
2. 前端 `pointAtOffset(coords, offset_m)` 算出点 P；
3. P 交给 `/route/snap`，看它回显哪一段、哪个 `offset_m`、哪个经纬度；
4. 判据：段号一致 + 回显 `offset_m ≈ 输入 offset_m`（< 2 m）+ P 与回显经纬度两点距离 < 2 m。

**判别力来源**：reverse 段（`coords[0]` 是几何起点、行车方向相反）上取**非中点** offset。
若前端误按"行进口径"镜像换算，输入 20 m 会落到几何 100.7 m 处，snap 必然回显 ~100.7。
中点（SZ-004 的 60.4 m 附近）两种口径互补重合，**不能**用作判别——脚本里已注释说明。

判别结论：输入 20 → 回显 20（若镜像应为 ~100.7）、输入 90 → 回显 89.9（若镜像应为 ~30.8）

（与后端 snap 样例一致），印证两种口径互补。

口径依据（代码注释 `src/shared/routeArrows.ts` 内保留）：
`work/twin/sumonet.py:344-355`（SUMO 边 `shape` = `coords` 顺序、不看 oneway）、
`work/twin/loop.py:1066-1071`（`_rev` 补边 `offset_m = length_m - getLanePosition()`，换算回原段起点起算）。

## 4. 已知数据问题（**不可用于任何几何校验**）

`GET /api/traffic/vehicles` 返回的 `twin-D1-####` 车辆快照，其 `lon/lat` 与本站点包几何
**全线偏差约 530 m（正向段同样偏差）**，`n=164`、median 530.02 m、max 700.63 m。
⇒ **这批车辆位置是旧口径 mock 快照，不能用于任何几何校验**（不能拿它当"箭头错位 / 起点错位"的证据）。
首版取证脚本曾误用它做对照，得到 500+ m 的假偏差，已废弃、改用 §2 的 snap 往返。

## 5. 结论

起点标记回退路径（`routes.json` 的 `arrival_route.start_point = null` 时走
`DashboardView.vue` 的 `pointAtOffset(seg.coords, offset_m)`）**口径正确**，
最大偏差 0.00 m；代码中只有一条偏移口径（`pointAtTravelOffset` 已于 2026-10-29 删除）。
