## 1. 分支保护（Gitee：仓库 → 管理 → 保护分支设置）

**入口**：`https://gitee.com/ozxowx/hubflow/branches/setting`（页面右侧可直接切到 `main`）。

**⚠️ Gitee 的模型与 GitHub 有两处不一样，先说清**：

1. **保护分支有两层，两层都要配**：① 把分支的**属性**设为「保护分支」（`常规分支` / `保护分支` / `只读分支` 三选一）；② 在**保护分支规则**里写一条匹配 `main` 的规则。**规则只对「保护分支」属性生效**——只写规则不设属性 = 规则空转（页面原文）。
2. **"要求门禁状态成功才能合并"是一个勾选项**（规则表单里的 `要求门禁状态成功才能合并`），不是独立开关；勾上之后，**必须先推到另一条分支、待检查项通过后才能并进 `main`**。

**已按 2026-10-10 决定配好（迁到 Gitee 后逐项对一遍）**：

- ✅ **分支属性 = 保护分支** —— `main` 不许直接推
- ✅ **保护分支规则匹配 `main`，权重 1**（实测 2026-10-14：规则 id `2816296`；**可推送代码成员 = 禁止任何人**，**可合并 Pull Request 成员 = 嚄u**，标准模式，白名单留空）
- ❌ **要求门禁状态成功才能合并** —— **不勾**：本仓库不挂流水线，没有检查项可 require（见第 3 节）
- ❌ **不需要"必须人工 approve"** —— 沿用 2026-10-10 决定，人审是纪律不是设置
- ❌ **规则白名单** —— 留空（白名单是"符合规则但允许不是保护分支"的例外名单，一期不用）

**分支命名（2026-10-10 起，全仓统一，与平台无关）**：

- **常驻个人分支已取消**（5 条 `feat/*` 已删，无独有提交，删除不丢代码）；
- **一条任务一条短分支**：`task/<Issue号>-<简述>`（例：`task/12-t1-points`），**合并后删除**；
- **文档类修订走 `docs/<主题>`**；
- `main`：**不许直推**，必须走 PR；**门禁本地跑绿**（`python scripts/doc_gate.py`）。

## 3. 门禁：本地跑，不挂流水线（**2026-10-14 业主裁定**）

**结论：`.gitee/workflows/` 里不放任何流水线文件**（迁移当天建过一份 Gitee Go 版 `ci.yml`，**同日按本裁定删除**）。

**为什么**：

- Gitee Go 是**增值服务（预付按构建时长）**——实测 `https://gitee.com/ozxowx/hubflow/gitee_go` 显示"开通 Gitee Go"、账户剩余时长 **0 分钟**，即**不买时长就不会跑**；
- 本仓库的门禁本质是**一条本地命令** `python scripts/doc_gate.py`（七组机械检查），**门禁读的是 git 索引里的 blob**——本地跑与平台跑读的是同一份内容，所以**本地绿 = 平台绿**，平台的边际价值只有"替你把关"这一项；
- 业主口径（2026-10-14）：**不要流水线，门禁本地跑**，减少外部依赖与费用。

**这条改动的代价（写在明处）**：**"红了也合得动"**——没有任何机器拦你。所以提交前跑门禁、并在 PR 的「怎么验证的」栏贴命令与结论，**从"建议"变成唯一防线**。

5. 强推 6 条分支到 Gitee；主仓的 4 条 task 分支用 `git update-ref`（**不动工作区**）指向重写后的提交，四个 worktree 的未提交改动**全部保留**。

**为什么必须强推 `main`，以及怎么推的（如实记录）**：

- Gitee 的保护分支**不允许 push**（实测报 `Auth error: No permission to push this protected branch`）；
- 当时的处置顺序是：**先把规则的权重改成 0**（页面原文："**权重为0时规则将被禁用**"，规则行随即显示"作用于 0 个分支"）→ 强推 `main` 与 5 条分支 → **再把权重改回 1**（规则行恢复"作用于 1 个分支"）；
- **这是一次"临时摘掉保护再戴上"的操作，如实记在这里。** 事后验证：保护已恢复 —— 规则仍是 `main` 权重 1、可推送成员仍是「禁止任何人」，从 worktree 直推 `main` 被正常拒绝。
- ⚠️ **遗留一处**：`main` 上的旧提交在**没有强推、没有 GC 的这段时间窗口内**理论上可被外部按旧 SHA 取到；**Gitee 侧尚无公开的 GC / 存储库整理入口**（页面「存储库 GC」按钮实测未开）。若这属于必须消除的风险，**下次重写前先用「清空仓库 + 重推」而不是强推**（见下面第 8 节的备忘）。

**副作用与共同影响（说清代价）**：

- **所有历史提交的 SHA 全变了**（包括 `main` 顶端与 4 条 task 分支顶端）。**文档里凡是引用 commit hash 的地方都已失效**——已核对：仓库文档里此前**没有**引用任何真实 commit hash（扫描出的 11 个十六进制串全是日期、字节数、`Issue #NN` 之类），所以**无需逐处修订**；
- **Gitee 上已开/已合的 Issue #IKLIG4 与 PR #1 / #2 里的提交链接会指向旧 SHA**，点开可能显示 404 —— **PR / Issue 正文本身不受影响**（GitHub 与 Gitee 的 PR 都按"合并记录"存文本，不按 SHA 校验正文）；
- **贡献者列表现在是单一作者**（远端实测：`git log` 172 个提交全为 `嚄u <ozxowx@gitee.com>`）。

**下次要重做时的备忘**：Gitee 的「清空仓库」会**保留仓库与 Issues / PR 记录、只清代码历史**——若目标是彻底抹掉旧对象，应走「**清空仓库 → 从重写副本重推**」这条路，而不是强推。
