## 2.2 三类司机 × 两种停靠方式

**三类司机：**

| 代号 | 类型 | 车辆属性 | 路径段 |
|---|---|---|---|
| D1 | 送客进站 | 多为私家车 | 起点 → 落客点 → 离站 |
| D2 | 接客出站 | 多为私家车 | 起点 → 候客区/蓄车区 → 站口 → 离站 |
| D3 | 送完又接（往返） | 多为出租车、网约车 | 起点 → 落客点 → 候客区 → 站口 → 离站 |

**两种停靠方式：**

| 代号 | 方式 | 对建模的影响 |
|---|---|---|
| S1 | 门口即停即走 | 落客区容量由**服务率**（辆/小时）决定 |
| S2 | 路边或停车场停靠 | 必须把「**从停车位走到站口的时间**」计入司机总耗时 |

**组合矩阵（一期全做）：**

| | S1 门口即停即走 | S2 路边/停车场停靠 |
|---|---|---|
| D1 送客（私家车） | 落客点 = 站门口；给离站路线 | 落客点 = 临停点/停车场；给**步行接驳时长** + 离站路线 |
| D2 接客（私家车） | 上客点 = 站门口；给**排队等待预估** | 候客点 = 停车场；给**步行接驳时长** + 到站口路线 |
| D3 往返（出租车/网约车） | 走**专属蓄车区**规则，不得占用私家车落客位 | 蓄车区按**车位数**定容量，满了改「外围等待 + 到点进区」 |

## 2.3 两类终点节点的容量口径（**必须分开建模**）

| 节点类型 | 容量口径 | 建模方式 | 为什么 |
|---|---|---|---|
| 落客区 / 上客点 | **服务率**（辆/小时） | 可套路段行程时间函数 | 车来了就服务，服务完即走，瓶颈是服务速度 |
| 候客区 / 蓄车区 | **车位数**（辆） | **必须用排队延误表达**，不套行程时间函数 | 车停进去就占位，瓶颈是车位数量 |

**司机视角总耗时的构成（S2 场景必须体现）：**

```text
总耗时 = 行驶时长 + 停靠排队时长 + 步行接驳时长
```

**"在停车场等"与"在门口等"的时间差，就是这个决策的全部意义。** 若引导到停车场却不把"走到站口"的时间明示，司机不会采纳。

## 2.4 候客区怎么定：地图人工打标签

**候客区位置由提供的地图人工打标签确认，不等官方口径。**

**底图来自高德地图 / 百度地图开放平台 API**（真实地图数据），不是自绘示意图。一期"真实底图 + 虚拟车流"。

**操作流程：**

1. 通过**高德地图 / 百度地图开放平台 API** 拉取站前区域底图与路网数据，作为打标签的底图。
2. 逐个圈出并命名点位，填属性。
3. 导出为站点包的点位映射文件（字段见第 8.1 节）。
4. 拿不到官方数据时按现场照片/公开地图估算，**逐项标「待核实」**。
5. 二期实地考察时逐条订正。

**要打的五类标签：**

| 标签类型 | 圈什么 | 必填属性 |
|---|---|---|
| 落客点 | 门口落客区 / 路边临停段 / 停车场落客位 | 类型（服务率型）、允许停留时长、服务率 |
| 上客点 | 门口即走上客位 | 类型（服务率型）、允许停留时长 |
| 候客区 / 蓄车区 | 出租车专属 / 网约车专属 / 社会车辆 | 类型（车位数型）、车位数、进出规则 |
| 检测断面 | 每条待测路段的虚拟断面线 | 桩号、车道数、对应视频文件 |
| 平交路口 | 影响车流的上游与站前路口 | 是否有信号、配时方案编号 |

**为什么这件事必须由人做**：圈点位是现场判断，AI 替不了。这也是「数据与标注」这个位置存在的理由。

## 3.0 技术栈定位：**全栈华为（基础设施与 AI）+ 通用应用框架**

| 全栈华为 | 通用选型（不受约束） |
|---|---|
| 服务器（华为）、操作系统（openEuler）、AI 框架（MindSpore）、视觉模型（MindYOLO）、边缘部署（MindSpore Lite / Atlas）、推理硬件（昇腾 Atlas）、数据库（openGauss） | 后端 FastAPI、**前端 Vue 3 + Vite**、地图数据（高德 / 百度开放平台）、交通仿真软件（SUMO） |

**为什么这样划**：**基础设施与 AI 全栈走华为**——这是项目的国产化底座，也是答辩时要讲清的部分；**应用层框架与地图数据用通用选型**——后端宿主是仓库里现成的 FastAPI，前端是现成的 Vue 工程（加 Vite 构建），地图受限于国内只能走高德 / 百度开放平台。**把这两层分开说，比笼统讲"全栈国产化"更经得起追问。**

**一期与硬件的边界（据实说明）**：一期是**单机演示**，**在 CPU 上跑通 MindSpore 链路即可**，不依赖 Atlas 加速卡，也不需要服务器与 openGauss 实例。**服务器、Atlas、openGauss 在二期部署时落地**——不是"不做"，是"二期做"。

**这条纪律要写进汇报口径**：一期结束时，可以讲"**MindSpore 链路已验证**"，**不得**讲"昇腾部署已验证"——因为昇腾本来就不在一期范围内。**这不是回避，是把范围说准。**

## 3.3 旁路与验收边界（**一期到底验什么**）

这是本项目最容易在答辩时被追问、也最容易自欺的一条，必须写死：

| 问题 | 口径 |
|---|---|
| 一期要不要昇腾卡？ | **不要**。一期只要 MindSpore（CPU 版即可）能加载 `.ckpt` 并跑出与旁路一致的结果，就算验证通过 |
| 没有 MindSpore 环境能不能开发？ | **能**。走 `TRAFFIC_BACKEND=ultralytics` 旁路，用 PyTorch 工具链跑通全链路 |
| 旁路跑通能不能说「MindSpore 链路已验证」？ | **不能**。旁路只证明算法逻辑成立，不证明 MindSpore 推理成立 |
| 那什么才算一期验收？ | MindSpore 加载 `.ckpt` 权重、**在 CPU 版 MindSpore 上**跑出与旁路一致的结果。**不需要昇腾卡** |
| 那什么时候才需要昇腾？ | **二期**做性能与部署时。一期不列为开口项，也不在一期汇报里承诺 |
| 一句话口径 | 一期结束可以讲「**MindSpore 链路已验证**」；**不得**讲「昇腾部署已验证」 |

## 4.1 架构分层

```text
数据层    样本视频 / 虚拟司机轨迹 / 地图 API 拉取的路网 / 时刻表 / 配时 / 天气系数
          （每条数据带 is_simulated 标记）

感知层    检测 → 跟踪 → 像素轨迹 → 透视标定 → 米制轨迹 + 车道归属
   ↓
指标层    流量 q / 速度 v / 密度 k / 排队 Lq → 饱和度 x → 拥堵等级
   ↓
决策层    路网 + 行程时间函数 + 系统最优 + 增量分配 → 配额租约表
   ↓
出口层    ① 司机端 App   ② 管理端平台   ③ 对外调用接口（形状预留）
   ↓
回流层    匿名采纳事件 → 采纳率校正；管理端下发/回写 → 配额与阈值改写
```

## 4.2 端到端链路（文字版，必须能读通）

```text
视频帧
  → 检测（找出车、标出框）
  → 跟踪（跨帧认出同一辆车，给 track_id）
  → 像素轨迹（{track_id: [(x_px, y_px, 类别), ...]}）
  → 透视标定 H（像素坐标 → 米制坐标）
  → 米制轨迹 + 车道归属
  → 四项基础指标：流量 q、平均车速 v、密度 k、排队长度 Lq
  → 饱和度 x = q̄ / c̄（15 分钟滑动窗口）
  → 拥堵等级（第 6 章五步流程）
  → 候选路径（K 最短路，K=3）
  → 行程时间函数 t = t⁰·[1+α(x/c)^β]
  → 系统最优（边际成本 α' = α(1+β)）+ 增量分配（M=5）
  → 配额租约表（每个 OD、每条路径的剩余配额）
  → ① 司机端：arrival_route + departure_route (+ pickup_route) + 耗时 + 备选 + 差异原因
     ② 管理端：路网四级色 + 热力 + 告警 + 下发 + 回写 + 报表
  → 回流：采纳事件（匿名）→ 采纳率 κ → 下一周期配额
          管理端下发/回写 → 阈值与配额改写 → 下一周期
          虚拟司机行为 → 下一轮仿真输入
```

## 4.4 两条回流（**没有它们就只是看板**）

| 回流 | 触发 | 作用 |
|---|---|---|
| 采纳回流 | 司机是否选中推荐方案（匿名事件） | 算出采纳率 κ，校正下一周期的配额发放量 |
| 处置回流 | 管理端下发方案、处置回写 | 改写下一周期的配额与阈值 |

**采纳率在线校正公式：**

```text
κ ← (1 − γ)·κ + γ·(x_obs / x_rec)
γ = 0.3（采纳率平滑系数，【demo 假设值 / 待标定】）
x_obs = 实测流量，x_rec = 推荐发放量
```

**为什么必须用实测流量而不是发放量**：发放量假设"发了推荐就会来车"。若采纳率偏低，实际饱和度低于预测值，用实测流量重算才能避免"以为分了流、其实没分，还按分过的容量继续放车"。

# 第 5 章  感知层

## 5.1 检测与跟踪的现有接口

| 能力 | 接口 | 输出 |
|---|---|---|
| 目标检测 | `Detector.predict_frame` / `track_frame` / `predict_image_file` | 检测框 `boxes_xyxy`、类别 `classes`、置信度 `confs` |
| 多目标跟踪 | `ByteTracker.update(...) -> TrackStep` | `TrackStep{boxes_xyxy, track_ids, classes, confs}` |
| 视频轨迹导出 | `track_video` | `TrackOutput{output_path, locations, category_nums}` |
| 越线计数 | `count_video` | `CountOutput{crossed_count}`，判定 `y < line_position`（默认 600） |

**现状缺口（必须补，且属于易被低估的工作量）**：现有轨迹输出是 `{track_id: [{"x": px, "y": px, "c": cls}]}`，**没有时间戳、没有米制尺度、没有车道归属**。要变成"车速 23 km/h、排队 180 米"，必须补时间戳与标定两步。

## 5.2 透视标定（像素 → 米）

**单应矩阵 H（3×3，h33 = 1），用 OpenCV findHomography（DLT + RANSAC）求解。**

| 项 | 口径 |
|---|---|
| 控制点数量 | ≥ 4 组，**推荐 6–8 组**最小二乘 |
| 控制点选取 | 停止线两端、车道线交点、斑马线角点、导流线折点 |
| 世界坐标来源 | 测距轮/激光测距仪实测；**拿不到时用"标准车道宽 3.5 m"推算，并标注为推算值** |
| 精度校验（留证） | 重投影误差 ≤ 3 px、尺度误差 ≤ 3%（【demo 假设值 / 待标定】） |
| 标定文件 | 写进站点包 `calibration.json` |

**有效标定带（必须定义）**：

```text
v ∈ [v_near, v_far]，远边界取"1 像素对应实际距离 ≤ 0.5 m"
超出 v_far 的目标：只计车辆数（密度、流量），不计入速度统计
```

**为什么必须定义**：远处 1 个像素对应的实际距离过大，测出来的速度噪声会大到不可用。不划这条线，速度指标就是假的。

## 5.3 四项基础指标

| 指标 | 符号 | 单位 | 口径 |
|---|---|---|---|
| 流量 | q | 辆/小时 | 窗口归一化 + 分车道 |
| 平均车速 | v | km/h | 仅统计有效标定带内、寿命 ≥ 1 s 的轨迹 |
| 密度 | k | 辆/km/车道 | 多车道时 `k_l = k / n_l`（n_l 为车道数） |
| 排队长度 | Lq | 米 | 车头间距 < 约 7 m 且连续 ≥ 3 辆的队列长度 |
| 排队消散时间 | Td | 分钟 | 由排队长度与到达率推算 |

**面域（落客区/候客区）用停车密度**：`ρ = N_zone / A_zone × 100`（辆/百平米）。

**通行能力 c：**

```text
有信号交叉口：c = s₀ · (g / C)  （s₀ 理想饱和流率，g/C 绿信比）
无信号路段：  c = 3600 / h_t   （h_t 车头时距）
拿不到配时：  用实测车头时距反推 c，标注「估计值，置信度下降」
```

## 5.4 误差预算与置信度

| 序号 | 误差源 | 机理 | 缓解手段 | 残余（demo 估计） |
|---|---|---|---|---|
| E1 | 透视标定误差 | H 不精确 ⇒ 米制尺度整体偏移 | 6–8 控制点最小二乘 | ±3%【demo / 待标定】 |
| E2 | 远端像素分辨率不足 | 远处 1 px 对应更大距离 | 有效标定带；分距离带置信度 | 远带 ±15%【demo / 待标定】 |
| E3 | 检测框抖动 | 中心点逐帧抖动 2–5 px | 3–5 帧滑窗拟合 / 卡尔曼平滑后再差分 | ±5%【demo / 待标定】 |
| E4 | 遮挡与 ID 切换 | 轨迹断裂或错误续接 | 物理上限门 `v ≤ 80 km/h`；只统计寿命 ≥ 1 s 的轨迹 | 剔除后 < 5% 异常样本 |
| E5 | 帧率与时间戳 | 丢帧、变帧率 | **必须用源视频时间戳，不得用固定 1/FPS** | < 2% |
| E6 | 采样偏差 | 只统计被检测到的车 | 与浮动车数据互为校验 | 见 5.5 |

**测量质量指标（随指标一起输出）：**

```text
SWR = N_switch / N_track             ID 切换率
Q   = 1 − clamp(SWR / SWR_max, 0, 1) 轨迹质量因子，SWR_max = 0.2【demo】
```

**Q 的用途**：Q < 0.5 时，该路段等级判为「数据不可用」（灰色），**绝不显示为蓝色**。

## 6.1 先处理一处已发现的冲突（必须显式修订）

现有材料里存在**两套互相打架的等级口径**：

| 来源 | 口径 |
|---|---|
| `plan/v3/content_3.md` 第 7.1 节 | 饱和度为主判据 + **绝对速度阈值**（≥30 / 20–30 / 10–20 / <10 km/h，按设计车速 40 假设）+ 排队绝对米数 |

- **理由二**：相对口径天然支持"换站只改配置"——换站只改站点包里的自由流速度 `v_f`，不改代码、不改表格。
- **落地**：绝对 km/h 由 `v_f` 换算后**回填进阈值表**，正文只出现换算后的绝对值。
- **修订记录必须写进文档**：原表哪里不一致、为什么改、改完谁的口径变了。

## 6.3 判定流程（五步）

```text
输入（路段 a，15 分钟滑动窗口）
  x     = q̄ / c̄        饱和度（窗口均值，不用瞬时值——会因信号周期波动产生虚假饱和）
  v                     实测平均车速 (km/h)
  v_f                   该路段自由流速度（站点包给出）
  L_q                   排队长度 (m)
  L_seg                 路段长度 (m)
  T_d                   排队消散时间 (min)
  Q                     轨迹质量因子 (0~1)
  age                   数据年龄 (s)

步骤 0 · 可用性门（优先级最高）
  若 age > τ_fresh(120 s) 或 Q < Q_min(0.5) 或 关键字段缺失
      → 灰 · 数据不可用（#8C8C8C）
  【硬规则】不可用绝不得显示为蓝色

步骤 1 · 硬触发（熔断，跳过所有加权）
  检测到事故 / 故障占道 / 危险品事件      → 红
  x ≥ 1.0 或 L_q ≥ 0.9 · L_seg           → 至少橙
  v ≤ v_jam(5 km/h) 或停滞               → 红

步骤 2 · 四项并列触发，取最高档
  档_x  按 v/c            < 0.6  蓝 | 0.6–0.8 黄 | 0.8–1.0 橙 | ≥ 1.0  红
  档_v  按 v/v_f          ≥ 0.5  蓝 | 0.3–0.5 黄 | < 0.3   橙 | ≈ 0    红
  档_Lq 按 L_q/L_seg      < 0.15 蓝 | 0.15–0.4 黄 | 0.4–0.9 橙 | ≥ 0.9  红
  档_Td 按分钟            < 2    蓝 | 2–5     黄 | 5–10    橙 | ≥ 10   红

  档位 = max(档_x, 档_v, 档_Lq, 档_Td)

步骤 3 · 情景系数只改输入，不改阈值
  c    ← c   × f_w(天气)      小雨 0.9 / 大雨 0.75 / 大雾 0.7 / 台风 0.6
  v_f  ← v_f × f_w(天气)      → 速度档不会被误升

步骤 4 · 聚合
  车道级 → 路段级：demo 取「最差车道」（保守），接口同时给出「加权平均」供对比
  路段级 → 区域级：max(所含路段等级)；事件类单独走告警，不参与等级计算
  落客区 / 候客区：用服务率或车位数定容量，走排队延误口径，不套路段行程时间函数

步骤 5 · 时间维防抖
  升档：立即生效
  降档：需连续 2 个统计周期（建议 5 min，按路段标定）都在下一档区间内
  强制降级：分级与人工判定连续 3 次不一致 → 转「提示」模式 + 人工复核
  红档撤除：双人确认
```

## 6.5 硬性边界（写死，不得违反）

1. **CI（四项加权合成的拥挤指数）不得作为判级依据**，只用于热力展示与辅助排序。CI 与四项指标冲突时，**一律以四项指标为准**。
   ```text
   CI = 100 · Σ w_j · f_j,  Σw_j = 1,  demo w = (0.40, 0.25, 0.25, 0.10)【待标定】
   f_1 = min(1, x / x_ref)                        x_ref = 1.0
   f_2 = clamp((v_f − v) / (v_f − v_jam), 0, 1)   v_jam = 5 km/h
   f_3 = clamp(L_q / L_seg, 0, 1)
   f_4 = clamp(T_d / T_ref, 0, 1)                 T_ref = 15 min
   ```
2. **等级不得只用颜色表达**：**颜色 + 图标 + 文字**三重编码必须同时出现，缺一视为不通过。
3. **等级不是按"多少车"定的**：车数是分子，还要除以"这条路能装多少"。同样 200 辆车，双向八车道干道上不算堵，单车道落客通道上已经爆了。
4. **"车停下来算不算拥堵"必须拆三类**：

   | 停车类型 | 判据 | 归类 |
   |---|---|---|
   | **排队停车** | 车头间距 < 约 7 m 且同车道连续 ≥ 3 辆 且持续 > 15 min | **算拥堵**，进入 Lq 与 Td |
   | **落客服务停车** | 车在落客区/上客区多边形内且停留 ≤ 允许时长 | **不算拥堵**，算「服务占用」，用服务率与等待时间表达 |
   | **违停 / 占道停车** | 超出允许时长，或停在非指定区域 | **算事件**，走告警链路，**不混进拥堵度** |

   **为什么必须拆**：如果把落客服务停车算成拥堵，系统会去"疏导"一辆本来正常在落客的车。
5. **不可测因素不改阈值，改三处**：能力折减、自由流速度同步折减、观测可靠性降权。数据新鲜度 120 s，超时标「陈旧」，**陈旧数据不进入推荐计算**。
6. **所有阈值带【demo 假设值 / 待标定】**。换站必须重新标定 `w_j`、`v_f`、`c`、各档边界。
7. **通行能力 c 的取值依据必须写明**（实测饱和流率 / 规范推荐值 / 仿真标定），否则饱和度不可复核。

# 第 7 章  分流决策引擎

> **本章产出**：`routes.json` 里的推荐路线、备选路线、离站路线、预计耗时、差异原因与配额状态。
> **谁负责**：决策线。**同时也是 /api/traffic/* 接口契约的唯一 owner。**
> **依赖谁**：第 5、6 章的 `segments.json`；第 8 章的站点包。

## 7.1 问题陈述：个体最优 ≠ 系统最优

普通导航给每位用户"此刻最快的那条"。当所有人同时采纳，那条路被自己的推荐压垮——**拥堵没有消失，只是换了个位置**。

本引擎的目标函数**不是"这条最快"，而是"全网总行程时间最小"**，并且要在"不知道司机是谁"的前提下实现。

## 7.2 路网模型

```text
节点 N：平交路口、落客区/上客区出入口、蓄车区出入口、停车场出入口、路段断面锚点
边   A：路段（有长度、车道数、自由流速度、通行能力）、转向（有转向限制）
属性：车道数、长度、限速、通行能力 c、自由流时间 t⁰、是否瓶颈、关联视频与断面
```

**节点类型决定建模方式（与第 2.3 节一致）：**

| 节点类型 | 建模 |
|---|---|
| 普通路段 | 路段行程时间函数 |
| 落客区 / 上客点（服务率型） | 服务率 + 排队 |
| 候客区 / 蓄车区（车位数型） | **排队延误**（闸门节点，有容量与放行速率） |
| 信号交叉口 | 路段函数 + **交叉口延误单独相加** |

## 7.3 路段行程时间函数

```text
t_a = t_a⁰ · [1 + α·(x_a / c_a)^β]
demo: α = 0.15, β = 4.0 【demo 假设值 / 待标定】
标定方法：ln(t/t⁰ − 1) = ln α + β·ln(x/c) 回归，需 ≥ 50 组/路段类型
```

**系统最优用边际成本近似：**

```text
α' = α · (1 + β)
```

## 7.4 候选路径生成

| 项 | 口径 |
|---|---|
| 算法 | Yen K 最短路径 |
| K | 3 |
| 路径重叠度 ρ_max | ≤ 0.7（避免三条路其实是同一条） |
| 无第二条可区分候选时 | 输出 `no_alternative: true` + 原因，**不得为凑数返回等价路径** |

## 7.5 流量分配与推荐分散

```text
增量分配：M = 5 份
随机分散：P(r) = exp(−μ·T_r) / Σ_j exp(−μ·T_j)，μ = 0.3 /min 【demo / 待标定】
```

| 约束 | 口径 |
|---|---|
| 路径级占比上限 `p_max` | K ≥ 3 时 0.5；K = 2 时 0.7 **且两候选耗时差 ≥ Δt_min（默认 2 min）** |
| 路段级占比上限 `q_seg_max` | 0.75；对"全部候选共用的瓶颈路段"不适用，但必须输出 `common_segment` 标记供复核 |
| 容量安全系数 θ | 0.9，按"未受控流量占比"反推 |
| 相容条件自检 | `p_max ≥ 1/K`、`q_seg_max ≥ 0.7`；违反时 **fail-closed 拒绝加载** |

## 7.6 配额租约机制（**本项目最核心的技术判断**）

**问题本质**：如果后端不知道是哪辆车、只知道"有多少车"，那么第一辆车拿到推荐后，第二辆车因为不知道第一辆已经被推荐了，会进入同一条路。

**解法：把"推荐"变成"配额租约"（quota lease）。四步：**

```text
① 不记身份，只记数量
   后端维护每个 OD 对、每条候选路径的剩余配额：
     R_r = p_max · D_od − 已发放量
   每次请求消耗一份。全程不记车、不记人、不记车牌。

② 先到先得，走配额
   第 1 辆车拿走 A 路的配额 → A 路配额见底
   第 2 辆车请求来时 A 路配额已是 0 → 引擎自动给 B 路
   ⇒ 矛盾消解：不需要知道是谁，就能让每辆车都被安排

③ 配额带租约时间
   T_lease = 90 s
   90 s 内未确认采纳（司机没按推荐走）→ 释放配额
   避免"发了没人走、路被虚拟占满"

④ 周期重算 + 滞回
   每 ΔT = 60 s 用【实测流量】重算一次全网配额（不是用发放量）
   切换路径要有 h = 10% 滞回，避免来回抖
```

**这个机制的意义**：原始设想是"后端不获取单一车辆，只提供前方有多少车、堵不堵"，那样**只能帮到第一辆车**。配额租约**不需要推翻这个隐私前提**，只加了一层计数状态，就把"只能帮第一辆"变成"每一辆都在配额内被安排"。

**边界情况处理：**

| 情况 | 处理 |
|---|---|
| 配额发完但路其实没堵（司机没采纳） | `T_lease` 超时释放 + 采纳率 κ 在线校正（第 4.4 节公式） |
| 一个 OD 对所有路径配额都满 | 输出 `capacity_shortage`，转需求侧（错峰/换乘/蓄车/外围等待），**不得硬塞** |
| 只有一条路可用 | 输出 `no_alternative: true` + 原因，**不得返回等价路径凑数** |
| 红档（四级）状态 | **≤ 10 s 内自动关闭个性化推荐**（返回 `recommended: null` + `fallback_flag: true`），切换统一疏散引导 |
| 采纳率长期偏低 | 连续 3 天低于 30%【demo 阈值 / 待标定】→ 效果报表标注「引导失效」，转管理端强制手段 |

## 7.7 防振荡与反效果回滚

| 机制 | 参数 |
|---|---|
| 决策周期 ΔT | 60 s |
| 切换滞回 h | 10% |
| 采纳率平滑 γ | 0.3 |
| 反效果判定 | 全网总行程时间恶化 > 1.05 或 排队消散时间恶化 > 1.10 |
| 回滚动作 | 自动回滚到上一版配额，并记录回滚原因与时间戳 |

## 8.3 地图接入（高德 / 百度地图开放平台 API）

**一期底图与路网来自真实地图数据，不是自绘示意图。**

| 项 | 口径 |
|---|---|
| 数据源 | **高德地图 + 百度地图开放平台 API**（两家都接），双 Provider 适配 |
| 一期用途 | ① 拉取站前区域**底图**，供人工打标签（第 2.4 节）；② 拉取**路网拓扑**（节点、道路等级、车道数、限速、单行），转成 8.2 的统一图结构 |
| 转换职责 | `map_ingest.py`：把地图 API 返回的路网数据转成 `{nodes, edges, attributes}`。**引擎只认统一图结构**，换站只换数据、不换代码 |
| 硬前置 | **商用授权与 Key 在第一周落实**（见第 3.2 节）。拿不到授权就没有底图 |
| 兜底方案 | 授权未到位期间，用一份**样例路网 JSON** 占位开发，保证不阻塞；授权到位后替换 |
| 数据质量不足时 | 地图 API 缺车道数、缺转向限制的路段 → 用人工补录的属性表覆盖，接入器只做拓扑骨架 |

### （1）两家怎么分工（**不建议两家同时在线取数**）

| 角色 | 高德 | 百度 |
|---|---|---|
| 定位 | **主用** | **备用 + 交叉校验** |
| 用途 | 底图瓦片、道路矢量、POI | 同左；用于核对高德拿到的车道数与单行属性 |

**接入方式：统一抽象层 + 双 Provider 适配器。** 站点包里声明 `map_provider: "amap"` 或 `"baidu"`；引擎只认统一图结构，**换供应商不改引擎代码**。

**为什么不让两家同时在线**：两家的道路等级划分、车道数取值口径不同，同时用会互相打架，对不齐的成本高于收益。**主用一家、另一家做校验与灾备**——这也是"接两家"的真正意义：不把授权押在单一供应商身上。

### （2）必须拉的四类数据

| 数据 | 用途 | 备注 |
|---|---|---|
| 底图瓦片 | 打标签的底图、管理端地图背景 | 前端 JS API 渲染；**通常不允许离线缓存**（见第（4）条） |
| 道路矢量 | 生成 `network.json` 的 nodes / edges | 道路等级、车道数、限速、单行、转向限制 |
| POI | 落客点 / 停车场 / 蓄车区**候选点** | 作为人工打标签的起点，**不是最终点位** |
| 行政区与路名 | 站点包的可读标识 | 便于人工核对与汇报 |

### （3）坐标系：**这一步错了，后面全错**

三套坐标系并存，必须显式转换：

| 坐标系 | 谁在用 |
|---|---|
| **WGS-84** | GPS / 北斗原始输出、卫星定位 |
| **GCJ-02** | 高德地图 |
| **BD-09** | 百度地图 |

**硬规则**：

1. **站点包统一存 WGS-84**，并在字段里标注原始坐标系。
2. 与高德交互：WGS-84 ↔ GCJ-02 互转；与百度交互：WGS-84 ↔ BD-09 互转（BD-09 需经 GCJ-02 中转）。
3. **定位数据（第 9 章）进入系统前先转成 WGS-84**——否则司机位置和路网对不上，推荐路线会整体偏移几十到几百米。
4. 转换算法**离线内置**，不得每次调在线转换接口。
5. **验收项**：同一地点用三种坐标系各取一次，转换后两两误差 ≤ 5 m【demo 目标值】。

**这是接入真实地图最容易踩、也最难排查的一个坑**——地图看起来完全正常，但车的位置整体偏了一条街。

### （4）配额、授权，以及一个必须提前确认的冲突

| 项 | 口径 |
|---|---|
| Key 类型 | **两套**：Web 服务 API Key（服务端拉路网 / POI）+ JS API Key（前端渲染底图） |
| 账号类型 | 个人开发者与企业认证的**配额与可调服务不同**；商用需企业认证 |
| QPS 与日配额 | 一期取数是一次性离线拉取，配额压力小；**演示时的底图渲染是持续调用**，要按演示时长核算 |
| **离线缓存许可** ⚠️ | **地图服务通常不允许把瓦片长期离线缓存**。而一期是"单机演示"——**这是真实冲突，必须在第一周确认**：要么演示现场保证联网，要么申请离线授权，要么底图降级为静态截图（仅用于打标签，不用于实时渲染） |

### （5）`map_ingest.py` 规格

```text
输入：区域范围（bbox 或站点名称）+ map_provider（amap / baidu）
处理：① 调用地图 API 拉道路矢量
      ② 坐标系统一转成 WGS-84
      ③ 按 8.2 的统一图结构建 nodes / edges / attributes
      ④ 缺失属性（车道数、限速、转向限制）标记为 null，交人工补录
输出：stations/network.json
      stations/map_source.json（记录 provider、拉取时间、坐标系、缺失字段清单）
```

**硬规则**：拉取结果**必须落盘**，不得每次运行都调 API——既省配额，也保证演示可复现。

### （6）为什么不用 OSM 作主路径

开放街图虽可离线免费，但国内站前区域的车道级属性普遍不全、更新滞后。**地图 API 是主路径，OSM 只作为离线备份的备选。**

> **注意**：一期是**真实底图 + 虚拟车流**。底图与路网是真的，车流与指标是孪生体算出来的。演示物料的角标要能区分这两层。

# 第 10 章  数字孪生与司机行为模拟

> **本章产出**：一个会自己演化的站前世界，以及它产生的虚拟司机轨迹（一套演示数据）。
> **谁负责**：后端（这是跨三条线的模块）。
> **依赖谁**：第 8 章的路网与点位；第 7 章的推荐结果（虚拟司机会采纳或不采纳）。

## 10.1 目标

一期**不依赖真实车辆**。在电脑里造一个站前世界，里面跑的是**有行为的虚拟司机**。这个世界要能：① 自己演化（车流一多，等级自然上升）；② 可重复（同一输入两次结果一致）；③ 支持开关对比（关推荐 vs 开推荐）。

## 10.2 虚拟个体属性

| 属性 | 取值 |
|---|---|
| 类型 | D1 送客 / D2 接客 / D3 往返（出租车、网约车） |
| 出发地 | 由 OD 需求矩阵按列车到发时刻生成 |
| 是否采纳推荐 | 由**采纳率参数**控制，**不是 100%** |
| 停靠选择 | 按系统给的落客点/候客点建议执行；不采纳时走默认路径 |
| 行为规则 | 见 10.3 |
| 状态输出 | 每仿真步输出位置、速度、车道、状态 |

**状态枚举**：`行驶 / 排队 / 落客服务 / 候客 / 违停 / 已离开`

## 10.3 行为规则

```text
行驶   按当前路段自由流速度前进，受前车限制
排队   遇前车减速则减速；车头间距 < 7 m 且连续 ≥ 3 辆时进入排队状态
落客   到达落客点 → 占用服务位 → 服务时长按分布抽样 → 释放
候客   到达候客区 → 若无空位则在外围等待（不进入）→ 有空位再进
违停   在非指定区域停留超过允许时长 → 标记为事件（不并入拥堵度）
采纳   若采纳推荐，按推荐路径行驶；若不采纳，按默认最短路径行驶
```

**必须支持"不采纳"**：如果全部虚拟司机都采纳推荐，演示就失去了真实性，也无法验证采纳率校正机制。

## 10.4 可回放（**硬性要求**）

| 要求 | 口径 |
|---|---|
| 输入文件 | 每个场景一份固定的需求与参数文件 |
| 随机种子 | **固定并写入输入文件** |
| 判定 | 同一输入跑两遍，关键指标（各路段等级序列、总行程时间）完全一致 |
| 日志 | 每轮留存运行日志与关键指标快照 |

**为什么硬性要求**：验收主线的对比方法就是"同一输入跑两遍、只切推荐开关"。如果输入不可复现，对比直接不成立。

## 10.5 两个用途必须分开

| 用途 | 说明 | 输出 |
|---|---|---|
| 用途一 · 产生演示数据 | 虚拟司机的行为轨迹 → 米制轨迹 → 参与指标融合与推荐计算 | 轨迹序列 |
| 用途二 · 做对照实验 | 同一输入跑两遍，只切换"是否启用推荐" | 两组指标对比 |

**纪律**：
1. 孪生体输出的一切数值都带 `is_simulated: true`。
2. 孪生体**不得**被表述为"真实交通仿真结果"，它是**机制验证工具**。
3. 用途一与用途二的结论不得混在一句话里说。

## 10.6 算力预算

| 管理端页面时延 | P95 ≤ 1500 ms | |

# 第 13 章  对外调用预留（Q14）

> **本章产出**：推荐能力如何被外部导航软件调用的接口形状定义。
> **谁负责**：决策线。
> **依赖谁**：第 12 章的接口契约。

## 13.1 为什么要有这一章

本项目的产品定位是**可被日常导航软件调用的扩展能力**，不是"又一个要司机专门下载的 App"。因此推荐能力**不能只做成自家 App 内的闭环**，必须预留对外调用。

**一期只定义接口形状与鉴权方式，不做真实对接。** 这一点必须写清楚，避免过度承诺。

## 13.2 调用场景

```text
导航软件判断车辆即将进入某高铁站周边区域（地理围栏）
  → 调用本平台推荐服务，传入：当前位置、目的地类型（送客/接客）、司机类型（可选）
  → 平台返回：走哪条路、停在哪里、送完怎么走、预计多久、为什么
  → 导航软件把结果渲染进它自己的界面
```

## 13.3 接口形状

| 项 | 口径 |
|---|---|
| 端点 | `/api/traffic/route/recommend` |
| 方法 | POST |
| 鉴权 | 平台级密钥（一期只定义形状，不发放真实密钥） |
| 请求 | 起点坐标、目的地类型、司机类型、时间戳 |
| 响应 | 与第 7.8 节 `routes.json` 单项结构一致 |
| 时延要求 | P95 ≤ 3000 ms |
| 返回内容边界 | **只含路段级匿名状态**，不含其他车辆位置 |
| 频率限制 | 按调用方配额（一期只定义字段，不做限流实现） |

## 13.4 一期边界（**必须写死的三条**）

1. **不做真实对接**：一期不与任何导航厂商联调。
2. **不做司机之间的互通**：C 端不订阅其他车辆位置，只调路段级聚合接口。
3. **不做个人信息回传**：所有个性化信息只在会话内使用，不入库。

**为什么不做司机之间的互通**（三条理由必须都写）：

| 理由 | 说明 |
|---|---|
| 合规 | 让司机看到"附近的车"等于暴露他人位置，涉及个人信息 |
| 样本残缺 | App 只看得到装了 App 的车，"这里没车"其实可能有一堆车——**比不给更糟** |
| 行为反效果 | 司机一旦看到"某区车少"会同时涌向该区，反而制造拥堵，与"按容量分配"的内核直接冲突 |

**唯一例外**：同车队/同平台内部的调度互通由平台侧自己做；本项目只提供**聚合口径的排队号**，不提供车辆列表。

> **本章交付**：`work/assembly/对外接口.md`。

## 14.1 问题一 · YOLO 要不要微调？微调什么程度？多环境多地图怎么办？

| | 内容 |
|---|---|
| **默认口径** | **检测本身不微调**——通用预训练权重对"车、人"已经够用。只微调三件事：① **车型细分**（出租车 / 网约车 / 私家车 / 大巴）；② **雨夜低照度子集**；③ **站前特有目标**（锥桶、护栏、违停占道）。<br>**"多环境多地图"的正解不是每换一个站重训一次模型，而是把泛化压力从模型转移到标定层**：检测器保持通用，每个站点、每个摄像头只换站点包里的标定文件 + 感兴趣区域 + 检测断面。 |
| **判定标准** | 冻结主干网络，只训检测头 + 最后一层颈部，3–5 轮，标注集 ≥ 2000 帧；该站点上出租车/网约车类别检测精度 ≥ 0.85 且车辆召回率 ≥ 85%。<br>**换站判据**：换一个站只新增配置文件，**不改任何权重、不改引擎代码**。 |
| **降级路径** | **数据量不到就不微调**。改装「顶灯 + 车身颜色」规则后处理区分出租车与私家车——顶灯是极强特征，成本比微调低一个数量级。雨夜单列子集出报告，不承诺精度。 |
| **详见** | 第 5 章（感知层）；第 8.4 节（换站清单） |

## 14.2 问题二 · 卫星定位怎么用？

## 14.4 问题四 · 最佳路线怎么算？

| | 内容 |
|---|---|
| **默认口径** | 四步：① **候选生成** K 最短路（K = 3，路径重叠度 ≤ 0.7）；② **行程时间** `t = t⁰·[1+α(x/c)^β]`，demo α = 0.15、β = 4.0；③ **系统最优**——目标函数不是"这条最快"，是"**全网总行程时间最小**"，用边际成本近似 `α' = α(1+β)`；④ **分配 + 分散**——增量分配（M = 5）+ Logit 分散（μ = 0.3/min），再用占比上限校验。 |
| **判定标准** | 路径级：`max_r P(r) ≤ p_max`（K ≥ 3 → 0.5；K = 2 → 0.7 且耗时差 ≥ 2 min）。<br>路段级：`Σ_{r∋a} P(r) ≤ q_seg_max`（0.75）。<br>**行为级**：同起终点连续请求多次，推荐**不集中单一路线**。<br>**反效果回滚**：总行程时间恶化 > 5% 或排队消散时间恶化 > 10% → 自动回滚上一版配额。 |
| **降级路径** | 只有一条候选可用 → 输出 `no_alternative: true` + 原因，**不得为凑数返回等价路径**。全部候选配额满 → `capacity_shortage`，转需求侧，**不得硬塞**。 |
| **详见** | 第 7 章 |

## 14.5 问题五 · 怎么算拥堵？多少车算拥堵？车停下来算不算？

| | 内容 |
|---|---|
| **默认口径** | **不用"多少车"直接判**——同样车数在不同路上完全不同。以**饱和度**（实际流量 ÷ 这条路能装多少）为主判据，再叠加速度、排队长度、消散时间，取最严重的一项定级。<br>**"车停下来"必须拆三类**：排队停车（算拥堵）／落客服务停车（**不算拥堵**，算服务占用）／违停占道（算**事件**，走告警，不混进拥堵度）。 |
| **判定标准** | **完整五步流程与伪代码见第 6.3 节**。四色 + 图标 + 文字三重编码齐全；数据不可用时显示灰色，**绝不显示为蓝色**。 |
| **降级路径** | 拿不到通行能力 → 用实测车头时距反推，标「估计值，置信度下降」。 |
| **必须避免** | 把落客服务停车算成拥堵——系统会去"疏导"一辆本来正常在落客的车。 |
| **详见** | 第 6 章（判级算法全文） |

## 14.6 问题六 · 不可测因素（下雨天）怎么处理？

| | 内容 |
|---|---|
| **默认口径** | **不改判级阈值，改三处**：① **能力折减**（小雨 0.9 / 大雨 0.75 / 大雾 0.7 / 台风 0.6）——分母变了，同样的车流自然升到更高档，**这是正确的物理行为**；② **自由流速度同步折减**——否则雨天"速度下降"会被误判成拥堵；③ **观测可靠性降权**——置信度下降时**不给强推荐，降级为"仅提示"**。 |
| **判定标准** | 同一车流在雨天判级高于晴天，且原因可追溯到折减系数；置信度低的时段推荐接口返回降级标记。 |
| **降级路径** | 摄像头被遮挡或离线、定位丢失、数据陈旧：数据新鲜度 120 s，超时标「陈旧」，**陈旧数据不进入推荐计算，只展示**；缺一路摄像头就用相邻断面 + 浮动车融合补，融合不了就 fail-closed 降级。<br>人为因素（大型活动、临时管制、事故）走**管理端人工置位**的口子。 |
| **详见** | 第 6.3 节步骤 3；第 5.5 节（融合与新鲜度） |

## 14.7 问题七 · 要不要规划停车场 / 长期停留点？

| | 内容 |
|---|---|
| **默认口径** | **要，但分三档引导**：<br>① **即停即走**（门口落客）：不需要停车引导，需要的是"落客区还剩多少服务能力、要等多久"；<br>② **短时停靠**（路边/停车场送客）：引导到临停点或停车场，**必须把"从停车位走到站口的时间"计入司机总耗时**；<br>③ **长期停留/候客**（接客出站、出租车待客）：引导到**蓄车区/候客区**，按**车位数**定容量；满了改「外围等待 + 到点进区」。 |
| **判定标准** | 三类司机各返回一条推荐路径 + 停靠点建议，每条带「停靠点类型 + 预计等待」。<br>**落客区（服务率型）与候客区（车位数型）必须分开建模**；后者用**排队延误**表达，不套行程时间函数。 |
| **降级路径** | 蓄车区满时输出 `capacity_shortage`；拿不到官方车位数据时按现场照片估算并标「待核实」。 |
| **详见** | 第 2.2、2.3 节；第 7.2 节（节点建模） |

## 14.8 问题八 · 出租车和私家车要不要区分？

| | 内容 |
|---|---|
| **默认口径** | **要，而且区分点不在外观，在行为约束**：私家车送客即走或接客即走；出租车/网约车是**往返**（送站 + 接站），受**专属蓄车区**（进区规则 + 容量）与「候客时长调控」约束。蓄车区当**闸门节点**建模（有容量、有放行速率），它会直接改变路网流量分布。 |
| **判定标准** | 文档给出两类司机的路径偏好差异表；蓄车区作为闸门节点有明确的容量与放行速率参数。 |
| **降级路径** | 若车型识别不可靠，退化为「**司机在 App 上自选身份**」（出租车/私家车），系统按所选身份给不同策略——**这是完全可接受的降级方案，且比错识别更可靠**。 |
| **不区分的后果** | **出租车被引到私家车落客位，一起堵在门口。** |
| **详见** | 第 2.2 节；第 7.2 节 |

## 14.9 问题九 · 送客入站 vs 接客出站，路线不同怎么办？

| | 内容 |
|---|---|
| **默认口径** | 这是**两个不同的出行需求，分开建模**：<br>· **送客**：起点 → 落客点（门口/路边/停车场）→ **离站段**；<br>· **接客**：起点 → **候客区/蓄车区（不是站口）** → 站口 → 离站；<br>· **往返**：起点 → 落客点 → 候客区 → 站口 → 离站（三段以上）。<br>一次出行建成**多段行程**，共用同一路网与同一套行程时间函数；离站段起点权重按「落客位释放时间」加权。 |
| **判定标准** | 一次请求返回 `arrival_route` + `departure_route` 两段，各带预计耗时；出租车往返再返回 `pickup_route`（第三段）。 |
| **为什么重要** | **「送到站后离开也需要一条线路」是本项目的独有需求**，普通导航不提供。送完人不走的车堵在落客位，才是站前拥堵的主要来源之一。 |
| **降级路径** | 某一段无法生成时（落客点不可达、候客区关闭、离站方向管制），**只返回可行段并在界面明示"该段暂不可用"**；离站段无法生成时降级为"按默认出站方向指引"，**不得返回空结果**。 |
| **详见** | 第 2.2 节；第 7.8 节（输出结构） |

## 14.10 问题十 · 交通信号灯要不要考虑？

| | 内容 |
|---|---|
| **默认口径** | **要吃进去，但不去控制它**（只生成建议并推送，不下发到信号机）。<br>信号影响两件事：① 交叉口的**通行能力** `c = s₀·(g/C)`（饱和度公式的分母）；② **交叉口延误**——延误单独加在行程时间上，路段行程时间函数只管路段本身。<br>上游路口在模型里作为**边界条件**（给一个到达流率曲线），**不当路段**——因为它决定了进入站前路段的实际到达节奏。 |
| **判定标准** | 有配时数据 → 通行能力按定义式算，饱和度分母可复核。站点包里配时是一份独立配置（demo 手写 1 个路口、2 套方案：平峰/高峰）。 |
| **降级路径** | **拿不到配时（很可能）→ 用实测车头时距反推通行能力** `c = 3600/h_t`，并标「估计值，置信度下降」。这一条必须写进领导版的风险表。 |
| **详见** | 第 5.3 节（通行能力）；第 7.2 节（节点建模）；第 8.1 节（`signal_plan.json`） |

## 14.11 问题十一 · 多辆车一起来怎么决策？

| | 内容 |
|---|---|
| **默认口径** | **把"推荐"变成"配额租约"**：① **不记身份，只记数量**——后端只维护每个 OD、每条候选路径的剩余配额，每次请求消耗一份，**全程不记车、不记人、不记车牌**；② **先到先得，走配额**——第 2 辆车请求来时 A 路配额已见底，引擎自动给 B 路；③ **配额带租约时间** `T_lease = 90 s`，未确认采纳即释放；④ **周期重算 + 滞回**——每 `ΔT = 60 s` 用**实测流量**（不是发放量）重算，切换路径有 `h = 10%` 滞回。 |
| **判定标准** | 连续多请求不集中单一路线；配额发完但未被采纳时靠租约超时释放 + 采纳率在线校正拉回；全部路径配额满 → `capacity_shortage`；只有一条可用 → `no_alternative: true`，**不得返回等价路径凑数**。 |
| **降级路径** | 采纳率长期偏低（连续 3 天低于 30%，【demo 阈值 / 待标定】）→ 效果报表标注「引导失效」，转管理端强制手段。 |
| **为什么这是核心创新** | 原始设想是"后端不获取单一车辆"，那样**只能帮到第一辆车**。配额租约**不需要推翻这个隐私前提**，只加了一层计数状态。 |
| **详见** | 第 7.6 节 |

## 14.12 问题十二 · 判断模型怎么训练？模拟数据怎么做？数字孪生？

| | 内容 |
|---|---|
| **默认口径** | **先把两件事分开：**<br>· **视觉模型**：靠**标注数据**训练，不靠数字孪生。微调数据 = 样本视频抽帧标注（≥ 2000 帧）。<br>· **决策模型**（路线分配）：**根本不需要"训练"**。它是**基于模型的计算**（行程时间函数 + 系统最优 + 随机分散），参数靠**标定**而不是训练。<br>**数字孪生用在哪？** ① **产生演示数据**——孪生体里的虚拟司机自己会开车、会排队、会等客；② **做对照实验**——同一输入跑两遍只切推荐开关；③ **可视化**——管理端地图上的实时车流量与四级色。 |
| **判定标准** | 一期**不训"拥堵预测"深度模型**。理由：没有带标签的真实数据；**用仿真数据训出来的模型去指导真实世界，是典型的仿真过拟合**。一期用「指标 + 规则 + 优化」三段式，**可解释、可验收、可回滚**。二期数据够（≥ 3 个月真实数据）再考虑加"短期流量预测"这类可插拔模块，**接口预留即可**。 |
| **模拟数据四条产线** | ① 视频：6 段样本 → 抽帧 → 检测跟踪 → 轨迹；② 轨迹：像素轨迹经透视反投影到米制 + 降频 10 秒 + 加 3 米噪声；③ 需求：列车到发时刻表 → 三类车 OD 需求矩阵；④ **虚拟司机**：孪生体里按行为规则生成的多智能体轨迹（**主产线**）。 |
| **降级路径** | 天气拿不到 → 系数 1.0；真实流量拿不到 → 只跑孪生体；仿真软件或开放平台授权有问题 → 全部数值标 `is_simulated: true`，效果结论只作**机制验证**。 |
| **详见** | 第 10 章（数字孪生）；第 14.1 节（微调边界） |

## 14.13 问题十三 · 完整链路：视觉模型怎么给判断模型，判断模型怎么反馈给两端？

| | 内容 |
|---|---|
| **默认口径** | `视频 → 检测+跟踪 → 像素轨迹 → 透视标定 → 米制轨迹+车道归属 → 四项指标 → 饱和度 → 判级（第 6 章）`<br>`→ 【决策引擎】路网 + 行程时间函数 + 系统最优 + 增量分配 → 配额租约表`<br>`→ 同时吐给两端：`<br>`　① 司机端 App：进站路线 + 离站路线（+ 往返车接客路线）、预计耗时、至少两条备选、差异原因、数据来源标记`<br>`　② 管理端：路网四级色 + 拥挤度热力 + 告警列表 + 方案下发 + 处置回写 + 效果报表`<br>`→ 闭环：采纳事件（匿名）→ 采纳率 → 下一周期配额；管理端下发/回写 → 配额与阈值改写；虚拟司机行为 → 下一轮仿真输入` |

## 14.14 问题十四 · C 端之间要不要互通？要不要让司机知道附近的车？

| | 内容 |
|---|---|
| **默认口径** | **不做"司机之间看到彼此"的互通，只做匿名聚合提示。** 司机看到的是**路段级的匿名状态**（这条路什么等级、预计多久），**不是"有多少辆车、在哪"**。 |
| **三条理由（必须都写）** | ① **合规**：让司机看到"附近的车"等于暴露他人位置，涉及个人信息。<br>② **样本残缺**：App 只看得到装了 App 的车，看到的"附近车"必然是残缺样本（"这里没车"其实有一堆车）——**比不给更糟**。<br>③ **行为反效果**：司机一旦看到"某区车少"，会**同时涌向该区**，反而制造拥堵。这与本项目"**按容量分配**"的内核直接冲突。 |
| **判定标准** | C 端**不订阅其他车辆位置**，只调路段级聚合接口；所有个性化信息**只在会话内使用，不入库**。 |
| **唯一例外** | 同车队/同平台内部的调度互通**由平台侧自己做**；本项目只提供**聚合口径的排队号**，不提供车辆列表。 |
| **降级路径** | 路段级聚合接口不可用时，C 端只显示本地已知状态 + "路况暂不可用"，**不得回退到"显示附近车辆"**——那会突破隐私红线，属于禁止的降级方向。 |
| **详见** | 第 13 章 |

# 第 15 章  人力分工与协作方式

> **本章产出**：七个位置的具体职责、**开发组用 GitHub / 其余人用共享文件夹的两套协作办法**、教团队用 AI 开发的培训口径。
> **谁负责**：项目经理。
> **依赖谁**：无。

## 15.1 先承认两件事（不回避）

1. **团队不会做前后端分离开发**（不同人同时跑服务、按接口联调）。
2. **团队的真实能力是"会用 AI 生成代码并跑起来"**，不是"手写工程代码"。

**再加一条现状，它决定协作方式必须分两套**：**开发组的 4 个人用 GitHub 协作，其余 3 个支持位置 + 队长不用**。

**所以分工方案必须绕开上面两件事，同时按"是否写代码"给两套协作办法——不能一刀切。**

## 15.2 分工总原则

| 原则 | 做法 | 为什么 |
|---|---|---|
| 一人一块 | 每人负责一个**目录**，目录里只有他改 | 配合分支 + PR，冲突面最小 |
| **文件当接口** | 模块之间用 JSON 文件传递，不用 HTTP 接口 | 不需要"同时跑两个服务"，也不需要理解 REST |
| 契约先冻结 | 开工第一天把三个文件的字段清单定死（一页纸） | 改字段要通知所有人，所以一开始就要定准 |
| 串行依赖、并行工作 | 依赖是串的，但每人都能先用**样例数据文件**开始干活 | 不需要等上游做完 |
| 最后才包服务 | 演示前最后一步，由 AI 生成 FastAPI 层把文件流包成接口 | 这一步最难，放到最后且由 AI 主导 |

## 15.3 七个位置怎么排

**四个技术位置（各 1 人）：**

| 位置 | 负责 | 端到端产出 | 文件夹 |
|---|---|---|---|
| 感知线 | 视频 → 检测跟踪 → 标定 → 四项指标 → 判级 | `segments.json` | `work/perception/` |
| 决策线 | **地图 API 接入** + 路网 → 候选路径 → 配额分配 → 推荐 | `routes.json` | `work/engine/` |
| 前端 | 管理端页面 + 司机端 App（**全程由 AI 辅助开发**） | 管理端页面 + 可运行 App | `work/frontend/` |
| 后端 | 服务宿主、接口包装、数据流串接、**总装脚本**、**公共文件唯一修改人** | `run_all.py` + `traffic.py` | `work/assembly/` |

**三个支持位置（各 1 人，做 AI 替不了的活）：**

| 位置 | 干什么 | 交付物 | 为什么 AI 替不了 |
|---|---|---|---|
| 数据与标注 | ① 样本视频抽帧、车辆与车型标注、写标注规范、质检；② **在真实地图底图上人工打标签确认落客点/上客点/候客区/检测断面/路口**；③ 控制点拾取 | 标注文件集 + 站点包数据 + 《标注规范 v1》 | 需要人对画面与点位的判断，**Q15 明确由人打标签** |
| 验收与测试 | 按第 17 章用例逐条跑、录屏留证、记缺陷 | 测试记录 + 缺陷清单 | **必须独立于开发者**，不能由技术位置兼 |
| 文档与演示 | 两份文档、演示脚本、数据来源清单、数据源标注核查 | 全部对外物料 | 答辩最需要，最容易被忽略 |

**队长（全程协助，不做固定的一块）：**

| 项 | 内容 |
|---|---|
| 定位 | **全程协助以上七个位置**——谁卡住就顶上去 |
| 不可分散的三件事 | ① **跨线协调**：接口与字段变更的最终裁定；② **公共文件复核**：后端改完由队长确认；③ **对外口径**：进度、演示、两份文档的口径统一 |
| 为什么必须有人做 | 七个人各守一块，只有队长有全局视角；一旦没人做协调，接口一改就全线阻塞 |

> **硬规矩：总装必须有人干。** 本方案明确由**后端**承担总装脚本与公共文件，队长负责串通与把关。**不能悬空**——否则七个人各做各的，最后拼不起来。

**给支持位置的纪律**：**AI 生成的东西，你必须自己核一遍才能提交。** 你们的价值是"最后一道人工关口"，不是"帮忙点鼠标"。

## 15.4 开发组用 GitHub 协作（**其余人不用**）

**分两组、两套办法——不是所有人都要学 GitHub。**

### （1）开发组（4 个技术位置）——用 GitHub 仓库

| 项 | 做法 |
|---|---|
| 仓库 | **一个仓库**，四个目录对应四个位置：`work/perception/`、`work/engine/`、`work/frontend/`、`work/assembly/` |
| 分支 | `main` 保护；每人一条工作分支（`feat/perception`、`feat/engine`、`feat/frontend`、`feat/backend`）；**不允许直接推 main** |
| 合并 | 走 **Pull Request**，由后端或队长 Review 后合并 |
| 提交节奏 | 一天一次起步，小步提交；提交信息写清"改了哪个模块、为什么" |
| 任务跟踪 | 每个位置的当日任务与卡点记在 **Issue** 里 |
| 冲突 | **不要硬合并**，找队长当面解 |
| **.gitignore 必写** | **视频、.ckpt 权重、图片数据集、模型产物一律不进仓库**（GitHub 有单文件与仓库大小限制）；这些放共享盘，路径写进 `README` |
| 前置动作 | ✅ **已完成**（2026-10-09）：仓库 `hubflow` 已建、`.gitignore` 与 `.gitattributes` 已写、`main` 已加保护、四条 `feat/*` 分支已建。**开工前只差两件事**：① 邀请开发组成员为协作者；② 每人 `git checkout 自己的分支` |

**给不熟悉 GitHub 的人的最低要求（只教四条，不要多教）：**

```text
1. 开工：  git checkout 自己的分支   →   git pull
2. 收工：  git add .  →  git commit -m "说明"  →  git push
3. 合并：  在网页上开 Pull Request，等 Review，不要自己点合并
4. 冲突：  停下来找队长，不要瞎点
```

### （2）非开发组（3 个支持位置 + 队长）——不用 GitHub

产出是**数据集、测试记录、文档**，不是代码，用 GitHub 反而凭空加一道门槛：

| 项 | 做法 |
|---|---|
| 版本管理 | **不用 GitHub**；每人一个共享文件夹，每天收工按日期复制留档，改错了就恢复前一天那份 |
| 命名 | 文件名带日期与版本：`标注集_20261008_v3.zip`，**永远不覆盖同名文件** |
| 与开发组的接口 | **点位标签、阈值配置这类小文本文件**由后端一次性提交进仓库；**图片与数据集等大文件**留共享盘，仓库里只记路径 |
| 交接看板 | 一张协作看板（白板或 Excel 就够）：`| 谁 | 今天产出什么 | 依赖谁的什么 | 状态 |` |
| 例外 | 谁愿意学可以参与读 Issue、提文档修订，**但不作为要求** |

**为什么分两套**：要求不写代码的人学分支、PR、冲突解决，除了增加出错概率没有收益；而开发组不用版本管理，四个人改同一份代码迟早互相覆盖。**两组各用各的，接口只有一个——共享盘上的文件。**

## 15.5 不会前后端分离怎么办

```text
【一期的真实做法】                    【演示前的包装】
视频 → 感知线 → segments.json
                    ↓
         决策线 → routes.json
                    ↓
         前端 → 管理端页面 / 司机端 App
                    ↓
         后端 → run_all.py 一键跑完全链路
                    ↓
         最后一步 → AI 生成 traffic.py 包成 HTTP 接口
```

- **各模块之间只认文件，不认服务。** 决策线 不需要知道感知线 用什么模型，只看 `segments.json` 的字段。
- **每个模块都要能独立跑**：`python work/perception/run.py` 就能产出自己的 JSON。
- **端到端联调 = 跑一次 run_all.py**，不是"开两个终端联调接口"。

## 15.6 怎么教团队用 AI 开发（只教三件事）

1. **怎么把提示词复制给 AI**：打开 AI 工具 → 粘贴 → 回车。
2. **怎么运行脚本**：双击 `.bat` 文件，或在终端敲一行命令。
3. **怎么把报错原样贴回给 AI**：全选报错文字 → 复制 → 粘贴 → 加一句"这是什么问题，怎么改"。

**《AI 投喂卡》模板（每次开工照着填）：**

```text
【我负责】work/张三/ 这个文件夹，别的文件夹我不动
【我要做】读 segments.json，算出推荐路线，写成 routes.json
【输入】work/perception/segments.json，字段是：路段id/时间/流量/速度/排队长度/等级
【输出】routes.json，必须有这些字段：请求id/推荐路线/备选路线/预计耗时/差异原因
【约束】不要改别的文件夹；不要引入需要联网的库；跑不起来就告诉我缺什么
【验收】我双击 run.bat，能在 work/张三/out/ 里看到 routes.json，用记事本打开字段齐全
```

**日常循环**：投喂 → 得到代码 → 双击运行 → 打开输出文件看一眼 → 不对就把报错贴回去。

## 15.7 每日节律（15 分钟）

每人只回答三个问题：

1. 昨天产出了**哪个文件**（不是"做了什么"，是文件名）？
2. 今天要产出**哪个文件**？
3. **卡在哪**（当场决定：谁帮、还是绕过去）？

**两条附加纪律**：接口/字段变更必须当天说；公共文件只有后端能改。

## 15.8 一期里程碑

| 周 | 交付 |
|---|---|
| W0 | 权重文件硬前置；**建 GitHub 仓库 + .gitignore + 分支保护**；**三个 JSON 字段契约冻结**；站点包 v0；地图打标签启动；标注启动 |
| W1–2 | 感知线跑通 `segments.json`；引擎用样例数据跑通 `routes.json`；双端页面壳；虚拟司机能上路 |
| W3–4 | 判级服务接入；配额分配机制；管理端接通数据；打标签完成 |
| W5–6 | 三场景串通；司机端接通数据；压力测试；标注与验收材料齐备 |
| W7–8 | 验收用例全过；**演示脚本无人干预连跑 3 轮**；文档定稿 |

**周期口径**：是"人力可投入情况下的建议值"，**不是承诺工期**。

# 第 16 章  开发途中会遇到的问题

> **本章产出**：15 条已知的坑与对策，逐条落到责任人。
> **谁负责**：后端维护，全员遵守。
> **依赖谁**：无。

| # | 坑 | 对策 | 责任人 |
|---|---|---|---|
| 1 | **硬前置卡死**：`.ckpt` 需 torch 环境、虚拟环境是空壳 | 先走 `TRAFFIC_BACKEND=ultralytics` 旁路解阻；自测报告必须写明「本次演示未验证 MindSpore 推理链路」 | 后端 |
| 2 | **把「后期事项」讲成「一期承诺」**（昇腾卡、服务器型号、容器化部署） | 一期只承诺 **MindSpore（CPU 版即可）链路验证**。汇报口径写死：可以讲「MindSpore 链路已验证」，**不得**讲「昇腾部署已验证」（第 3.2、3.3 节） | 队长 / 文档与演示 |
| 3 | **鸿蒙 ArkTS 是全新栈**：若无人写过，工期风险高 | ①**全程由 AI 辅助开发**；②前端与后端各 1 人分担，前端先用 H5 预览顶联调、鸿蒙跑真机最小可用页；③先做最小可用页，不做花哨动效 | 前端 |
| 4 | **地图 API 授权或配额批不下来** | ①第一周即申请高德与百度开放平台（**Web 服务 Key + JS API Key 两套**）；②两家并行，避免单点被拒；③授权未到位期间用样例路网 JSON 占位开发，**不阻塞** | 决策线 / 队长 |
| 5 | **演示现场没网，而地图瓦片通常不允许离线缓存** | 第一周就确认三选一：现场保证联网 / 申请离线授权 / 底图降级为静态截图（仅用于打标签）。详见第 8.3 节（4） | 队长 |
| 6 | **坐标系没转，车的位置整体偏一条街** | 站点包统一存 **WGS-84**；与高德转 GCJ-02、与百度转 BD-09；转换算法离线内置；验收项：三种坐标系两两误差 ≤ 5 m【demo 目标值】。详见第 8.3 节（3） | 决策线 / 感知线 |
| 7 | **像素→米最容易被低估**：控制点拿不到只能用 3.5 m 车道宽推算 | demo 用本地坐标系 + 人工拾取 4–8 控制点；标定文件写进站点包并留重投影误差证据 | 感知线 / 数据与标注 |
| 8 | **远距离目标测速不可用** | 定义**有效标定带**；超出边界的目标只计数量（密度、流量），**不计入速度统计** | 感知线 |
| 9 | **判级降档抖动**：阈值边界来回跳 | 升档立即、降档需连续 2 个统计周期；切换滞回 10% | 感知线 |
| 10 | **数据缺失被显示成蓝色**（后果最严重） | 数据陈旧或质量不足时显示**灰色「数据不可用」**；陈旧数据**不进入推荐计算，只展示** | 感知线 / 前端 |
| 11 | **阈值全是占位值** | 任何对外材料引用必须带【demo 假设值 / 待标定】 | 文档与演示 |
| 12 | **数字孪生可视化做过头** | 一期管理端只做「地图 + 四级色 + 热力 + 点击看指标」，**不做 3D 孪生大屏**；但**虚拟司机行为必须做** | 后端 / 前端 |
| 13 | **仿真不可复现**：随机种子没固定，两次对比结果不同 | 固定种子 + 同一输入文件 + 每轮留日志（第 10.4 节） | 后端 |
| 14 | **采纳率是仿真值** | demo 无真实用户，任何"接受率"数字**不得作为承诺** | 验收与测试 / 文档与演示 |
| 15 | **三场景不可回放** | 同一份场景输入跑两遍、只切推荐开关，否则"分流有效"的对比不成立 | 后端 |
| 16 | **公共文件被多人同时改** | `main.py` 注册、路由表、接口契约**只由后端一人改** | 后端 |
| 17 | **开发组不熟 GitHub 就上手，容易互相覆盖或误合并** | 只教四条命令（`checkout`+`pull` / `add`+`commit`+`push` / 开 PR / 冲突找队长）；`main` 加保护**不允许直接推**；**视频、权重、数据集不进仓库**，先写好 `.gitignore`（第 15.4 节） | 后端 / 队长 |
| 18 | **算力估不准，演示现场崩了** | 按第 10.7 节做压力测试；以"无人干预连跑三轮"为验收口径 | 后端 |

# 第 17 章  验收用例与 DoD

> **本章产出**：可客观判定的验收用例与完成定义。

## 17.1 验收用例

| 编号 | 用例 | 判定方式（客观） |
|---|---|---|
| TC-01 | 感知链路可复现 | 指标可复现、分级与阈值表一致、上报周期可配置生效 |
| TC-02 | 双端同源 | 同一时刻两端同一路段的指标与等级一致，且都能追溯到 `is_simulated` 标记 |
| TC-03 | 多方案与差异原因 | **备选 ≥ 2 条**（+ 推荐 1 条 = 合计 ≥3 条方案）、差异原因含节点与耗时差、四项字段齐全；唯一候选时按 `no_alternative: true` 例外 |
| TC-04 | 分流分散性 | 同起终点连续请求多次，推荐**不集中单一路线**，占比不超上限 |
| TC-05 | 权限降级 | 拒绝定位与通知后全流程不中断 |
| TC-06 | 弱网/断流降级 | 显式提示数据陈旧或不可用，不再强推荐，不崩溃 |
| TC-07 | 闭环回写 | 下发 → 回执 → 回写状态可推进，回写四项齐全 |
| TC-08 | 自动改道 | 下发分流后司机端重新规划，推荐与下发前不同且提示已更新 |
| TC-09 | 报表 | 四项对比存在，标注来源与时间窗 |
| TC-10 | 应急不引导 | 注入应急状态后推荐被替换为"服从现场指挥" |
| TC-11 | **数据不可用不显示为蓝色** | 制造数据陈旧/质量不足，界面必须显示灰色「数据不可用」 |
| TC-12 | **离站路线存在** | 一次请求必须返回 `departure_route`；出租车往返再返回 `pickup_route` |
| TC-13 | **同场景可回放** | 同一场景输入跑两遍，关键指标完全一致 |
| TC-14 | **开关对比成立** | 同一输入下关闭推荐与开启推荐各跑一遍，四项指标可同屏对比 |

## 17.2 完成定义（DoD）

| 编号 | 完成定义 | 判定方式 |
|---|---|---|
| M1-1 | 前置完成 `.ckpt` 生成后，`demo_cli.py image / track / count` 可复现 | `track1` 轨迹数、`cross1` 越线数与 README 基线一致 |

# 第 18 章  二期：实地考察与真实数据演示

> **本章产出**：把一期的虚拟数据逐项换成真实数据的替换清单与执行路径。
> **谁负责**：二期由三个支持位置（数据与标注 / 验收与测试 / 文档与演示）+ 队长主导（**角色反转**：一期靠 AI 放大产能，二期靠现场）。
> **依赖谁**：一期全部 DoD 通过；数据授权到位。

## 18.1 二期只做三件事

1. **接真实数据**：真实摄像头、真实卫星定位。
2. **重新标定阈值**：一期所有标"待标定"的参数，用现场实测值回填。
3. **在真实数据上重演一期的对比**：同样的场景、同样的开关对比，用实测值替换虚拟值。

**二期不是"一期没做完的部分"，也不是"重写一套"。功能完全相同。**

## 18.2 踏勘清单

| 项 | 内容 |
|---|---|
| 点位确认 | 逐个核对第 2.4 节打标签的结果，订正所有"待核实"项 |
| 摄像头 | 点位、朝向、视野、分辨率、帧率、供电与网络 |
| 控制点 | 现场用测距轮/激光测距仪实测控制点世界坐标 |
| 信号配时 | 向交警申请实时/离线配时方案 |
| 车道几何 | 车道数、车道宽、渠化、转向限制 |
| 落客/候客区 | 官方口径的车位数量、允许停留时长、进出规则 |
| 列车时刻 | 到发时刻表与高峰时段 |

## 18.3 标定实测项

| 参数 | 一期状态 | 二期动作 |
|---|---|---|
| `w_j` CI 权重 | 0.40/0.25/0.25/0.10（demo） | 以人工判读等级为标签做回归，需 ≥ 200 条样本 |
| `α, β` 行程时间参数 | 0.15 / 4.0（demo） | 回归拟合，需 ≥ 50 组/路段类型 |
| `μ` 分散度 | 0.3 /min（demo） | 观测"时间差 → 实际选择比例"反解 |
| `s₀` 饱和流率 | 1800 辆/(h·车道) | 现场车头时距实测 |
| `h_s` 排队车头间距 | 约 7 m | **现场观测（一期唯一没给 demo 值的参数）** |
| `v_jam` 拥堵速度下限 | 5 km/h | 现场观测排队时车速分布 |
| 各档边界 | 相对口径 | 换算为绝对值后回填阈值表 |
| 速度阈值 | 按 `v_f` 换算 | 回填为绝对 km/h |

## 18.4 数据授权路径

| 数据 | 找谁 | 前置 |
|---|---|---|
| 视频/摄像头 | 交警、车站、枢纽运营方 | 用途说明、合规边界 |
| 卫星定位/浮动车 | 平台方 | 数据共享协议 |
| 列车到发时刻 | 铁路部门 | 接口或共享 |
| 信号配时 | 交警 | 权限范围 |
| 天气 | 气象部门或商业服务 | 采购或开放平台注册 |
| 地图底图 | 地图服务商 | 许可范围 |

**硬性红线**：**数据授权未到位 → 不得对外宣称"真实接入"。**

## 18.5 合规专项（不进则不能开工）

| 项 | 要求 |
|---|---|
| 个人信息保护影响评估（PIA/DPIA） | 独立 DoD 事项；**未通过则暂停真实数据接入与个人定位采集**，不得进入后续阶段 |
| 数据分类分级 | 明确每类数据的级别与处理要求 |
| 留存期限及依据 | 逐类写明 |
| 共享白名单与边界 | 谁能拿到、拿到什么 |
| 访问审计 | 频次与责任人 |
| 隐私红线 | 车牌、人脸、个人定位轨迹**不进入**演示物料 |

## 18.6 「虚拟数据 → 真实数据」替换清单

| 一期虚拟项 | 二期真实来源 | 替换后必须重做的事 |
|---|---|---|
| 样本视频 | 真实摄像头 | 重新标定（`calibration.json`）；重新出误差预算 |
| 虚拟司机轨迹 | 浮动车/卫星定位 + 真实过车 | 重新校验融合口径与 `N_min` |
| **地图 API 拉取的真实路网**（一期已是真实底图） | 现场实测订正 | 逐条核实车道数、限速、渠化与转向限制，订正所有「待核实」项 |
| 手工打标签的点位 | 官方口径核实 | 逐条订正并留核实记录 |
| 手工时刻表 | 真实到发时刻 | 重新生成 OD 需求矩阵 |
| 手工配时 | 真实配时方案 | 重算通行能力 c 与交叉口延误 |
| 天气系数 | 气象数据 | 校准折减系数 |
| **全部【待标定】参数** | 现场实测 | 回填绝对值；**每项都要写标定报告** |
| 孪生体虚拟司机 | 保留为**对照基线** | **不得**再用作二期演示内容 |

## 18.7 二期 DoD

| M2-2 | 感知层指标在真实数据上达到目标；未达则回到标定环节 |

| M2-4 | 至少 1 次真实高峰时段完成"预警 → 分流 → 撤档"全流程（含撤除回写） |
| M2-5 | 全部对外材料完成"真实/模拟"数据源标注复核 |
| M2-6 | **完成个人信息保护影响评估并出具报告，结论为"可继续实施"**；未通过则暂停真实数据接入 |
