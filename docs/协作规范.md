# 协作规范

> 这份文档只讲一件事：**四个人怎么在一个仓库里不打架。**
>
> **配套文档**：[`开发规范.md`](开发规范.md) —— 管"代码长什么样"（字段命名、提交信息格式、提交前自检、密钥红线）；[`分工表.md`](分工表.md) —— 管"谁做什么、这周交什么文件"。**三份都要看**：这份管流程，开发规范管代码，分工表管任务。

## 1. 谁改哪个目录

| 位置 | 只改这个目录 | 不要碰 |
|---|---|---|
| 感知线 | `work/perception/` | 其他三个 `work/` 子目录 |
| 决策线 | `work/engine/` | 同上 |
| 前端 | `work/frontend/` | 同上 |
| 后端 | `work/assembly/` + 根目录公共文件 | 其他三个 `work/` 子目录 |

**公共文件**（`README.md`、`.gitignore`、`docs/数据契约.md`、将来的 `main.py` 注册与路由表）**只由后端一人改**，其他人只提 Issue 不动手。

> `stations/` 由决策线定结构、数据与标注岗填数据。**小文本配置文件可以进仓库**，图片数据集不行。

## 2. 分支：每人一条，名字固定

| 位置 | 分支名 |
|---|---|
| 感知线 | `feat/perception` |
| 决策线 | `feat/engine` |
| 前端 | `feat/frontend` |
| 后端 | `feat/backend` |

`main` 有保护，**不允许直接推**。所有改动都经过 Pull Request。

## 3. 每天只做四件事（四条命令）

```bash
# ① 开工前：切回自己的分支，拉最新
git checkout feat/perception
git pull

# ... 改代码 ...

# ② 收工前：看一遍自己改了什么
git status
git diff

# ③ 提交
git add .
git commit -m "感知：接入透视标定，输出米制轨迹"

# ④ 推上去
git push
```

第一次推新分支时 git 会提示加参数，照它给的命令复制即可（一般是 `git push -u origin feat/perception`）。

## 4. 合并：开 Pull Request，不要自己点合并

1. 推完分支后，打开仓库网页，会看到 **Compare & pull request** 按钮，点它；
2. 标题写清楚：`感知：新增四项指标计算`；
3. 描述里写三件事：**改了什么 / 怎么验证的 / 有没有影响别人**（模板已建好，照着填即可）；
4. 选 **Reviewer** —— **仓库里已配 `.github/CODEOWNERS`，会自动带上对应的人**；没自动带上的话手动加；
5. 等 Review 通过后**由 Reviewer 合并**。

**不要自己点 Merge。** 也不要在没 Review 的情况下往 `main` 推。

### 谁审谁（**开工前先看清楚**）

| 情况 | 谁审 | 为什么 |
|---|---|---|
| **当前（账号未齐）** | **一律队长 `@YONEK0`** | 只有他和 `@ouu2006` 有账号；他自己不写代码，**天然独立于开发** |
| 账号齐了之后 | 该目录的 owner（见 `CODEOWNERS`）+ 队长 | 同线互审 + 队长兜底 |
| **改了公共文件**（根 README、`.gitignore`、数据契约、路由注册） | **必须队长过一眼** | 公共文件只后端能改，但改错影响所有人 |
| **改了契约字段**（`segments.json` / `routes.json` / `render.json`） | **决策线裁定 + 队长确认** | 契约是冻结件，改了要通知全员 |
| **改了技术手册**（两份拷贝） | **必须队长过一眼** | 两份拷贝要同步，漏一份就分叉 |

> **写 PR 的人自己不能当自己 PR 的 Reviewer。** GitHub 也不允许——作者点不了自己的 Approve。
> 所以**谁都不能"自己的 PR 自己批"**：开发组成员之间互审，或由队长审。

### 机器与 AI 已经查过的，人不用再查一遍

**PR 一开出来，静态门禁和 AI 审查会自动跑一遍**，结果直接贴在 PR 评论里：

- **静态门禁（硬性）**：禁入文件、密钥特征、目录越界、跨目录 import、JSON 可解析性。
  **不通过 PR 直接挡住**，合不了。所以**这三类问题你不用再逐个查**。
- **AI 审查（建议性）**：字段命名、口径纪律、契约一致性等语义问题，**只提示不挡**。

**人（code owner）只需要看两件机器判不了的事**：
① PR 描述里"有没有影响别人"那节是否属实；② **这个改动会不会影响答辩口径**。

完整说明见 [`自动审查.md`](自动审查.md)。**推之前想自查**：`python tools/ci/review.py --base origin/main --head HEAD --no-ai`（30 秒出结果）。

### 一条硬规矩：PR 不能"挂着没人审"

推完 PR 之后，**在当天的站会上说一句"我开了 PR #N，请谁谁看一下"**。
PR 挂过夜是允许的，**挂过两个站会没人管就是流程失效**——此时找队长指派。

## 5. 冲突：停下来找队长

出现下面这样的提示就是冲突了：

```
CONFLICT (content): Merge conflict in work/engine/run.py
```

**不要瞎点、不要乱删代码。** 正确做法：

1. 停下手里的事；
2. 把冲突文件路径发给队长；
3. 队长当面一起解。

> 冲突大多来自"两个人改了同一个文件"。所以第 1 条（谁改哪个目录）是这份文档里最重要的一条。

## 6. 任务与卡点记在 Issue 里

每天站会之前，把自己当天的任务开成一条 Issue：

- 标题：`[感知线] 接入透视标定`；
- 内容：要产出什么文件、依赖谁的什么、卡在哪里；
- 做完就关掉。

**Issue 是给人看的，不用写得很正式**，一句话也行。

> 仓库里已有模板：新建 Issue 时选「每日任务」即可，格式已经填好。

## 7. 大文件与密钥不进仓库

**视频、模型权重、图片数据集一律不提交。**

`.gitignore` 已经拦住了 `*.mp4`、`*.pt`、`*.ckpt`、`*.onnx`、`*.safetensors` 等格式。如果你要用的文件被拦住了，说明它本来就不该进仓库——**放共享盘，把路径写进对应目录的 README**。

如果误提交了大文件：**立刻告诉队长**，不要自己折腾 `git filter-branch`。

> ⚠️ **本仓库是公开的（public）。** 地图 Key、密码、`.env` 一律不得提交。要配 Key：`cp .env.example .env` 后填进 `.env`（已被忽略）。**万一误提交了 Key，先去地图控制台把 Key 作废**，再找队长——顺序不能反，理由见 [`开发规范.md`](开发规范.md) 第 11.4 节。

## 8. 每天 15 分钟站会

每人只回答三个问题：

1. 昨天产出了什么？
2. 今天要产出什么？
3. 卡在哪里？

**卡住当场决定：谁帮，还是绕过去。**
