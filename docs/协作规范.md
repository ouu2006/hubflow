# 协作规范 · V2.0

> 这份文档只讲一件事：**8 个人（3 名开发 + 4 名非技术成员 + 队长）怎么在一个仓库 + 一个共享盘里不打架。**
>
> **配套文档**：[`开发规范.md`](开发规范.md) —— 管"代码长什么样"（字段命名、提交信息格式、提交前自检、密钥红线）；[`分工表.md`](分工表.md) —— 管"谁做什么、这周交什么文件、怎么算做完"；[`表格模板说明.md`](表格模板说明.md) —— 管"非技术成员填哪张表、列有哪些、谁写转换脚本"。**四份都要看**：这份管流程，开发规范管代码，分工表管任务，表格模板说明管数据。
>
> **V2.0 的一句话变化**：**只有 3 个人写代码（用 AI 写），4 个人填表格，队长不写代码。** 所以这份规范有两条通道——**代码走 GitHub，数据走共享盘**。

## 1. 谁改哪个目录

| 角色 | **只改这些** | 不要碰 |
|---|---|---|
| **开发A** 孪生与路况 | `work/twin/`、`work/perception/` | 其他 `work/` 子目录、`stations/` 的结构、公共文件 |
| **开发B** 决策与定位 | `work/engine/`、`stations/` 的结构与脚本产物 | 其他 `work/` 子目录、公共文件 |
| **开发C** 接口与双端 | `work/frontend/`、`work/assembly/`、**公共文件** | 其他 `work/` 子目录 |
| **N1 / N2 / N3 / N4** | **共享盘**对应目录（站点包表格 / 测试与验收 / 文档与演示 / 数据来源与合规） | **任何仓库文件**——要改就提 Issue 或在站会上说 |
| **队长** | `docs/` 计划类文档（全流程计划、分工表、协作规范、手册、表格模板说明） | 业务代码 |

**三条写死的归属**：

1. **公共文件**（根 `README.md`、`.gitignore`、`.github/`、`docs/数据契约.md`、路由注册）**只由开发C 一人改，改完队长复核**，其他人只提 Issue 不动手；
2. **`stations/`**：**开发B 定结构**（`network` / `points` / `signal_plan` / `demand` / `factors` / `scenarios` / `thresholds` / `calibration`【二期】/ `sumo/`，另加 `map_source.json` 溯源），**N1 / N2 填数据**（填表格 → 开发写脚本转换 → 生成 JSON），**`stations/` 下的 JSON 不许手改**；
3. **计划类文档**（全流程计划、分工表、协作规范、手册、表格模板说明）**由队长维护**，走 `docs/*` 临时分支，可请开发C 代提交。

> **小文本配置文件可以进仓库**（`stations/*.json`、`stations/sumo/*.net.xml`），**图片、视频、权重、数据集不行**——放共享盘，把路径写进对应目录的 README。

## 2. 分支：每人一条，名字固定

| 角色 | 分支名 |
|---|---|
| **开发A** | `feat/twin`（**待队长新建**） |
| **开发B** | `feat/engine` |
| **开发C** | `feat/frontend` |

`main` 有保护，**不允许直接推**。所有改动都经过 Pull Request。

> - `feat/perception`、`feat/backend` **停用**（不删除，二期视需要复用）；
> - 文档类修订走临时分支 `docs/*`；
> - **非技术成员不用 GitHub、不需要分支**——他们的"分支"就是共享盘里带日期版本的文件。

## 3. 开发组每天只做四件事（四条命令）

```bash
# ① 开工前：切回自己的分支，拉最新
git checkout feat/twin        # 开发B 写 feat/engine，开发C 写 feat/frontend
git pull

# ... 让 AI 写代码，自己跑通 ...

# ② 收工前：看一遍自己改了哪些文件
git status
git diff

# ③ 提交（前缀见 开发规范.md 第 10 节）
git add .
git commit -m "孪生：虚拟检测器输出四项指标时序"

# ④ 推上去（第一次推新分支用 git push -u origin feat/twin）
git push
```

**四条命令之外的 Git 操作，一律先问队长。**

## 4. 合并：开 Pull Request，不要自己点合并

1. 推完分支后，打开仓库网页，会看到 **Compare & pull request** 按钮，点它；
2. 标题写清楚：`决策：新增时段容量预约，routes.json 补 reservation 字段`；
3. 描述里写三件事：**改了什么 / 怎么验证的 / 有没有影响别人**（模板已建好，照着填即可）；
4. 选 **Reviewer**——仓库里已配 `.github/CODEOWNERS`，会自动带上对应的人；没自动带上的话手动加；
5. 等 Review 通过后**由互审人合并**。

**不要自己点 Merge。** 也不要在没 Review 的情况下往 `main` 推。

### 谁审谁（**开工前先看清楚**）

| 顺序 | 谁做 | 看什么 |
|---|---|---|
| **第 0 步** | **提交者自己 + AI 预审** | 把 `git diff` 贴给 AI，让它按 [`开发规范.md`](开发规范.md) 第 11 节的**四条自检** + "有没有动契约字段 / 别人的目录"过一遍，**把 AI 的预审意见贴进 PR 描述**。AI 预审**不替代人审**，只是把低级问题挡在前面 |
| **第 1 步** | **代码互审：A 审 B、B 审 C、C 审 A** | 开发A 审开发B 的 PR、开发B 审开发C 的 PR、开发C 审开发A 的 PR。**谁都不能审自己的 PR**（GitHub 也不允许作者 Approve） |
| **第 2 步** | **队长兜底** | 只看两件机器判不了的事：**① 有没有影响别人**（契约字段 / 别人的目录 / 公共文件）；**② 会不会影响对外口径**（不得把模拟说成实测、不得把单站说成可复制、不得把孪生说成真实仿真） |

| 特殊情况 | 谁审 + 谁合并 |
|---|---|
| **改了公共文件**（根 `README.md`、`.gitignore`、`.github/`、`docs/数据契约.md`、路由注册） | **只能由开发C 改**，改完**队长复核**，**队长合并** |
| **改了契约字段**（`segments.json` / `routes.json` / `vehicles.json`） | **开发B 裁定**（唯一裁定人）+ 队长确认，**当天更新 `docs/数据契约.md` 并通知全员** |
| **改了计划类文档**（全流程计划、分工表、协作规范、手册、表格模板说明） | **队长维护**，可请开发C 代提交；两份拷贝（手册）要同步，漏一份就分叉 |
| **站点包数据**（表格转换产物 + 转换脚本） | 脚本进 PR，**队长合并**（非代码类 PR） |
| **代码 PR 的合并人** | **互审人**（A 审 B → A 合并 B 的 PR）；**队长不写代码，只合并非代码类 PR** |

> **写 PR 的人自己不能当自己 PR 的 Reviewer。** GitHub 也不允许——作者点不了自己的 Approve。

### Reviewer 要看什么（**不用通读代码**）

Reviewer 不是从头读一遍 diff，只看三件事：

1. **AI 预审的意见是否属实、有没有漏处理**（预审意见要贴在 PR 描述里）；
2. **PR 描述里"有没有影响别人"那节是否属实**——动没动契约字段、动没动别人的目录、动没动公共文件；
3. **这个改动会不会影响答辩口径**——不得把"模拟数据"表述为实测、不得把"孪生算出来的数"说成实测、不得把"单站"说成"可复制"、不得把"MindSpore 链路已验证"说成"昇腾部署已验证"。

其余机械检查由**提交者自己**在 push 前走一遍（见 [`开发规范.md`](开发规范.md) 第 11 节的四条自检）：
跑通自己的模块、字段名对得上契约、没改到别人的目录、`git status` 里没有 `.env` / 视频 / 权重。

> 仓库上装了 **Sourcery**（第三方静态分析 App），它也会对 PR 出意见。**它查的是代码本身的通用问题**（安全模式、代码异味），**不挡合并**，也不必逐条响应——与项目口径无关的可以忽略。

### 一条硬规矩：PR 不能"挂着没人审"

推完 PR 之后，**在当天的站会上说一句"我开了 PR #N，请谁谁看一下"**。
PR 挂过夜是允许的，**挂过两个站会没人管就是流程失效**——此时找队长指派。

## 5. 非技术成员怎么协作（**共享盘 + 表格 + 交接看板**）

**一句话：非技术成员不碰代码、不用 GitHub，靠"填表格 + 交文件"参与开发**（总纲 D9 与第 10 节）。

### 5.1 三条通道

| 通道 | 干什么 | 在哪 |
|---|---|---|
| **共享盘** | 干活的地方：填表、录屏、写文档、存素材 | 见 5.2 的目录结构 |
| **表格模板 T1~T9** | 填什么、列有哪些、谁写转换脚本 | 见 [`表格模板说明.md`](表格模板说明.md) |
| **交接看板** | 谁交了什么、过没过、卡在谁那里 | 共享盘 `05_站会与交接/` |

### 5.2 共享盘目录结构（**照这个建，不要另起一套**）

```text
共享盘/
├── 01_站点包表格/        T1、T2（N1）· T3~T6（N2）· T9（二期）
├── 02_测试与验收/        T7 检查表、缺陷清单、录屏（N3）
├── 03_文档与演示/        文档、演示脚本、PPT（N4）
├── 04_数据来源与合规/    T8 数据来源清单、授权材料、隐私告知（N4）
└── 05_站会与交接/        站会记录、交接看板（队长 + 全员）
```

### 5.3 三条纪律

1. **文件名带日期与版本**：`T5_因素表_20261012_v3.xlsx`。**每天按日期留一版，永不覆盖同名文件**；
2. **拿不到官方数据就标【待核实】**，按现场照片 / 公开地图估算，**不许编一个数当真值**；
3. **`stations/` 下的 JSON 不许手改**——那是开发写的转换脚本的产物。要改数据就**改表格并升版本号**，再让脚本重跑。

### 5.4 交接看板（**一张纸就够，每天更新一次**）

| 列 | 填什么 |
|---|---|
| 谁 | N1 / N2 / N3 / N4 |
| 交了什么文件 | 文件名 + 版本号（如 `T2_路段属性核对表_20261015_v4.xlsx`） |
| 对着哪条判定 | 如"T2 无空白、差异有原因（TC-15 前置）" |
| 过没过 | 过 / 没过 / 卡住 |
| 卡在谁那里 | 卡在开发B 的转换脚本 / 卡在底图权限 / 卡在队长裁定…… |

### 5.5 需要开发帮什么（**别自己动手，也别干等**）

| 情况 | 找谁 | 怎么找 |
|---|---|---|
| 表格要变成 `stations/` 的配置文件 | **T1 / T2 → 开发B；T3~T6 → 开发A；T9（二期）→ 开发B** | 站会上说一句"我这版表可以转了"，把文件路径发出来 |
| 表格列不够用 / 想加一列 | **开发B**（`stations/` 结构 owner） | 站会提出，由开发B 更新模板并同步改 [`表格模板说明.md`](表格模板说明.md) |
| 数据里发现路网缺失、点位对不上 | **开发A**（netedit 里补画路网） | 在表格里标"缺失"并在看板上写出来 |
| 要提 Issue / 要提交文件到仓库 | **开发C 代提交**（队长口径：非技术成员不碰 GitHub） | 站会上说，或请队长转达 |
| 判定值想放宽 | **不允许** | 只能由队长走总纲 / 手册修订流程 |

### 5.6 非技术成员**不需要**做的事

不用装 Git、不用注册 GitHub、不用看代码、不用懂 JSON。**只需要：会填表、会按日期存文件、会在站会上说清楚"交了哪个文件、对着哪条判定、过没过"。**

## 6. 冲突：停下来找队长

出现下面这样的提示就是冲突了：

```
CONFLICT (content): Merge conflict in work/engine/run.py
```

**不要瞎点、不要乱删代码。** 正确做法：

1. 停下手里的事；
2. 把冲突文件路径发给队长；
3. 队长当面一起解。

> 冲突大多来自"两个人改了同一个文件"。所以第 1 条（谁改哪个目录）是这份文档里最重要的一条。

---

## 7. 任务与卡点记在 Issue 里

每天站会之前，把自己当天的任务开成一条 Issue（**开发组自己开；非技术成员请开发C 或队长代开**）：

- 标题：`[决策] 时段容量预约落地`；
- 标签：`孪生` / `感知` / `决策` / `定位` / `前端` / `接口` / `站点` / `文档`（八选一或几选）；
- 内容：要产出什么文件、依赖谁的什么、卡在哪里；
- 做完就关掉。

**Issue 是给人看的，不用写得很正式**，一句话也行。

> 仓库里已有模板：新建 Issue 时选「每日任务」即可，格式已经填好。
> **每条 Issue 里请把对应周的「完成判定」一并贴进去**——否则大家只知道要交什么文件，不知道要做到什么程度。

## 8. 大文件与密钥不进仓库

**视频、模型权重、图片数据集一律不提交。**

`.gitignore` 已经拦住了 `*.mp4`、`*.pt`、`*.ckpt`、`*.onnx`、`*.safetensors` 等格式。如果你要用的文件被拦住了，说明它本来就不该进仓库——**放共享盘，把路径写进对应目录的 README**。

如果误提交了大文件：**立刻告诉队长**，不要自己折腾 `git filter-branch`。

> ⚠️ **本仓库是公开的（public）。** 地图 Key、密码、`.env` 一律不得提交。要配 Key：`cp .env.example .env` 后填进 `.env`（已被忽略）。**万一误提交了 Key，先去地图控制台把 Key 作废**，再找队长——顺序不能反，理由见 [`开发规范.md`](开发规范.md) 第 13.4 节。

## 9. 每天 15 分钟站会

**开发组**只回答三个问题：

1. 昨天产出了什么文件？
2. 今天要产出什么文件？
3. 卡在哪里？

**非技术成员**只说一句话：

> **"我交了哪个文件（版本号）、对着哪条判定、过没过。"**

**卡住当场决定：谁帮，还是绕过去。**

---

## 10. 卡住怎么办

按总纲开篇纪律：**按默认口径先做下去，再提出来讨论，不要停下来等。**
只有一种情况要停下来——**要改判定值 / 要改契约字段 / 要动别人的目录**，这三件事必须当天说、由队长或开发B 裁定。
