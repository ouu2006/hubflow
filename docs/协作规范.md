# 协作规范 · V2.1

> 这份文档只讲一件事：**全队 7 人（3 名开发 + 3 名任务池协作成员 + 1 名队长，队长由其中 1 人兼任）怎么在一个仓库 + 一个共享盘里不打架。**
>
> **配套文档**：[`开发规范.md`](开发规范.md) —— 管"代码长什么样"（字段命名、提交信息格式、提交前自检、密钥红线）；[`分工表.md`](分工表.md) —— **项目分工表**（中心文档①）：管"架构层职责表——谁负责哪一层、交什么、挂哪条验收"（**任务派活走 GitHub Issues 的任务池**）；[`表格模板说明.md`](表格模板说明.md) —— 管"任务池成员填哪张表、列有哪些、谁写转换脚本"。**四份都要看**：这份管流程，开发规范管代码，分工表管职责边界，表格模板说明管数据。
>
> **V2.1 的一句话变化**：**3 个人主写代码（用 AI 写），3 名协作成员按「任务池（许愿池）」认领任务（表格 / 数据 / 测试 / 文档为主，也参与部分技术开发）；队长由这 7 人中的 1 人兼任（身份，不额外占编、不写业务代码）。** 原 N1 / N2 / N3 / N4 **定岗已作废**，改为**任务池认领制、无锁角色**。所以这份规范有三条通道——**日常产出走共享盘，代码与脚本改动走 GitHub，任务的发布与认领在 Issues 任务板上**（详见第 5 节）。

**三条写死的归属**：

1. **公共文件**（根 `README.md`、`.gitignore`、`.github/`、`docs/数据契约.md`、路由注册）**只由开发C 一人改，改完队长复核**，其他人只提 Issue 不动手；
2. **`stations/`**：**结构归属逐个文件写死**（与 [`开发规范.md`](开发规范.md) 第 3.1 节同口径）：`network` / `points` / `signal_plan` / `scenarios`（含 `assimilation`）结构归**开发B**；`demand` / `factors` 结构**与转换脚本**归**开发A**；`calibration` 归**开发A**；`thresholds`（**判级参数组 + 决策参数组**）归**开发B**；`sumo/` 归**开发A**；`map_source.json` 归**开发B**。**池·S / 池·P 只填数据**（填表格 → 开发写脚本转换 → 生成 JSON），**`stations/` 下的 JSON 不许手改**；
3. **计划类文档**（全流程计划、分工表、协作规范、手册、表格模板说明）**由队长维护**，走 `docs/<主题>` 分支，可请开发C 代提交。

**全仓只有两个"例外"要记清，其余都按上表归属**：

1. **`work/perception/` 是「一目录两写手」**：**除 `level.py` 外全部归开发A**，**判级 `level.py` 归开发B**。例外的是**这个文件**，不是"同一文件两组"——**`level.py` 只有一个写手（开发B）**；
2. **`stations/sumo/*.net.xml` 由开发A 产出**（`netbuild.py` + `netedit` 补画）——开发B 定的是**统一图结构 `network.json`**（`map_ingest.py`），**不重跑 `netconvert`、不写 `sumo/`**；开发A 需要图结构时**读** `network.json`。

**`thresholds.json` 只有一个写手**：**判级参数**（等级边界 / 权重 / `v_f` / 因素合成下限）与**决策参数**（BPR `alpha` / `beta`、`x_safe`、`eps_harm_s`、`k_candidates`、`hysteresis`、`lease_expire_s`）**两组都归开发B**（**2026-10-10 已裁定**：判级 `level.py` 连同判级参数组一并转归开发B）。**两组的具体顶层键名由开发B 在 W0 定结构时确定**；改前在站会说一句。详见 [`开发规范.md`](开发规范.md) 第 3.1 节。

> **小文本配置文件可以进仓库**（`stations/*.json`、`stations/sumo/*.net.xml`），**图片、视频、权重、数据集不行**——放共享盘，把路径写进对应目录的 README。

## 2. 分支：一条任务一条短分支

**不再有常驻个人分支**——`feat/twin`、`feat/engine`、`feat/frontend`、`feat/perception`、`feat/backend` **共 5 条已删除（2026-10-10）**，它们均已并入 `main` 且无独有提交，删除不丢代码。

| 什么时候 | 分支名 |
|---|---|
| **一条任务** | `task/<Issue号>-<简述>`，例：`task/12-t1-points`；**合并后删除** |
| **文档类修订** | `docs/<主题>` |

`main` 有保护，**不允许直接推**。所有改动都经过 Pull Request，并通过 **CI 门禁（检查名 `ci`）**。

> - **协作成员（任务池认领者）的日常产出走共享盘**（带日期版本的文件就是他们的"版本管理"，不需要分支）；**一旦要动代码或脚本，就必须走 PR**——初期由开发C 代提交，愿意自己提交的按"四条命令"来；
> - **一条任务一条分支，合并后就删**——不要留常驻分支，也不要一条分支上堆几件不相干的事。

## 3. 每天只做四件事（四条命令）

```bash
# ① 开工前：从最新 main 切出任务分支（例：认领 Issue #12）
git checkout main && git pull
git checkout -b task/12-t1-points

# ... 让 AI 写代码，自己跑通 ...

# ② 收工前：看一遍自己改了哪些文件
git status
git diff

# ③ 提交（前缀见 开发规范.md 第 10 节）
git add .
git commit -m "站点：T1 点位表转 points.json"

# ④ 推上去
git push -u origin task/12-t1-points
```

**四条命令之外的 Git 操作，一律先问队长。**

## 4. 合并：开 Pull Request，不要自己点合并

1. 推完分支后，打开仓库网页，会看到 **Compare & pull request** 按钮，点它；
2. 标题写清楚：`决策：新增时段容量预约，routes.json 补 reservation 字段`；
3. 描述里写四件事：**改了什么 / 怎么验证的 / 审查记录 / 有没有影响别人**（模板已建好，照着填即可）；
4. 选 **Reviewer**——仓库里已配 `.github/CODEOWNERS`，会自动带上对应的人；没自动带上的话手动加（**它现在只负责"带人"，不阻塞合并**）；
5. 等 **CI 全绿**（检查名 `ci`）+ **互审通过**后，**由互审人合并**。

**不要自己点 Merge。** 也不要在没 Review 的情况下往 `main` 推。

> ⚠️ **2026-10-10 调整：GitHub 不再替你拦这一步。** `main` 分支保护里"**必须有人工 approve**"与"**必须 CODEOWNERS 批准**"**已取消**（实测见 [`仓库设置清单.md`](仓库设置清单.md)）；机器现在只强制两件事：**① 必须走 PR；② `ci` 检查必须绿**。
> 也就是说——**没人批也点得动合并按钮**。下面这套"谁审谁"从"设置拦得住"变成"**纪律 + 留痕**"：PR 的「审查记录」栏就是唯一的证据。**取消的是机器那道卡，不是你们对彼此的承诺。**

### 谁审谁（**开工前先看清楚**）

| 顺序 | 谁做 | 看什么 |
|---|---|---|
| **第 0 步** | **提交者自己**：自查 + AI 预审 + 门禁 | ① 四条自检（[`开发规范.md`](开发规范.md) 第 11 节）；② 把 `git diff` 贴给 AI 按同一套自检过一遍，**意见贴进 PR**（这是**自查**，不替代人审）；③ 跑 `python scripts/doc_gate.py`（与 CI 同一条命令）；④ 等 CI 出结论，**红 check 自己修到绿**，不留给别人 |
| **第 1 步** | **快速独立审查**（全新上下文，**目标 ≤ 5 分钟**） | 只给"改动范围 + **4 个问题**"，**不给**实现思路、可疑点、既有结论；只读 `git diff`；结论 **≤ 10 行**贴进 PR。做法与时限见下一节 |
| **第 2 步** | **代码互审：A 审 B、B 审 C、C 审 A** | 开发A 审开发B 的 PR、开发B 审开发C 的 PR、开发C 审开发A 的 PR。**谁都不能审自己的 PR**（GitHub 也不允许作者 Approve） |
| **第 3 步** | **队长兜底** | 只看两件机器判不了的事：**① 有没有影响别人**（契约字段 / 别人的目录 / 公共文件）；**② 会不会影响对外口径**（不得把模拟说成实测、不得把单站说成可复制、不得把孪生说成真实仿真） |

| 特殊情况 | 谁审 + 谁合并 |
|---|---|
| **改了公共文件**（根 `README.md`、`.gitignore`、`.github/`、`docs/数据契约.md`、路由注册） | **只能由开发C 改**，改完**队长复核**，**队长合并** |
| **改了契约字段**（`segments.json` / `routes.json` / `vehicles.json`） | **开发B 裁定**（唯一裁定人）+ 队长确认，**当天更新 `docs/数据契约.md` 并通知全员** |
| **改了计划类文档**（全流程计划、分工表、协作规范、手册、表格模板说明） | **队长维护**，可请开发C 代提交；两份拷贝（手册）要同步，漏一份就分叉 |
| **站点包数据**（表格转换产物 + 转换脚本） | **表格由池·S / 池·P 填**（共享盘）；**脚本进 PR，队长合并**（非代码类 PR）；**`stations/` 下的 JSON 不许手改** |
| **代码 PR 的合并人** | **互审人**（A 审 B → A 合并 B 的 PR）；**队长不占代码目录，只合并非代码类 PR** |

> **写 PR 的人自己不能当自己 PR 的 Reviewer。** GitHub 也不允许——作者点不了自己的 Approve。**2026-10-10 起没有人批也能合，所以这条只靠自觉。**

### 第 1 步怎么做：快速独立审查（**2026-10-10 增补；目标 ≤ 5 分钟**）

**为什么要有这一步**：第 0 步的 AI 预审是**作者自查**——同一个上下文里，AI 已经知道你的意图、已经认同了你的取舍。所以再要一次"**不知道你是怎么想的**"的审查。

**为什么必须限时**：不设边界的对抗性审查会变成一次全仓研究——几十分钟、几十条风格建议，性价比立刻为负（本仓库历史上那个「自动审查」workflow 就是被手动停掉的）。**这一步是"体检"，不是"论文答辩"。**

| 项 | 要求 |
|---|---|
| 审查者 | **全新上下文**（新会话 / 新子代理 / 另一个工具都行），**不复用写代码时的对话** |
| 给它什么 | **只有两样**：改动范围（`git diff` / 分支）+ **下面这 4 个问题** |
| **不给什么** | 实现思路、可疑点、已有结论、预期结果、任何提示——**给了，这次审查无效** |
| 它做什么 | **只读 `git diff`**。**不做**：全量测试、全仓扫描、构造反例实验、历史追溯、跨模块深挖、风格建议 |
| 只回答 4 问 | ① 改动与 PR 里"改了什么"是否一致（**有没有夹带无关改动**）？② 有没有碰**契约字段 / 别人的目录 / 公共文件**？③ 有没有**真实密钥 / 大文件**，或把模拟数据说成实测这类**口径**问题？④ 有没有明显的逻辑错误、或**会挡住下游**的字段与接口不一致？ |
| 输出上限 | **≤ 10 行**：每条可执行发现写"文件:行号 + 一句话"；没有发现就写"**4 问全过，未发现可执行问题**" |
| **时限** | **目标 ≤ 5 分钟**。**5 分钟做不完，说明这个 PR 太大——拆 PR**，不要开更长的审查 |
| 结论去哪 | PR 的「**审查记录**」栏（模板已留位），**把审查者的原始结论原文贴进去**（只写"审过了"不算留痕） |
| 什么时候重发 | 修复**明显改变了做法**时，换一个全新上下文再跑一次，**只审改动过的部分** |

> **这一步不做的事**（写清楚，免得又变成全仓研究）：不做安全审计、不做性能分析、不做测试质量评估——那些属于 **池·Q 的独立验收**（手册第 17 章）和后续代码评审，不要塞进这个 5 分钟的框里。

### CI 门禁（**2026-10-10 增补**）

- 工作流：[`.github/workflows/ci.yml`](../.github/workflows/ci.yml)，**检查名固定为 `ci`**（仓库里还注册过一个已停用的「自动审查」workflow，不影响本项）；
- 跑什么：`python scripts/doc_gate.py` —— **六组检查**：① 编码（UTF-8 无 BOM）与换行；② 大文件与禁入类型（视频 / 权重 / 数据集 / 交付物 / `.env`）；③ Markdown 相对链接（**围栏代码块里的链接不算**）；④ JSON 可解析（含 [`数据契约.md`](数据契约.md) 的 json 围栏，大小写与 `~~~` 写法都认）；⑤ 密钥扫描（**只覆盖常见形态**——前缀式、`XXX_KEY=真值`、JSON 里的 `"xxx_key": "真值"`；**它不是保险箱，红线仍是不提交任何真实密钥**）；⑥ 契约字段 `snake_case`；
- 受管文本含 `.md` / `.py` / `.json` / `.yml` 与 `.sh` / `.ps1` / `.bat` / `.ts` / `.vue` / `.ets` 等代码类；**未列出的类型不查**；
- **本地与 CI 是同一条命令**（CI 里写 `python3`，同一脚本）：push 之前自己先跑一遍，别把红 check 留给别人；**门禁看的是 git 索引里的内容**，所以没 `git add` 的新文件也会被查到；
- 关于换行：仓库统一 LF 是由 [`.gitattributes`](../.gitattributes) 强制的，门禁**兜底**检查异常情况（未跟踪文件、绕过 clean 的 blob）；
- **带红 check 的 PR 一律视为未完成**，不得报告"做完了"；
- 以后加了代码（`work/**`），在同一个 workflow 里**按目录追加 job**（或按改动范围裁剪），**`ci` 这个 job 名不要改**——`main` 分支保护要 require 的就是它，**2026-10-10 起它已经是必需检查**（设置项见 [`仓库设置清单.md`](仓库设置清单.md)）。

### Reviewer 要看什么（**不用通读代码**）

Reviewer 不是从头读一遍 diff，只看三件事：

1. **AI 预审意见与快速独立审查的结论是否属实、有没有漏处理**——两块都要贴在 PR 的「审查记录」栏里；
2. **PR 描述里"有没有影响别人"那节是否属实**——动没动契约字段、动没动别人的目录、动没动公共文件；
3. **这个改动会不会影响答辩口径**——不得把"模拟数据"表述为实测、不得把"孪生算出来的数"说成实测、不得把"单站"说成"可复制"、不得把"MindSpore 链路已验证"说成"昇腾部署已验证"。

其余机械检查由**提交者自己**在 push 前走一遍（见 [`开发规范.md`](开发规范.md) 第 11 节的四条自检 + 门禁脚本）：
跑通自己的模块、字段名对得上契约、没改到别人的目录、`git status` 里没有 `.env` / 视频 / 权重、`python scripts/doc_gate.py` 全绿。

> 仓库上装了 **Sourcery**（第三方静态分析 App），它也会对 PR 出意见。**它查的是代码本身的通用问题**（安全模式、代码异味），**不挡合并**，也不必逐条响应——与项目口径无关的可以忽略。

### 一条硬规矩：PR 不能"挂着没人审"

推完 PR 之后，**在当天的站会上说一句"我开了 PR #N，请谁谁看一下"**。
PR 挂过夜是允许的，**挂过两个站会没人管就是流程失效**——此时找队长指派。

**PR 未完成的三种形态**（任何一种都不得报告"做完了"）：

1. **带红 check**（CI 没绿就合不了——**这是唯一被 GitHub 强制的一条**）；
2. **有没读 / 没处置的审查意见**；
3. **没填「审查记录」栏**（等于 AI 预审与快速独立审查两块都没留痕）。

## 5. 任务池（许愿池）怎么用（**共享盘 + 表格模板 + Issue 任务板**）

**一句话：协作成员不再定岗（N1~N4 已作废），改为从「任务池（许愿池）」认领任务**——以"填表格 + 交数据/测试记录/文档"为主，同时参与一部分技术开发（netedit 补画路网、控制点拾取、因素与场景配置、检查脚本、物料生成脚本）；**动到代码或脚本就走 PR**。

**角色简称**：开发A / 开发B / 开发C；**池·V / 池·S / 池·P / 池·Q** = 任务池四个系列（视频线 / 站点踏勘 / 参数调研 / 独立验收）的**认领者**（协作成员，无锁角色，原 N1~N4 定岗已作废）；**队长** = 7 人中 1 人兼任，**不参与认领**。术语正式名 **任务池**，对外口语 **许愿池**。

### 5.1 三条通道

| 通道 | 干什么 | 在哪 |
|---|---|---|
| **共享盘** | 干活的地方：填表、录屏、写文档、存素材 | 见 5.5 的目录结构 |
| **表格模板 T1~T9** | 填什么、列有哪些、谁写转换脚本 | 见 [`表格模板说明.md`](表格模板说明.md) |
| **Issue 任务板** | 任务的发布与认领：谁发布了什么、谁认领了、卡在谁那里 | 仓库的 [Issues](https://github.com/ouu2006/hubflow/issues)（**任务板 = GitHub Issues**） |

### 5.2 四个系列（**认领的就是这四类任务**）

| 系列 | 内容 | 类型 |
|---|---|---|
| **V 视频线** | CVAT 标注、控制点拾取、人工计数对账、断面适配器运行 | 操作 |
| **S 站点 / 踏勘** | 踏勘四合一、点位表维护、12306 → demand、netconvert 执行 | 操作 + vibecoding |
| **P 参数 / 调研** | 参数工作表、问卷、竞品记录 | 操作 |
| **Q 独立验收** | 校验器复跑、金样例回放、判定复跑、缺陷登记、总验收署名 | 验收（**回避规则**） |

**表 T1~T9 落在哪个系列**（与 [`表格模板说明.md`](表格模板说明.md) 同口径）：

| 表 | 内容 | 系列（谁填） | 转换脚本 |
|---|---|---|---|
| T1 | 点位表 | 池·S | 开发B |
| T2 | 路段属性核对表 | 池·S | 开发B |
| T3 | 列车时刻表 | 池·S | 开发A |
| T4 | 需求比例表 | 池·S | 开发A |
| T5 | 因素表 | 池·P | 开发A |
| T6 | 场景剧本表 | 池·S | 开发A |
| T7 | 测试检查表 | 池·Q（不进仓库） | — |
| T8 | 数据来源清单 | 池·P + **队长复核**（不进仓库） | — |
| T9 | 人工判读表（二期） | 池·P + 池·Q | 开发B |

### 5.3 任务怎么发布、怎么认领（**发布 1 条 + 认领 3 条**）

**发布规则**：任务由**对应 owner 发布**（开发A / 开发B / 开发C / 队长）；**vibecoding 类必须挂齐三件 prerequisite（输入样例 / 输出样例 / 自检脚本），缺一不得发布**；**发布必打难度标签 L0 / L1 / L2，L1 必附骨架与断点拆分**。细则见 [`hubflow-plan/04-协作任务池规程.md`](hubflow-plan/04-协作任务池规程.md)。

**三条认领规则**：

1. **验收回避**：系列 Q 任务的认领者 ≠ 该产物的生产者 / 运行者；**开发不得认领 Q**；
2. **系列续领权**：同系列任务优先由首启者续领，换人须留交接记录（要点 + 坑）；
3. **WIP ≤ 2 + 30 分钟上报**：每人同时进行中任务至多 2 个；卡住 30 分钟在 Issue @队长。

**状态流转**：**待领 → 进行中 → 待审（Issue 附产物 / PR）→ 完成（owner 审过关闭）**。

### 5.4 交接留痕（**认领者必做**）

认领者在 **Issue 评论**里写「**交了哪个文件、对着哪条判定、过没过**」——这一句就是唯一的过程证据，站会照着念。

### 5.5 共享盘目录结构（**照这个建，不要另起一套**）

```text
共享盘/
├── 01_站点包表格/        T1、T2（池·S）· T3~T6（池·S）· T9（二期，池·P + 池·Q）
├── 02_测试与验收/        T7 检查表、缺陷清单、录屏（池·Q）
├── 03_文档与演示/        文档、演示脚本、PPT（池·P）
├── 04_数据来源与合规/    T8 数据来源清单、授权材料、隐私告知（池·P + 队长复核）
└── 05_站会与交接/        站会记录、交接看板（队长 + 全员）
```

### 5.6 三条纪律

1. **文件名带日期与版本**：`T5_因素表_20261012_v3.xlsx`。**每天按日期留一版，永不覆盖同名文件**；
2. **拿不到官方数据就标【待核实】**，按现场照片 / 公开地图估算，**不许编一个数当真值**；
3. **`stations/` 下的 JSON 不许手改**——那是开发写的转换脚本的产物。要改数据就**改表格并升版本号**，再让脚本重跑。

### 5.7 交接看板（**一张纸就够，每天更新一次**）

| 列 | 填什么 |
|---|---|
| 谁 | 池·V / 池·S / 池·P / 池·Q（写认领者的人名 + 系列） |
| 交了什么文件 | 文件名 + 版本号（如 `T2_路段属性核对表_20261015_v4.xlsx`） |
| 对着哪条判定 | 如"T2 无空白、差异有原因（TC-15 前置）" |
| 过没过 | 过 / 没过 / 卡住 |
| 卡在谁那里 | 卡在开发B 的转换脚本 / 卡在底图权限 / 卡在队长裁定…… |

### 5.8 需要开发帮什么（**别自己动手，也别干等**）

| 情况 | 找谁 | 怎么找 |
|---|---|---|
| 表格要变成 `stations/` 的配置文件 | **T1 / T2 → 开发B；T3~T6 → 开发A；T9（二期）→ 开发B** | 站会上说一句"我这版表可以转了"，把文件路径发出来 |
| 表格列不够用 / 想加一列 | **开发B**（`stations/` 结构 owner） | 站会提出，由开发B 更新模板并同步改 [`表格模板说明.md`](表格模板说明.md) |
| 数据里发现路网缺失、点位对不上 | **开发A**（netedit 里补画路网） | 在表格里标"缺失"并在看板上写出来 |
| 要提 Issue / 要提交文件到仓库 | **owner 发布任务，成员认领**；要改代码/脚本的走 PR（**初期请开发C 代提交**） | 站会上说，或在 Issue 里 @队长 / 开发C |
| 判定值想放宽 | **不允许** | 只能由队长走总纲 / 手册修订流程 |

### 5.9 协作成员**不需要**做的事

不用装 Git、不用注册 GitHub、不用看代码、不用懂 JSON。**只需要：会填表、会按日期存文件、会在 Issue 里留下"交了哪个文件、对着哪条判定、过没过"。**

## 6. 冲突：停下来找队长

出现下面这样的提示就是冲突了：

```
CONFLICT (content): Merge conflict in work/engine/run.py
```

**不要瞎点、不要乱删代码。** 正确做法：

1. 停下手里的事；
2. 把冲突文件路径发给队长；
3. 队长当面一起解。

> 冲突大多来自"两个人改了同一个文件"。所以第 1 条（谁改哪个目录）是这份文档里最重要的一条。

## 7. 任务与卡点记在 Issue 里（**任务池的载体**）

**任务板 = GitHub Issues**：任务由**对应 owner 发布**（开发A / 开发B / 开发C / 队长），**协作成员在池子里认领**（细则见 5.3 与 [`hubflow-plan/04-协作任务池规程.md`](hubflow-plan/04-协作任务池规程.md)）。每条 Issue 写清：

- 标题：`[决策] 时段容量预约落地`；
- 标签：`孪生` / `感知` / `决策` / `定位` / `前端` / `接口` / `站点` / `文档`（八选一或几选）+ **系列标签（V / S / P / Q）+ 难度标签 L0 / L1 / L2**；
- 内容：要产出什么文件、依赖谁的什么、卡在哪里；
- **vibecoding 类必须挂齐三件 prerequisite（输入样例 / 输出样例 / 自检脚本），缺一不得发布**；**L1 必附骨架与断点拆分**；
- 做完就关掉。

**Issue 是给人看的，不用写得很正式**，一句话也行。

> 仓库里已有模板：新建 Issue 时选「每日任务」即可，格式已经填好。
> **每条 Issue 里请把对应周的「完成判定」一并贴进去**——否则大家只知道要交什么文件，不知道要做到什么程度。

## 8. 大文件与密钥不进仓库

**视频、模型权重、图片数据集一律不提交。**

`.gitignore` 已经拦住了 `*.mp4`、`*.pt`、`*.ckpt`、`*.onnx`、`*.safetensors` 等格式。如果你要用的文件被拦住了，说明它本来就不该进仓库——**放共享盘，把路径写进对应目录的 README**。

如果误提交了大文件：**立刻告诉队长**，不要自己折腾 `git filter-branch`。

> ⚠️ **本仓库是公开的（public）。** 地图 Key、密码、`.env` 一律不得提交。要配 Key：`cp .env.example .env` 后填进 `.env`（已被忽略）。**万一误提交了 Key，先去地图控制台把 Key 作废**，再找队长——顺序不能反，理由见 [`开发规范.md`](开发规范.md) 第 13.4 节。

## 9. 每天 15 分钟站会

**开发组**只回答三个问题：

1. 昨天产出了什么文件？
2. 今天要产出什么文件？
3. 卡在哪里？

**协作成员**只说一句话：

> **"我交了哪个文件（版本号）、对着哪条判定、过没过。"**

**卡住当场决定：谁帮，还是绕过去。**

---

## 10. 卡住怎么办

按总纲开篇纪律：**按默认口径先做下去，再提出来讨论，不要停下来等。**
只有一种情况要停下来——**要改判定值 / 要改契约字段 / 要动别人的目录**，这三件事必须当天说、由队长或开发B 裁定。
