## 0. 角色与权限（全队 7 人 = 3 名开发 + 3 名任务池协作成员 + 1 名队长兼任）

| 角色 | 技能 | 权限类型 | 载体 |
|---|---|---|---|
| **开发A** 孪生与路况（**区域负责人**） | 后端强 | **设计 + 实现**（模块内部自设计）+ **拆活与发布小任务** + **本区域日常技术复核** | `work/twin/`、`work/perception/`（**不含 `level.py`**） |
| **开发B** 决策与定位 + 判级（**区域负责人**） | 后端强 | **设计 + 实现 + 全部契约 schema 唯一裁定人**（上游契约 v2.0 既定）+ **判级** + **拆活与发布小任务** + **本区域日常技术复核** | `work/engine/`、`stations/` 结构、`tools/`、`contracts/`、**`work/perception/level.py`** |
| **开发C** 接口与双端（**区域负责人**） | 前端强 | 前端设计 + 实现；后端仅胶水（契约校验 import 开发B 的模型，**不写 schema**）+ **拆活与发布小任务** + **本区域日常技术复核** | `work/frontend/` `work/assembly/` |
| **协作成员 ×3** | 弱（初学 vibecoding：能跑不能设计） | **任务池（许愿池）认领**（操作 / 验收 / vibecoding 三类任务，规则见 §4）；**无锁角色** | 共享盘（日常产出）＋ 仓库（走 PR），产物经 Issue / PR 交接 |
| **队长（由 7 人中 1 人兼任）** | — | 拍板 / 合规 / 对外 / 非代码 PR 合并 / 计划类文档维护；不占代码目录，**不参与池子认领** | `docs/` 计划类文档、`scripts/`、决策记录 |

> ⚠️ **实际人数不是 3 名协作成员怎么办**：开发只有 2 人时，开发C 的**接口层并入开发A、App 降为 P1**；协作成员少于 3 人时**减少认领通道**（先保 V / S 两个系列），但 **Q 系列不得由开发兼任**、**开发一律不得认领验收任务**。

**开发是"区域负责人（派活方）"，协作成员是"接活方"**（2026-10-10 口径）：

- **三个区域**（沿用现有划分）：**开发A = 孪生与路况**（孪生链路 + 视频感知链路 + 数据同化）；**开发B = 决策与定位 + 判级**；**开发C = 接口与双端**。
- **区域负责人做什么**：① 把自己区域的活**发布到 GitHub Issues**（打难度标签 L0 / L1 / L2；vibecoding 类**建议**挂齐三 prerequisite：输入样例 / 输出样例 / 自检脚本）；② 对自己区域的产物做**日常技术复核**。**任务粒度由发布者自定，不强制拆到"半天可完成"**——**发出去之后，执行者觉得复杂可以自己拆，也可以用一条 PR 覆盖多条 Issue**（见下方"怎么派活"）。
- **怎么派活**：**只发布到任务池，一律认领**——**区域 owner 不点名、不指派**；**谁认领谁干，可单人可多人组队**；**挂久了没人接不用管、也不必拆小**（**不得改成点名**）。
- **与"独立验收"的区别**：区域 owner 的**日常技术复核**只是"看一眼产物对不对"，**不算验收结论**；**一期退出的独立验收（M1-1 ~ M1-10）仍走池·Q + 回避规则**——认领者 ≠ 该产物的生产者 / 运行者，**开发不得认领 Q**（见 §2）。

**本表不预设"哪条任务派给谁"。** 表中的「开发A / 开发B / 开发C」是**区域 owner 代号**，「池·V / 池·S / 池·P / 池·Q」是**任务认领者代号**——**具体谁来接，看 GitHub Issues 的任务池：谁认领谁干。**

> **注意这是两件事**：**模块 owner 与目录归属照写**（§1：这一层 / 这个文件谁维护，避免两个写手）；**"这一周哪条任务谁去做"不写**——派活走 Issues（谁认领谁干）。

- **可单人，也可多人**：一条任务**1 个人接也行，几个人一起接也行**（组队时在 Issue 评论里写明成员与分工，例如 V1 双人独立标注、V3 三人组队对账）；**验收类（系列 Q）仍适用回避规则**，且**开发不得认领 Q**。
- **人员名单（姓名 / GitHub / 权限）不在本表维护**：账号与权限见 GitHub 仓库协作者名单与 [`仓库设置清单.md`](仓库设置清单.md)；目录归属见 §0 与 [`协作规范.md`](协作规范.md) 第 1 节。

> **分支模型**：**没有常驻个人分支**——一条任务一条短分支 `task/<Issue号>-<简述>`（合并后删除），文档修订走 `docs/<主题>`；5 条 `feat/*` 已于 2026-10-10 删除（详见 [`协作规范.md`](协作规范.md) 第 2 节）。

## 2. 职责补丁（复查缺口，必须并入）

1. **独立验收机制**（不得由开发兼任）：验收类任务进任务池（**系列 Q**），由**回避规则**保证独立性——认领验收任务者**不得是该产物的生产者或运行者**；**一期退出的署名验收记录**由"总验收"任务认领者**主签**、另一名协作成员**复核副签**。**开发一律不得认领验收任务。**
   > **别把两件事混起来**：**区域 owner 对自己区域产物的"日常技术复核"**（拆活方顺带看一眼，**不算验收结论**）**≠** 这里的**独立验收**（`M1-1 ~ M1-10` 的退出判定）。后者必须由 **池·Q** 认领者独立执行，**开发不得认领 Q**。
2. **队长合规职责**（P2-0）：T8 数据来源清单、视频与地图授权申请、隐私告知、PIA、**真实数据接入前的合规门禁**——**即使兼任也显式保留，不并入"对外对接"一句话。**

## 3. TC-17 评测协议（A/B 实验因果性）

写进完成判定，不是任何人的内部设计：

1. 先开同化生成统一需求与初始状态，随后**固定随机种子与车辆群**（显式 `<vehicle>` / `<trip>` 需求文件；`saveState` 平台相关慎用）；
2. **评估期关闭在线 calibrator 增删车 / 清堵**（或明确声明为"完整闭环实验"并单列，**不得与算法收益混同归因**）；
3. 配对跑疏导**开 / 关两遍**，统计 **inserted / removed / not_entered / completed** 四计数；
4. KPI（总耗时、先入车不恶化、转移率 ≤ 0）**只在与共同车辆群可比的口径上比较**。

## 4. 任务池（许愿池）认领机制

**任务板 = GitHub Issues**。任务由**对应区域 owner 发布**（**开发A 孪生与路况 / 开发B 决策与定位 + 判级 / 开发C 接口与双端**；**发布必打难度标签 L0 / L1 / L2**；vibecoding 类**建议**挂齐三 prerequisite：**输入样例 / 输出样例 / 自检脚本**，骨架与断点拆分**是可选建议**）；**认领 = 在 Issue 里 self-assign / 评论"认领"即锁定**。

> **谁拆活、怎么派**：**区域 owner 发布，但不点名、不指派**——**只发到池子，一律认领**；谁认领谁干，可单人可多人组队。**没人接不用管、也不必拆小**（**不得改成点名**）；**Issue 只管提，拆分与 PR 组织由执行者决定——一条 Issue 可自拆多条，一条 PR 也可覆盖多条 Issue**（2026-10-10 业主口径）。

> **可单人，也可多人**：**一条任务 1 个人接也行，几个人一起接也行**——组队在 Issue 评论里写明**成员与分工**（例如 V1 双人独立标注、V3 三人组队对账）；**验收类（系列 Q）组队同样适用回避规则**。

> ⭐ **底层框架默认固定，但框架作者（开发A/B/C）有修改权；后面拆分出来的工作给推荐方式，不锁死做法**（2026-10-10 定）：**框架层（默认固定，但框架作者可改）**= 架构分层与模块边界、总体链路与口径、技术栈与选型、契约、确定性与可回放——改法：**契约→开发B 裁定 + 当天更新数据契约 + 通知全员；模块边界 / 总体链路→涉及的开发共同议定 + 通知受影响的人；技术栈→队长 / 业主拍板；确定性与可回放→实现可改但不得破坏**；**不可个人改**= 完成判定与数值、对外口径纪律、许可与合规红线（走总纲 / 手册修订流程）；**推荐（可自选）**= 模块**内部**怎么实现（算法与模型细节、栈内库与工具选择、命令与脚本写法、文件组织、伪代码路径）以及任务拆分粒度与排期。**换了推荐做法必须在 Issue / PR 的「实现方式」栏说明“用了什么方式 + 契约与判定不变”，并写进 `work/<模块>/DESIGN.md`**（完整清单见 [`开发规范.md`](开发规范.md) 文首总原则）。

**状态流转**：待领 → 进行中 → 待审（Issue 附产物 / PR）→ 完成（owner 审过关闭）。

**三条认领规则**：

| # | 规则 | 目的 |
|---|---|---|
| 1 | **验收回避**：系列 Q（验收）任务的认领者 ≠ 该产物的生产者 / 运行者；**开发不得认领 Q** | 独立验收不采信自述（上游 §4.6） |

## 10. 口径与纪律（每人必读）

> **本节正文于 2026-10-10 从原「角色 × 周」版分工表迁入。**
> 与 [`数据契约.md`](数据契约.md) 第八节、[`开发规范.md`](开发规范.md) 第 13 节重叠的部分**以那两份为准**；本节是**给每个人看的一页速查**。

| 项 | 口径 |
|---|---|
| **模拟数据标注** | 一期**全部**数值是演示数据（模拟），每个数值带 `is_simulated: true`，对外一律标 **「演示数据（模拟）· 双数据源（视频链路 + 孪生链路）」**（M1-7，抽查 100%） |
| **不把孪生说成真实仿真** | 孪生是**机制验证工具**，不是"真实交通仿真结果"；"产生数据"与"对照实验"两个用途的结论**不得混在一句话里说** |
| **不把视频链路说成现场实测** | 一期**就有**"视频识别 → 车流量"这一段（**视频感知链路**，`source: "video"`）：6 段真实样本视频 → YOLO → 透视标定 → 四项指标。**可以讲**"视频识别正在算路段拥堵"、"MindSpore 链路已验证"；但视频是**样本视频、非本站现场**，**不得**说成"现场实测"或"已在肇庆东站上线"，**不得**讲"昇腾部署已验证"。`.ckpt` 链路**一期即投入使用**，**不是**二期资产 |
| **不把真值说成 App 定位** | 一期定位**直接来自孪生真值**；二期才靠 App 定位 + 地图匹配（D2）。两条数据线**不做任何关联**（D3） |
| **demo 数值必须带标记** | `X_SAFE` = 0.85【待标定】、`EPS_HARM` = 30 s【待标定】、TC-17 的 ≤ 30 s【待标定】、TC-18 的 σ = 20 m 与 ≥ 90%【demo 目标值】、因素合成下限 40%【待标定】、二期 MAPE 与可用性【待标定】、**数据同化门控 `confidence < 0.6`【待标定】与 `data_age_s > 120 s`、TC-20 的流量偏差 ≤ 15% 与车速偏差 ≤ 20%【均为待标定】**——**引用时必须照抄标记** |
| **契约变更** | 改 `segments.json` / `routes.json` / `vehicles.json` 字段**必须当天在 Issue 里说**，由**开发B 裁定**并当天更新 `docs/数据契约.md` |
| **分工口径（本期裁定）** | **① 判级归开发B**：`work/perception/level.py` 与 **`thresholds.json` 两组参数（判级组 / 决策组）都归开发B**，该文件**只有一个写手**；`work/perception/` 是「**一目录两写手**」，例外的是**文件** `level.py`（**开发A 不含判级**）。**② 协作成员任务池认领**：**任务池（许愿池）认领制、无锁角色**，**N1~N4 定岗全部作废**；验收走**系列 Q + 回避规则**（开发不得认领）。**③ 分支模型**：**常驻个人分支取消**，改**一条任务一条短分支 `task/<Issue号>-<简述>`**，**合并后删除**，`main` 只经 PR + `ci` 绿 |
| **大文件与密钥** | 视频 / 权重 / 数据集 / `.env` 一律不进仓库（见 [`开发规范.md`](开发规范.md) 第 13 节） |
| **公共文件** | 根 `README.md`、`.gitignore`、`.github/`、`docs/数据契约.md`、路由注册**只由开发C 改**，其他人只提 Issue |
| **卡住怎么办** | 按总纲开篇纪律：**按默认口径先做下去，再提出来讨论，不要停下来等** |
