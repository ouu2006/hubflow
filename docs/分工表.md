# 分工表（角色 × 周 → 任务 → 交付文件 → **完成判定**）· V2.0

> **本文档解决的问题**：总纲 [`全流程计划.md`](全流程计划.md) 第 8 节说了"每个阶段要出什么"、第 9 节说了"8 个人分别是谁"——但都没落到三件事：**这一周谁做什么、交哪个文件、干到什么程度才算完**。本表把它补上，按 **W0–W10 全周期**展开。
>
> **怎么用**：
> ① 队长在第一节总表填「姓名」与「GitHub」两栏；
> ② 每人只看自己那一节：这周的**任务 → 交付文件 → 完成判定**；
> ③ 站会只说一句话：**"我交了哪个文件、对着哪条判定、过没过"**；
> ④ 验收岗（N3）按第六节逐条打勾，**打不出勾就是没做完**。
>
> **判定值来源**：手册第 17 章（TC-01~TC-20、M1-1~M1-10、M2-1~M2-9）、[`全流程计划.md`](全流程计划.md) 第 6/8/9/10 节、手册第 5/6/7/11/12 章。**本表不新造任何数字。** 带【待标定】【demo 目标值】【建议值】的数值一律照抄标记，**不得当成承诺对外说**。
>
> **周期口径**：**W0 是阶段 0（1–2 周）；W1–W10 是一期十周**，周期均为**建议值**，按人力可投入情况调整，**不是承诺工期**。每个阶段（每两周）的出门条件不满足，不得进入下一阶段。
>
> **一句话记住本版变化**：**全队 7 人 = 3 名开发（主写代码）+ 4 名协作成员（数据/测试/文档为主，同时参与部分技术开发）；队长由其中 1 人兼任（身份，不额外占编、不写业务代码）**；旧的"感知线 / 决策线 / 前端 / 后端 / 数据与标注 / 验收与测试 / 文档与演示"七个位置名**全部作废**。

## 二、开发组怎么用 GitHub（**只教四条命令**）

**一个仓库**（`hubflow`）、**每人一条分支**、**`main` 有保护不许直推**、**所有改动走 Pull Request**。

| 角色 | 分支 | 只改这些目录 |
|---|---|---|
| 开发A | `feat/twin`（**已建 2026-10-10**） | `work/twin/`、`work/perception/`（**孪生链路 + 视频感知链路**：检测跟踪、透视标定、四项指标、判级） |
| 开发B | `feat/engine` | `work/engine/`、`stations/`（结构与脚本产物） |
| 开发C | `feat/frontend` | `work/frontend/`、`work/assembly/`、公共文件 |

> `feat/perception`、`feat/backend` **停用**（不删除，二期视需要复用）；文档类修订走临时分支 `docs/*`。

### 2.1 四条命令（每天就这四条，别的不用学）

```bash
# ① 开工前：切回自己的分支，拉最新
git checkout feat/twin        # 开发B 写 feat/engine，开发C 写 feat/frontend
git pull

# ... 让 AI 写代码，自己跑通 ...

# ② 收工前：看一遍自己改了哪些文件
git status
git diff

# ③ 提交（前缀见 开发规范.md 第 10 节）
git add .
git commit -m "孪生：虚拟检测器输出四项指标时序"

# ④ 推上去（第一次推新分支用 git push -u origin feat/twin）
git push
```

### 2.2 开 PR：标题 + 三件事

推完分支后在网页上点 **Compare & pull request**，描述里写三件事（模板已建好）：

1. **改了什么**（文件 + 一句话）；
2. **怎么验证的**（跑了哪条命令、看到什么、附上自测记录）；
3. **有没有影响别人**（有没有动契约字段、别人的目录、公共文件）。

**不要自己点 Merge。**

### 2.3 谁审谁（**开工前先看清楚**）

| 顺序 | 谁做 | 看什么 |
|---|---|---|
| **第 0 步** | **提交者自己：先让 AI 审一遍** | 把 `git diff` 贴给 AI，让它按 [`开发规范.md`](开发规范.md) 第 11 节的四条自检 + "有没有动契约字段 / 别人的目录"过一遍，**把 AI 的预审意见贴进 PR 描述**。AI 预审**不替代人审**，只是把低级问题挡在前面 |
| **第 1 步** | **代码互审：A 审 B、B 审 C、C 审 A** | 开发A 审开发B 的 PR、开发B 审开发C 的 PR、开发C 审开发A 的 PR。**谁都不能审自己的 PR**（GitHub 也不允许作者 Approve） |
| **第 2 步** | **队长兜底** | 只看两件机器判不了的事：**① 有没有影响别人**（契约字段 / 别人的目录 / 公共文件）；**② 会不会影响对外口径**（不得把模拟说成实测、不得把单站说成可复制） |

| 特殊情况 | 谁审 + 谁合并 |
|---|---|
| **改了公共文件**（根 `README.md`、`.gitignore`、`.github/`、`docs/数据契约.md`、路由注册） | **只能由开发C 改**，改完**队长复核**，队长合并 |
| **改了契约字段**（`segments.json` / `routes.json` / `vehicles.json`） | **开发B 裁定**（唯一裁定人）+ 队长确认，**当天更新 `docs/数据契约.md` 并通知全员** |
| **计划类文档**（全流程计划、分工表、协作规范、手册、表格模板说明） | **队长维护**（可请开发C 代提交），走 `docs/*` 临时分支 |
| **站点包数据**（表格转换产物） | 开发B / 开发A 生成，**转换脚本进 PR**，队长合并 |
| **代码 PR 的合并人** | **互审人**（A 审 B → A 合并 B 的 PR）；队长不占代码目录，只合并非代码类 PR |

**一条硬规矩**：推完 PR 之后，**在当天站会上说一句"我开了 PR #N，请谁谁看一下"**。PR 挂过夜允许，**挂过两个站会没人管就是流程失效**——此时找队长指派。

## 三、协作成员怎么用（共享盘 + 表格模板，**技术活也有一份**）

**原则：协作成员以"填表格 + 交数据/测试记录/文档"为主，同时参与一部分技术开发。** 业务数据只从表格进；开发写转换脚本，把表格转成 `stations/` 下的配置文件（总纲第 10 节）。

**他们参与的技术开发**：N1 用 `netedit` 补画缺失路段、**拾取视频链路的透视标定控制点（≥4 组，推荐 6–8 组）**、校核点位坐标、**填断面 ↔ SUMO edge 映射**；N2 配置因素与场景参数、准备预测特征表、生成人工判读标签；N3 把用例写成自动化检查脚本、跑压测与回放；N4 写演示物料与文档生成脚本。**开发组给模板 + 样例 + AI 投喂卡，协作成员用 AI 改脚本；动到代码或脚本就走 PR**（开发C 代提交或自己提交），由互审人 + 队长复核。

| 项 | 口径 |
|---|---|
| **在哪干活** | **日常产出在共享盘**（目录结构与命名规则见 [`协作规范.md`](协作规范.md) 第 5 节）；**不需要 Git 也能干活**。要动代码/脚本时走 PR——**初期由开发C 代提交，愿意自己提交的按"四条命令"来（鼓励）** |
| **填什么** | **T1~T9 九个模板**，列定义逐个见 [`表格模板说明.md`](表格模板说明.md) |
| **谁转成 JSON** | T1 / T2 → **开发B**；T3 / T4 / T5 / T6 → **开发A**；T7 / T8 **不进仓库**；T9（二期）→ **开发B** |
| **每天留档** | 文件名带日期与版本（`T5_因素表_20261012_v3.xlsx`），**每天按日期留一版，永不覆盖同名文件** |
| **拿不到官方数据** | 按现场照片 / 公开地图估算，**逐项标【待核实】** |
| **站会只说一句** | **"我交了哪个文件、对着哪条判定、过没过"**（不说"我做了什么"） |
| **表格转 JSON 之后** | **不许手改 `stations/` 下的 JSON**——改了下次跑脚本就被覆盖。要改就改表格并升版本号 |

## 七、口径与纪律（每人必读）

| 项 | 口径 |
|---|---|
| **模拟数据标注** | 一期**全部**数值是演示数据（模拟），每个数值带 `is_simulated: true`，对外一律标 **「演示数据（模拟）· 双数据源（视频链路 + 孪生链路）」**（M1-7，抽查 100%） |
| **不把孪生说成真实仿真** | 孪生是**机制验证工具**，不是"真实交通仿真结果"；"产生数据"与"对照实验"两个用途的结论**不得混在一句话里说** |
| **不把视频链路说成现场实测** | 一期**就有**"视频识别 → 车流量"这一段（**视频感知链路**，`source: "video"`）：6 段真实样本视频 → YOLO → 透视标定 → 四项指标。**可以讲**"视频识别正在算路段拥堵"、"MindSpore 链路已验证"；但视频是**样本视频、非本站现场**，**不得**说成"现场实测"或"已在肇庆东站上线"，**不得**讲"昇腾部署已验证"。`.ckpt` 链路**一期即投入使用**，**不是**二期资产 |
| **不把真值说成 App 定位** | 一期定位**直接来自孪生真值**；二期才靠 App 定位 + 地图匹配（D2）。两条数据线**不做任何关联**（D3） |
| **demo 数值必须带标记** | `X_SAFE` = 0.85【待标定】、`EPS_HARM` = 30 s【待标定】、TC-17 的 ≤ 30 s【待标定】、TC-18 的 σ = 20 m 与 ≥ 90%【demo 目标值】、因素合成下限 40%【待标定】、二期 MAPE 与可用性【待标定】、**数据同化门控 `confidence < 0.6`【待标定】与 `data_age_s > 120 s`、TC-20 的流量偏差 ≤ 15% 与车速偏差 ≤ 20%【均为待标定】**——**引用时必须照抄标记** |
| **契约变更** | 改 `segments.json` / `routes.json` / `vehicles.json` 字段**必须当天在 Issue 里说**，由**开发B 裁定**并当天更新 `docs/数据契约.md` |
| **大文件与密钥** | 视频 / 权重 / 数据集 / `.env` 一律不进仓库（见 [`开发规范.md`](开发规范.md) 第 13 节） |
| **公共文件** | 根 `README.md`、`.gitignore`、`.github/`、`docs/数据契约.md`、路由注册**只由开发C 改**，其他人只提 Issue |
| **卡住怎么办** | 按总纲开篇纪律：**按默认口径先做下去，再提出来讨论，不要停下来等** |
