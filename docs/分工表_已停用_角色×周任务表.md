# 分工表（角色 × 周 → 任务 → 交付文件 → **完成判定**）· V2.1

> **本文档解决的问题**：总纲 [`全流程计划.md`](全流程计划.md) 第 8 节说了"每个阶段要出什么"、第 9 节说了"7 个人分别是谁"——但都没落到三件事：**这一周谁做什么、交哪个文件、干到什么程度才算完**。本表把它补上，按 **W0–W10 全周期**展开。
>
> **怎么用**：
> ① 队长在第一节总表填「姓名」与「GitHub」两栏；
> ② 每人只看自己那一节：这周的**任务 → 交付文件 → 完成判定**；
> ③ 站会只说一句话：**"我交了哪个文件、对着哪条判定、过没过"**；
> ④ 验收岗（**池·Q**）按第六节逐条打勾，**打不出勾就是没做完**。
>
> **判定值来源**：手册第 17 章（TC-01~TC-20、M1-1~M1-10、M2-1~M2-9）、[`全流程计划.md`](全流程计划.md) 第 6/8/9/10 节、手册第 5/6/7/11/12 章。**本表不新造任何数字。** 带【待标定】【demo 目标值】【建议值】的数值一律照抄标记，**不得当成承诺对外说**。
>
> **周期口径**：**W0 是阶段 0（1–2 周）；W1–W10 是一期十周**，周期均为**建议值**，按人力可投入情况调整，**不是承诺工期**。每个阶段（每两周）的出门条件不满足，不得进入下一阶段。
>
> **一句话记住本版变化（V2.1）**：**全队 7 人 = 3 名开发（A / B / C）+ 3 名任务池协作成员 + 1 名队长（由 7 人中 1 人兼任，不额外占编）**；协作成员**不再定岗**，改为**任务池（许愿池）认领制、无锁角色**，**N1 / N2 / N3 / N4 定岗全部作废**；**判级 `level.py` 与 `thresholds.json` 判级参数组归开发B**；常驻个人分支取消，改**一条任务一条短分支 `task/<Issue号>-<简述>`**。旧的"感知线 / 决策线 / 前端 / 后端 / 数据与标注 / 验收与测试 / 文档与演示"七个位置名**全部作废**。

### 2.1 四条命令（每天就这四条，别的不用学）

```bash
# ① 开工前：从最新 main 切出任务分支（例：认领 Issue #12）
git checkout main && git pull
git checkout -b task/12-t1-points

# ② 收工前：看一遍自己改了哪些文件
git status
git diff

# ③ 提交（前缀见 开发规范.md 第 10 节）
git add .
git commit -m "站点：T1 点位表转 points.json"

# ④ 推上去
git push -u origin task/12-t1-points
```

### 2.2 开 PR：标题 + 四件事

推完分支后在网页上点 **Compare & pull request**，描述里写四件事（模板已建好）：

1. **改了什么**（文件 + 一句话）；
2. **怎么验证的**（跑了哪条命令、看到什么、附上自测记录；含本地门禁 `python scripts/doc_gate.py` 与 CI 结论）；
3. **审查记录**（**AI 预审**意见 + **快速独立审查**的 4 问结论，见第 2.3 节第 1 步）；
4. **有没有影响别人**（有没有动契约字段、别人的目录、公共文件）。

**不要自己点 Merge。**

> ⚠️ **2026-10-10 起 GitHub 不再强制人工 approve**：`main` 只强制"**必须走 PR** + **`ci` 必须绿**"（实测见 [`仓库设置清单.md`](仓库设置清单.md)）——**没人批也点得动合并按钮**，四道关靠纪律与 PR 里的「审查记录」栏留痕。

| **第 0 步** | **提交者自己 + CI 门禁** | ① 四条自检（[`开发规范.md`](开发规范.md) 第 11 节）；② 把 `git diff` 贴给 AI 预审（**自查，不替代人审**）；③ 跑 `python scripts/doc_gate.py`（**与 CI 同一条命令**，检查名 `ci`）；④ **红 check 自己修到绿**，不留给别人 |
| **第 1 步** | **快速独立审查**（全新上下文，**目标 ≤ 5 分钟**） | 只给"**改动范围 + 4 个问题**"，**不给**实现思路 / 可疑点 / 既有结论 / 任何提示（给了这次审查无效）；只读 `git diff`；结论 **≤ 10 行**填进 PR 的「审查记录」栏。**5 分钟做不完说明 PR 太大 → 拆 PR**。4 个问题见 [`协作规范.md`](协作规范.md) 第 4 节 |
| **第 2 步** | **代码互审：A 审 B、B 审 C、C 审 A** | 开发A 审开发B 的 PR、开发B 审开发C 的 PR、开发C 审开发A 的 PR。**谁都不能审自己的 PR**（GitHub 也不允许作者 Approve） |
| **第 3 步** | **队长兜底** | 只看两件机器判不了的事：**① 有没有影响别人**（契约字段 / 别人的目录 / 公共文件）；**② 会不会影响对外口径**（不得把模拟说成实测、不得把单站说成可复制） |

| 特殊情况 | 谁审 + 谁合并 |
|---|---|
| **改了公共文件**（根 `README.md`、`.gitignore`、`.github/`、`docs/数据契约.md`、路由注册） | **只能由开发C 改**，改完**队长复核**，队长合并 |
| **改了契约字段**（`segments.json` / `routes.json` / `vehicles.json`） | **开发B 裁定**（唯一裁定人）+ 队长确认，**当天更新 `docs/数据契约.md` 并通知全员** |
| **计划类文档**（全流程计划、分工表、协作规范、手册、表格模板说明） | **队长维护**（可请开发C 代提交），走 `docs/<主题>` 分支 |
| **站点包数据**（**表格 → 脚本生成的产物**） | 表格由**协作成员按系列 S / V 认领填写**（T1 / T2 → 池·S，控制点与断面映射 → 池·V，T3~T6 → 池·S / 池·P）；**转换脚本归开发B**（T3 / T4 / T5 / T6 → 开发A）——**JSON 不许手改**；脚本与产物变更走 PR，**队长合并** |
| **代码 PR 的合并人** | **互审人**（A 审 B → A 合并 B 的 PR）；队长不占代码目录，只合并非代码类 PR |

**一条硬规矩**：推完 PR 之后，**在当天站会上说一句"我开了 PR #N，请谁谁看一下"**。PR 挂过夜允许，**挂过两个站会没人管就是流程失效**——此时找队长指派。

**PR 未完成的三种形态**：① 带红 check；② 有没读 / 没处置的审查意见；③ 没填「审查记录」栏。**其中只有 ① 会被 GitHub 拦住（`ci` 是必需检查）；②③ 靠自觉与站会追问。**

## 三、任务池（许愿池）怎么用（共享盘 + 表格模板 + Issue 任务板）

**原则：协作成员是"任务池认领制、无锁角色"——不预设固定岗位，认领哪个系列就干哪个系列的活。** 日常产出以"填表格 + 交数据 / 测试记录 / 文档"为主，同时参与一部分技术开发（vibecoding 类任务）。业务数据**只从表格进**；**开发写转换脚本**，把表格转成 `stations/` 下的配置文件（总纲第 10 节）。**N1 / N2 / N3 / N4 定岗全部作废。**

**任务板 = GitHub Issues。** 任务由**对应 owner 发布**；**vibecoding 类必须挂齐三件 prerequisite（输入样例 / 输出样例 / 自检脚本），缺一不得发布**；**发布必打难度标签 L0 / L1 / L2，L1 必附骨架与断点拆分**（细则见 [`hubflow-plan/04-协作任务池规程.md`](hubflow-plan/04-协作任务池规程.md)）。

**四个系列**：

| 系列 | 内容 | 类型 |
|---|---|---|
| **V 视频线** | CVAT 标注、控制点拾取、人工计数对账、断面适配器运行 | 操作 |
| **S 站点 / 踏勘** | 踏勘四合一、点位表维护、12306 → demand、netconvert 执行 | 操作 + vibecoding |
| **P 参数 / 调研** | 参数工作表、问卷、竞品记录 | 操作 |
| **Q 独立验收** | 校验器复跑、金样例回放、判定复跑、缺陷登记、总验收署名 | 验收（**回避规则**） |

**三条认领规则**：

1. **验收回避**：系列 Q 任务的认领者 ≠ 该产物的生产者 / 运行者；**开发不得认领 Q**；
2. **系列续领权**：同系列任务优先由首启者续领，换人须留**交接记录（要点 + 坑）**；
3. **WIP ≤ 2 + 30 分钟上报**：每人同时进行中任务至多 2 个；卡住 30 分钟在 Issue @队长。

**状态流转**：**待领 → 进行中 → 待审**（Issue 附产物 / PR）**→ 完成**（owner 审过关闭）。

**交接留痕**：认领者在 Issue 评论里写「**交了哪个文件、对着哪条判定、过没过**」。

**T1~T9 → 系列对照**（`表格模板说明.md` 与相关表格用）：

| 表 | 内容 | 系列（谁填） | 转换脚本 |
|---|---|---|---|

| **T2** | 路段属性核对表 | **池·S** | 开发B |
| **T3** | 列车时刻表 | **池·S** | 开发A |
| **T4** | 需求比例表 | **池·S** | 开发A |
| **T5** | 因素表 | **池·P** | 开发A |
| **T6** | 场景剧本表 | **池·S** | 开发A |

**他们参与的技术开发**：**池·V** 用 `netedit` 补画缺失路段、**拾取视频链路的透视标定控制点（≥ 4 组，推荐 6–8 组）**、校核点位坐标、**填断面 ↔ SUMO edge 映射**；**池·S** 配置因素与场景参数、准备预测特征表；**池·P** 生成人工判读标签、写演示物料与文档生成脚本；**池·Q** 把用例写成自动化检查脚本、跑压测与回放。**开发组给模板 + 样例 + AI 投喂卡，协作成员用 AI 改脚本；动到代码或脚本就走 PR**（开发C 代提交或自己提交），由互审人 + 队长复核。

| 项 | 口径 |
|---|---|
| **在哪干活** | **日常产出在共享盘**（目录结构与命名规则见 [`协作规范.md`](协作规范.md) 第 5 节）；**不需要 Git 也能干活**。要动代码 / 脚本时走 PR——**初期由开发C 代提交，愿意自己提交的按"四条命令"来（鼓励）** |
| **填什么** | **T1~T9 九个模板**，列定义逐个见 [`表格模板说明.md`](表格模板说明.md) |

| **表格转 JSON 之后** | **不许手改 `stations/` 下的 JSON**——改了下次跑脚本就被覆盖。要改就改表格并升版本号 |

## 六、验收岗怎么用这张表

**验收岗 = 池·Q（任务池系列 Q 的认领者，回避规则）**：对**每个角色的每一周**，按"完成判定"逐条打勾：

| 打勾结果 | 含义 |
|---|---|
| **全部勾上** | 该角色本周完成 |
| **有勾不上的** | **就是没做完**——不是"基本完成"，也不是"下轮补" |
| **判定本身做不了**（如上游数据没到、环境装不上） | 记为**阻塞**，升级队长裁定，**不得自行降标准** |

**三条硬规矩**：

1. **判定值不许改。** 本表所有门槛摘自手册第 17 章、[`全流程计划.md`](全流程计划.md) 与手册正文；要改判定走总纲 / 手册修订流程，**不能在分工表里悄悄放宽**——那等于自己给自己发合格证。
2. **验收必须独立于开发。** 验收任务进**系列 Q**，由**回避规则**保证独立性——**认领者 ≠ 该产物的生产者 / 运行者**，**开发一律不得认领验收任务**（总纲 9.1）；实测与自测不一致时**以池·Q 为准**。
3. **一期退出条件**：**M1-1 ~ M1-10 全过**方可进入二期；**任一项不过，二期不得开工**。

**池·Q 每周要交的三样东西**：① 打勾版的 T7 检查表（带日期版本）；② 录屏 / 截图证据（命名带日期与用例号）；③ 缺陷清单更新（有严重度与状态）。

**一期退出的署名验收记录**：由"**总验收**"任务认领者**主签**、另一名协作成员**复核副签**（见 1.1 ⑤ 与 [`hubflow-plan/04-协作任务池规程.md`](hubflow-plan/04-协作任务池规程.md)）。

## 七、口径与纪律（每人必读）

| 项 | 口径 |
|---|---|
| **模拟数据标注** | 一期**全部**数值是演示数据（模拟），每个数值带 `is_simulated: true`，对外一律标 **「演示数据（模拟）· 双数据源（视频链路 + 孪生链路）」**（M1-7，抽查 100%） |
| **不把孪生说成真实仿真** | 孪生是**机制验证工具**，不是"真实交通仿真结果"；"产生数据"与"对照实验"两个用途的结论**不得混在一句话里说** |
| **不把视频链路说成现场实测** | 一期**就有**"视频识别 → 车流量"这一段（**视频感知链路**，`source: "video"`）：6 段真实样本视频 → YOLO → 透视标定 → 四项指标。**可以讲**"视频识别正在算路段拥堵"、"MindSpore 链路已验证"；但视频是**样本视频、非本站现场**，**不得**说成"现场实测"或"已在肇庆东站上线"，**不得**讲"昇腾部署已验证"。`.ckpt` 链路**一期即投入使用**，**不是**二期资产 |
| **不把真值说成 App 定位** | 一期定位**直接来自孪生真值**；二期才靠 App 定位 + 地图匹配（D2）。两条数据线**不做任何关联**（D3） |
| **demo 数值必须带标记** | `X_SAFE` = 0.85【待标定】、`EPS_HARM` = 30 s【待标定】、TC-17 的 ≤ 30 s【待标定】、TC-18 的 σ = 20 m 与 ≥ 90%【demo 目标值】、因素合成下限 40%【待标定】、二期 MAPE 与可用性【待标定】、**数据同化门控 `confidence < 0.6`【待标定】与 `data_age_s > 120 s`、TC-20 的流量偏差 ≤ 15% 与车速偏差 ≤ 20%【均为待标定】**——**引用时必须照抄标记** |
| **契约变更** | 改 `segments.json` / `routes.json` / `vehicles.json` 字段**必须当天在 Issue 里说**，由**开发B 裁定**并当天更新 `docs/数据契约.md` |
