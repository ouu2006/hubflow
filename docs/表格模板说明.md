# 表格模板说明（T1~T9）· V2.1

> **这份文档解决一件事**：**任务池成员填什么表、每张表有哪些列、填成什么样算合格，以及这张表由哪个脚本变成 `stations/` 下的哪个配置文件。**
>
> **总原则**（总纲第 10 节）：**任务池成员以填表格为主，同时参与一部分技术开发（转换脚本、检查脚本、因素与场景配置等）；业务数据只从表格进。** 开发写转换脚本，把表格转成 `stations/` 下的配置文件。表格放共享盘，文件名带日期与版本，永不覆盖。
>
> **任务从哪来**：**任务由对应 owner 在 GitHub Issues 发布，成员认领**（细则见 [`hubflow-plan/04-协作任务池规程.md`](hubflow-plan/04-协作任务池规程.md)）；**N1~N4 定岗已作废**，改为**任务池认领制**——本文件里的"谁填"一律写**系列**：**池·V**（视频线）/ **池·S**（站点踏勘）/ **池·P**（参数调研）/ **池·Q**（独立验收）。
>
> **配套文档**：[`全流程计划.md`](全流程计划.md)（总纲，第 10 节是表格驱动的来源）、[`分工表.md`](分工表.md)（**项目分工表**：架构层职责表、模块 owner、交付物与完成判定）、[`开发规范.md`](开发规范.md)（第 7 节是转换脚本的硬要求）、[`协作规范.md`](协作规范.md)（第 5 节是任务池、共享盘目录与交接看板）。
>
> **一期用 T1~T8，二期用 T9。** 一期全部数值都是**演示数据（模拟）**，任何进入 `stations/` 的数值最终都标 `is_simulated: true`。

## 二、填表通用纪律（**九张表都适用，先看这一节**）

| # | 纪律 | 具体怎么做 |
|---|---|---|
| 1 | **文件名带日期与版本** | `T5_因素表_20261012_v3.xlsx`。日期用 `YYYYMMDD`，版本从 `v1` 起 |
| 2 | **永不覆盖同名文件** | 每天按日期留一版；要改就在新版本上改，**不许把昨天的文件覆盖掉** |
| 3 | **拿不到官方数据就标【待核实】** | 按现场照片 / 公开地图估算，**逐项标【待核实】**，不许留空白、不许编一个数当真值 |
| 4 | **列名不许自己改** | 要加列 / 改列名，**先在站会上说**，由 **开发B（结构 owner）** 更新模板并同步改本文件，然后大家再用新模板 |
| 5 | **谁填谁签字** | 每张表最后两列是 `填表人` 与 `日期`，**每行都要有** |
| 6 | **`stations/` 下的 JSON 不许手改** | 那是脚本产物。要改数据就改表格并升版本号，然后让脚本重跑（[`开发规范.md`](开发规范.md) 第 7 节） |
| 7 | **不许写真实个人信息** | 车牌、人脸、个人定位轨迹一律不填；一期是演示数据（模拟），二期也不许把真实个人信息写进表格 |
| 8 | **一版一交接** | 交表时在站会上说一句：**"我交了 `T5_..._v3`，对着第 3 节的判定，过没过"** |

## 三、T1 点位表（池·S 填 → `stations/points.json`，脚本：开发B）

**用途**：把站前区域的**点位**标出来——落客点、上客点、候客区、**检测断面**、平交路口。
**关键口径**：`detector` 类点位 = **检测断面**。**一期这里放虚拟检测器，二期这里放摄像头**（同一个位置、同一套字段），这样二期换数据源不改下游（D1）。
**数据同化的映射也在这张表上**：检测断面的 **`role`（`boundary` / `internal`）+ `sumo_edge_id`** 就是"视频实测该灌给孪生的哪条边"的唯一出处（开关在 T6 的 `assimilation` 列，见第八节）。

| 列名 | 必填 | 说明 | 示例值 |
|---|---|---|---|
| `point_id` | 必填 | 点位编号，前缀表类型：`DROP-` 落客 / `PICK-` 上客 / `WAIT-` 候客 / `DET-` 检测断面 / `JCT-` 路口 | `DROP-03` |
| `name` | 必填 | 中文名（管理端要显示） | 站前落客区 A |
| `type` | 必填 | `dropoff` / `pickup` / `waiting` / `detector` / `junction` 五选一 | `dropoff` |
| `lon` / `lat` | 必填 | 经纬度（写明坐标系，默认 WGS-84；与底图不一致时标【待核实】） | 112.5861 / 23.0735 |
| `segment_id` | 必填 | 落在哪条路段，**必须能在 T2 里找到** | `SEG-004` |
| `offset_m` | 必填 | 距该路段起点的米数 | 85 |
| `direction` | 必填 | 朝向：上行 / 下行 | 上行 |
| `capacity_vph` | 条件必填 | 只给落客点 / 上客点 / 候客区填：服务能力（辆/小时），**一期为估算值** | 180【待标定】 |
| `role` | **必填**（所有点位都填，`detector` 尤其关键） | **点位角色**：`boundary` = **围栏外 → 站前的上游边界断面**（**只有这一类才允许数据同化回灌**）；`internal` = **站前内部路段**（落客通道 / 候客区 / 离站方向）的断面；非 `detector` 点位填 `internal` | `boundary` |
| `sumo_edge_id` | **必填**（`detector` 必填，其余可填所在 edge） | **该点位 / 断面对应的 SUMO edge id**（`stations/sumo/*.net.xml` 里的边编号）。SUMO 的 `<calibrator>` 就挂在这条边上，**映射错了就灌到别的路上** | `E-012` |
| `detector_role` | 条件必填 | 只给 `detector` 填：**一期 = 虚拟检测器；二期 = 摄像头** | 一期虚拟检测器 |
| `source` | 必填 | 来源：现场照片 / 公开地图 / 估算 / 官方资料 | 公开地图 + 现场照片 |
| `verified` | 必填 | 已核实 / 待核实 | 待核实 |
| `filler` / `date` | 必填 | 填表人与日期 | 池·S / 2026-10-12 |

**填表纪律**：

1. **五类点位每类至少 1 条**（W1 判定）；
2. **检测断面清单必须交给开发A 对齐**——孪生里虚拟检测器就布在这些点位上；
3. 每个点位的 `segment_id` 必须能在 T2 里查到，**查不到就是这条没填完**；
4. 转换后 `points.json` 的条数**必须等于表格行数**，对不上要逐条写原因；
5. **`role` 与 `sumo_edge_id` 是必填**，`detector` 缺任一列**不算填完**；**`role` 只能取 `boundary` / `internal` 两个值**，并能在站会上说清"为什么这个断面算边界断面"；
6. **边界断面才允许回灌**：**只有 `role = boundary` 的断面**，视频链路的实测流量 / 车速才会通过 SUMO `calibrator` 每 **60 s** 回灌给孪生；**`internal` 断面一个都不许回灌**——否则孪生被钉死、推荐再也改变不了路况（**TC-20 第②项**专验）。一期至少 **1 个 `boundary` 断面**（**M1-10**），二期全部 `boundary` 断面在线闭环 + 熔断（**M2-9**）；
7. **边界断面清单要冻结**：池·S 填完由开发A / 开发B 核对、**队长签字冻结**；冻结后要改走变更流程（改表格 → 升版本号 → 重跑脚本）。

**关键口径**：**TC-15 = T2 路段属性核对表全部打勾；SUMO 路网与高德底图逐条一致或注明差异原因。**"不一致"也算打勾，**但必须写原因**。

| 列名 | 必填 | 说明 | 示例值 |
|---|---|---|---|

| `from_node` / `to_node` | 必填 | 起终点节点编号（OSM / netconvert 产出） | `N-012` / `N-018` |
| `length_m` | 必填 | 路段长度（米） | 380 |
| `lanes` | 必填 | 车道数 | 3 |
| `speed_limit_kmh` | 必填 | 限速（km/h） | 40 |
| `c_vph` | 必填 | 通行能力（辆/小时）；**拿不到官方值就估算并标【待标定】** | 1288【待标定】 |
| `oneway` | 必填 | 是 / 否（单双向） | 是 |
| **底图核对** | 必填 | **只有三种取值：一致 / 不一致 / 待核实，没有空白格** | 不一致 |
| **差异原因** | 条件必填 | 填"不一致"时必须写；填"一致"可空 | 高德底图此处两车道，实地三车道 |

**填表纪律**：

1. **没有空白格**——不确定就写"待核实"；
2. 缺失路段**不由池·S 自己画**：在表里标"缺失"并告诉开发A，由开发A 在 netedit 里补画（总纲风险 3 的应对）；
3. 差异原因写"人话"（如"底图两车道、实地三车道"），不要写"数据不符"这种看不出问题的话。

| 列名 | 必填 | 说明 | 示例值 |

| `train_no` | 必填 | 车次 | `G1234` |
| `direction` | 必填 | 到达 / 出发 | 到达 |
| `time` | 必填 | 计划时刻（HH:MM） | 17:42 |
| `delay_min` | 选填 | 典型晚点分钟数（一期手填） | 5【待核实】 |
| `platform` | 选填 | 站台号 | 3 |
| `pax_est` | 必填 | 预计下车 / 上车人数 | 320【待核实】 |
| `vehicle_est` | 必填 | 预计接 / 送车辆数 | 110【待核实】 |

| `verified` | 必填 | 已核实 / 待核实 | 待核实 |

## 六、T4 需求比例表（池·S 填 → `stations/demand.json`，脚本：开发A）

**用途**：每类时段 / 每天的**需求倍率**、三类司机占比、两种停靠方式占比、车型构成、App 渗透率。
**对应因素**：F10 时段 / 日历、F12 车型构成、F14 App 渗透率 / 采纳率（总纲第 6 节）。

| 列名 | 必填 | 说明 | 示例值 |
|---|---|---|---|
| `time_window` | 必填 | 时段 | 17:00–19:00 |
| `day_type` | 必填 | 工作日 / 周末 / 节假日 / 春运 | 工作日 |
| `demand_multiplier` | 必填 | 需求倍率（基准时段 = 1.0） | 1.8【待标定】 |
| `od_pair` | 必填 | OD 对编号（与 T1 / T2 的节点一致） | `OD-01` |
| `share_D1` / `share_D2` / `share_D3` | 必填 | 三类司机占比：D1 送客 / D2 接客 / D3 往返，**每行加总 = 100%** | 45% / 30% / 25% |
| `share_S1` / `share_S2` | 必填 | 两种停靠方式占比：S1 门口即停即走 / S2 路边或停车场，**加总 = 100%** | 60% / 40% |
| `share_private` / `share_taxi` / `share_online` / `share_bus` | 必填 | 车型构成（F12），**加总 = 100%** | 55% / 20% / 22% / 3% |
| `app_penetration` | 必填 | App 渗透率（F14） | 0.3【建议值】 |
| `filler` / `date` | 必填 | 填表人与日期 | 池·S / 2026-10-14 |

**填表纪律**：

1. **每行三组比例都要自己验算一遍加总 = 100%**；加不上就写原因（例如"车型构成里还有 3% 大巴未计入"——那也要写清楚）；
2. 倍率是**相对值不是绝对值**，写清基准是什么（默认基准时段 = 1.0）；
3. S2 停靠会影响"从停车位走到站口的时间"，**比例填错会让总耗时算错**，拿不准就标【待核实】。

## 七、T5 因素表（池·P 填 → `stations/factors.json`，脚本：开发A）

**用途**：把 **14 类因素（F01~F14）**逐类登记清楚：**数据从哪来、改的是什么、作用范围、生效时间窗、谁实现**（D5）。
**关键口径**：每条路段最终输出的 `factors_applied` 就来自这张表——**"这一刻哪些因素在起作用、各改了多少"**。合成规则：各因素对通行能力与畅通速度**分别相乘**，合成后**不低于原值的 40%【待标定】**（总纲第 6 节）。

| 列名 | 必填 | 说明 | 示例值 |
|---|---|---|---|
| `factor_id` | 必填 | F01~F14 | `F01` |
| `name` | 必填 | 因素名（与总纲第 6 节一致） | 大雨 |
| `target` | 必填 | 改什么：`c` 通行能力 / `v_f` 畅通速度 / `demand` 需求 / `lanes` 车道数 / `confidence` 置信度 | `c` |
| `multiplier` | 必填 | 乘数（改容量 / 速度 / 需求用）；封路类写 0 或另加说明 | 0.75 |
| `start` / `until` | 条件必填 | 生效时间窗（ISO 时间或 HH:MM）；常驻因素写"全天 / 全年" | 2026-10-12T17:00+08:00 |
| `scope` | 必填 | 作用范围：全网 / 指定路段（写 `segment_id` 列表）/ 指定点位 | `SEG-003,SEG-004` |
| `source_1` | 必填 | 一期来源：手填 / 孪生模拟 / 场景注入 | 手填 |
| `source_2` | 必填 | 二期来源：气象接口 / 摄像头 / 停车场接口 / 交警通告 / **仍手填** | 气象数据接口 |
| `notes` | 选填 | 备注（如"合成后不低于原值 40%【待标定】"） | —— |
| `filler` / `date` | 必填 | 填表人与日期 | 池·P / 2026-10-16 |

**14 类因素对照（一期来源见总纲第 6 节）**：

| 编号 | 因素 | 编号 | 因素 |
|---|---|---|---|
| F01 | 天气（雨、雾、台风、高温） | F08 | 施工 / 临时管制 |
| F02 | 昼夜 / 能见度 | F09 | 信号配时 |
| F03 | 列车到发（班次、晚点、客流） | F10 | 时段 / 日历（工作日、周末、节假日、春运） |
| F04 | 落客区占用 | F11 | 大型活动（演唱会、展会） |
| F05 | 停车场 / 蓄车区余位 | F12 | 车型构成（私家车 / 出租 / 网约 / 大巴） |
| F06 | 路边违停 / 占道 | F13 | 外围路网路况 |
| F07 | 交通事故 / 故障车 | F14 | App 渗透率 / 采纳率 |

**填表纪律**：

1. **每类因素都要写清 `target` 取哪一个**（容量 / 速度 / 需求 / 车道数 / 置信度）——这是判级与推荐能不能算对的关键；
2. 作用范围写 `segment_id` 的，**必须能在 T2 里找到**；
3. 时间窗写清楚的格式，别写"晚上"这种没法算的；

## 十二、转换脚本约定（**写脚本的开发看这一节**）

| 项 | 约定 |
|---|---|
| **谁写** | T1 / T2 → **开发B**（放 `work/engine/`）；T3 / T4 / T5 / T6 → **开发A**（放 `work/twin/`）；T9 → **开发B**（二期） |
| **怎么读** | 读表格导出的 **CSV / 单 sheet**，**表头固定**（就是本文件列的列名）；**行顺序无关** |
| **必须幂等** | **同一张表跑两次，结果完全一样**；同一份表格重跑不许产生 diff |
| **必须可重跑** | 表格升版本 → 重跑 → 生成新的 `stations/*.json`，**不许手工补 JSON** |
| **来源要留痕** | 生成物里带来源记录（**表格文件名 + 版本 + 转换时间**）；`network.json` 的来源记录写在 `map_source.json`（引擎不读） |
| **不许猜** | 表格里缺失 / 空白的必填列，脚本**报错退出并指出行号**，**不许用默认值悄悄补上**；**T1 的 `role` / `sumo_edge_id` 缺任一列直接报错**；**T6 的 `assimilation.edges` 若写了 `role = internal` 的 edge，同样报错退出** |
| **校验要报数** | 脚本必须打印：读了多少行、生成了多少条、跳过了几行（跳过要写原因） |
| **进 PR 的规矩** | 脚本进 PR；**转换前后的 diff 一并贴进 PR 描述**；契约字段有变化时由**开发B 当天更新 `docs/数据契约.md`** |

**验收方式（每个脚本都要走一遍）**：脚本作者**当池·S / 池·P 的面跑一次** → 条数对得上 → **池·Q 随机抽 10 行对照 JSON 字段** → 对不上就记缺陷。
