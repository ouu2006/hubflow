## 一、一句话口径

> **单在 Gitee，证据在 PR，行在仓库。**

| 在哪 | 是什么 | 谁写 |
|---|---|---|
| **Gitee Issues** | 任务定义（要产出什么 / 完成判定 / 三 prerequisite）+ **交接留痕评论** | 发布者 / **认领者** |
| **Gitee PR** | 改动内容 + 「审查记录」栏（AI 预审 + 全新上下文 4 问） | **提交者** |
| **仓库 `docs/任务记录.md`**（本文件） | **任务记录台账**：每完成一单一行 | **完成这单的人**顺手加一行 |

## 二、什么时候要写（**触发条件**）

| 这次… | 要不要写一行 |
|---|---|
| **一个 Issue 关闭了**（它对应的 PR 已合并） | ✅ **必写**——关单人顺手加一行 |
| **一个 PR 合并了，但不挂在任何 Issue 上**（业主直接点的活 / 小修 / 清理） | ✅ **必写**——合并时加一行，单号栏写 PR 号 |
| **单子只做了一半就停**（阻塞、换单、交接给别人） | ✅ 写一行，`结果` 填 `部分` 或 `阻塞` |
| **单子作废 / 被别的单吞掉** | ✅ 写一行，`结果` 填 `作废`，并写清被谁吞 |
| **同一单后来又补了交付**（补 PR、补证据、补审查） | ✅ **再加一行**（`做了什么` 栏写"追加：…"），**旧行一个字不改** |
| **历史补录**（2026-10-16 一次性补录 2026-10-09 起的全部单，见第 3.2 节） | ✅ 已在表里——**此后不再追溯补录**，只按上面几条往后加 |
| 只是查资料 / 讨论 / 问问题，**没有任何交付** | ⬜ 不用写 |

> ⚠️ **行数由"单"决定，不由改动大小决定**：一次小修也是一单，也要留一行——恰是"小改动不留痕"最容易让后面的人查不出是谁干的。
> **台账只追加**：新行一律加在表格**末尾**，上面已有的行**一个字都不改**（历史留痕；要更正就在末尾另加一行写清）。

## 三、怎么写（**七个字段，逐条说清**）

| 字段 | 填什么 | 反例（不许这样写） |
|---|---|---|
| **日期** | `YYYY-MM-DD`——**本行登记那天**（不是开工那天） | "今天" |
| **单号** | Gitee Issue 号（`IKM5T1`）；没有单就写 PR 号（`!26`）；两者都有就写 `IKM5T1 / !23`；GitHub 时代的旧单写 `#88` | "那个地图单" |
| **区域** | 与 Issue 标签同口径的七个取值之一：**孪生与路况 / 决策与判级**（区域全称是「决策与定位 + 判级」，Gitee 标签里 `+` 被平台拒，故标签名写作「决策与判级」）**/ 接口与双端 / 站点与踏勘 / 参数与调研 / 独立验收 / 文档与合规**；跨区域写 `跨区域` | "前端"、"后端" |
| **做了什么** | **一句话说清交付物**：动了哪个文件 / 出了什么产物 / 关掉了什么缺口 | "改了一些东西" |
| **对着哪条判定** | **照抄**判定原文（手册第 17 章的 `TC-xx` / `M1-x`、[`分工表.md`](分工表.md) §8 的完成判定、或该单 Issue 的「完成判定」栏）——**不许自己改写** | "没问题" |
| **结果** | **只许四种**：`完成` / `部分` / `阻塞` / `作废`——说的是"**这单做完了没**"，**不是**"判定过没过" | "基本完成"、"差不多" |
| **证据** | PR 号（`!23`）、仓库相对路径（`docs/任务记录.md`）、Issue 评论（"IKM5T1 的交接留痕评论"）；**不写本机绝对路径**（手册修订表第 39 条） | "截图在我机器上" |

### 3.1 与「填表报告」的分工（**两张表都要填，别互相吞**）

| | [`填表报告.md`](填表报告.md) 台账 | **本文件** 台账 |
|---|---|---|
| 回答什么 | **这一版 `stations/*.json` 是哪张表第几版转出来的** | **这一单做了什么、做完没、证据在哪** |
| 一行是什么 | 一次提交里的**一个产物** | **一单** |
| 什么时候必填 | 动了 `stations/*.json` 或表格转换脚本 | **每完成一单** |
| `结果` 取值 | `已转` / `已核对` / `占位` / `未重跑` / `待转` | **`完成` / `部分` / `阻塞` / `作废`** |
| 谁查 | 门禁**第 7 组**（格式 + 产物覆盖 + 结果语义） | 门禁**第 8 组**（格式 + 结果枚举 + 日期） |

> **"过没过"的正式判定**归**池·Q 的 T7 独立验收**（手册第 17 章）——本表只如实登记"这单做完了没、对着哪条判定"，**不下结论**。同理，**不许**把"没验过"写成 `完成`：真没做完就写 `部分`。

### 3.2 历史补录行怎么填（**2026-10-16 一次性补录，此后不再追溯**）

**补了什么**：`2026-10-09`（仓库奠基）起到本表建立之前的**全部单**——GitHub 时代 39 条 Issue + 56 条 PR、Gitee 时代 24 条 Issue + 26 条 PR，加一行"计划期（无单）"。**数据源是仓库内已有的两份归档 + git 历史**，不是重新问平台。

| 字段 | 补录行的口径（**与第三节的常规行不同，只对补录行生效**） |
|---|---|
| **日期** | 取**该单交付 PR 的合并日**（git 合并提交）；无 PR 的取**最后一次点名该单的提交日**（**排除 `docs/历史台账/` 的归档提交**，否则全被拉到归档那天）；两者都取不到才用该单所在时代的归档日 |
| **单号** | `#NN`（GitHub 时代）/ `IK…`（Gitee 时代）；**Gitee 侧若由旧单重建，标 `（旧 #NN 重建）`**；没有对应单的 PR 标 `（PR，无单）`，并附它自己点名过的关联单号 |
| **区域** | 照抄该单正文的「区域 / 任务类型」栏或平台标签 |
| **做了什么** | 照抄该单标题（去掉开头的 `[区域]` 前缀与结尾的 `（L?）` 难度标记，其余一字不改） |
| **对着哪条判定** | 照抄该单「完成判定」栏的**条目名**（最多列 5 条；**完整原文**在该单归档节里逐字可查）；原文确实没有这一栏的，如实写「该单原文无「完成判定」栏」 |
| **结果** | **按单状态搬运**：`closed` / `CLOSED` / `MERGED` → `完成`；`open` / `OPEN` → `部分`；`rejected` / 未合并即关闭 → `作废` |
| **证据** | 关联 PR 号 + 归档文件链接，**行尾统一标 `（补录）`**（与常规行一眼可分） |

> ⚠️ **补录行没有逐条重跑验证**：它做的是"**状态与原文的搬运**"，不是"重新验收"。所以它**不能**当"判定过没过"的证据——要正式结论仍看**池·Q 的 T7** 与该单的**交接留痕**（[`协作规范.md`](协作规范.md) §5.4）。**表里的 `完成` 只表示"该单当时已关闭/已合并"。**

## 四、机器怎么判（门禁第 8 组）

**门禁只有一条命令，本地跑**：`python scripts/doc_gate.py`（见 [`协作规范.md`](协作规范.md) 第 4 节）。第 8 组只查机器判得动的四件事：

| # | 查什么 | 怎么判 | 判不过会怎样 |
|---|---|---|---|
| ① | **台账章节在不在** | 认 `## …任务记录台账` 这一节；**本文件不存在也判失败**（少了它就没法登记"做了什么"） | **判失败** |
| ② | **行格式** | 每行七个字段齐全；`结果` 只能是 `完成` / `部分` / `阻塞` / `作废` 之一；日期是 `YYYY-MM-DD` | **判失败**，指出行号 |
| ③ | **不许空表** | 台账至少要有一行（基线行也算）——空表说明还没人登记过 | **判失败** |
| ④ | **HTML 注释闭合** | `<!--` 与 `-->` 个数相等 | **判失败**——**未闭合会把整张表从渲染里藏掉**（按行查的检查全绿、人却看不到表；2026-10-16 补录时真踩过一次） |

**这组检查拦不住的（写清楚，别误以为它全包了）**：**"这一单到底有没有人留行"机器判不了**——git 只看得见文件变了，看不见"这单完成了"。所以这条纪律靠两道人工关：**① 关单人 / 合并人自己加行**（[`协作规范.md`](协作规范.md) §5.4）；**② 兜底审在 PR 里看一眼**。**没有"门禁绿了就说明填过了"这回事。**
