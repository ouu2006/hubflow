# 开发规范

> **这份文档只讲一件事**：四个人各自让 AI 生成代码，怎么保证拼起来能跑。
>
> `协作规范.md` 管"怎么不打架"（目录、分支、PR）；**本文件管"代码长什么样"**。两者都是硬约束，不是建议。

## 1. 为什么必须有这份文档

团队的真实开发方式是"让 AI 生成代码并跑起来"（见技术手册 15.1）。AI 每次生成的命名、结构、风格都不一样，而我们的模块之间是**按字段名对接**的——字段名一改，下游直接读不到。

**所以：约定字段名比约定代码风格重要得多。** 本文件第 2 节最硬，其余依次递减。

## 2. 字段命名（**最硬的一条，违反即返工**）

**所有 JSON 字段一律 `snake_case`，单位写进字段名后缀。** 三个数据文件的字段以 [`数据契约.md`](数据契约.md) 为唯一准绳，**不得自行增删改名**。

| 规则 | 正例 | 反例 |
|---|---|---|
| 小写下划线 | `segment_id` | `segmentId` / `SegmentID` |
| 单位进后缀 | `v_kmh`、`L_q_m`、`eta_min`、`window_sec` | `speed`、`queue_length`、`eta` |
| 布尔加 `is_` 前缀 | `is_simulated`、`no_alternative` | `simulated`、`hasAlt` |
| 时间戳统一 `ts`，ISO-8601 带时区 | `"2026-10-08T17:32:00+08:00"` | 时间戳毫秒数、`time` |
| 数组用复数 | `segments`、`alternatives` | `segmentList`、`alt` |

**每个数值必须带 `is_simulated`**（一期恒为 `true`）。这不是可选字段，是技术手册第 12 章写死的约定。

> **要加字段怎么办**：先在 Issue 里说，由**决策线**（`/api/traffic/*` 契约唯一 owner）裁定并当天更新 `数据契约.md`，**其他人不得先改代码再补文档**。

## 3. 目录与依赖边界

| 规则 | 说明 |
|---|---|
| 只改自己目录 | 见 `协作规范.md` 第 1 节 |
| **禁止跨目录 import** | `work/engine/` 里**不得** `from work.perception import ...`。模块之间**只通过 JSON 文件传递** |
| 每个模块有独立入口 | `work/<位置>/run.py`，单独跑就能产出自己的 JSON（技术手册 15.5） |
| 公共文件只由后端改 | 根目录 `README.md`、`.gitignore`、`docs/数据契约.md`、路由注册表 |
| 站点包路径 | `stations/`（根目录，六个 JSON）。**引擎代码里不得出现站点名、坐标、路名硬编码** |

**为什么禁止跨目录 import**：目录边界就是人的边界。一旦 A 的代码 import 了 B 的模块，B 改个函数签名 A 就跑不起来，而 A 可能不知道。**文件当接口，谁都不依赖谁的代码。**

## 4. 命名与结构（Python）

| 对象 | 规则 | 例 |
|---|---|---|
| 文件 / 目录 | `snake_case` | `level.py`、`map_ingest.py` |
| 函数 / 变量 | `snake_case` | `classify_congestion`、`data_age_s` |
| 类 | `PascalCase` | `SegmentMetrics`、`LevelConfig` |
| 常量 | `UPPER_SNAKE_CASE` | `DEFAULT_WINDOW_SEC`、`CKPT_MAP` |

**函数签名照抄技术手册。** 技术手册 6.4 已给出 `classify_congestion(segment, weather, config) -> CongestionLevel` 等签名，**不得自行改名**——改名等于契约变更。

**每个模块顶部写 docstring**，三行说清：输入是什么文件、输出是什么文件、关键口径。

## 5. 编码与换行（**Windows 上最容易踩**）

| 项 | 规定 | 为什么 |
|---|---|---|
| 文件编码 | **UTF-8，不带 BOM** | 带 BOM 会让 `json.load` 在某些工具里首字符报错 |
| 换行符 | **LF**，由 `.gitattributes` 强制 | 四人都是 Windows，不统一就会出现"整个文件都是改动"的假 diff |
| 读写 JSON | 显式 `encoding="utf-8"` | 不写会跟随系统默认编码，换机器就乱码 |
| 输出中文 | 允许；`json.dump(..., ensure_ascii=False)` | 保证 `level_name: "拥堵"` 可读 |

## 6. 依赖与环境

| 规则 | 说明 |
|---|---|
| **不引入需要联网的库** | 一期是**单机演示**，现场不保证有网（技术手册 3.2） |
| 不新增第三方依赖不打招呼 | 要加就在 Issue 里说，由后端统一记进依赖清单 |
| 依赖版本以**上游仓库锁定值为准** | `agentic-traffic-management/traffic-core-mindspore/requirements-mindspore.txt` 逐字节锁定版本，**不得升级**（numpy 必须 < 2.0，MindSpore 2.8.0 的硬约束） |
| 大文件不进仓库 | 视频、权重、数据集、模型产物一律放共享盘 |

## 7. 注释

**只写代码本身表达不出的约束**，不写"这一行在做什么"。

| 该写 | 不该写 |
|---|---|
| 为什么降档要连续 2 个周期（防抖动） | `# 遍历 segments` |
| 这个阈值来自哪次标定、标了什么 | `# 把 x 加到 total` |
| 超出有效标定带的目标不计入速度统计（否则远距离测速不可用） | `# 判断是否超出` |

**不要写"本次修改了什么"**——那是提交信息的事，代码注释里写它，下一个人读到就是噪音。

## 8. 提交信息格式

**格式：`<位置>：<做了什么>`**，位置取值：`感知` / `决策` / `前端` / `后端` / `站点` / `文档` / `修复`。

```text
感知：接入透视标定，输出米制轨迹
决策：新增配额租约分配，routes.json 补 quota 字段
前端：管理端态势总览页接入 segments.json
后端：run_all.py 串通三段链路，支持 --stress
站点：补肇庆东站路网与点位标签 v0
文档：数据契约补 k_vpk / ci 字段
修复：判级降档抖动——改为连续 2 周期确认
```

**一次提交只做一件事。** 不要把"改了字段 + 顺手格式化了整个文件"混在一起，Review 的人看不出你改了什么。

**契约变更必须单独一次提交**，并在提交信息里写明影响谁，例如：

```text
决策：routes.json 新增 walk_min 字段（仅 S2 停靠有值）——影响前端，需同步渲染
```

## 9. 提交前自检（**四条，30 秒**）

```text
① 我能单独跑通我这个模块吗？      python work/<位置>/run.py
② 我的输出 JSON 字段名对得上契约吗？  对照 docs/数据契约.md 逐字段看一眼
③ 我有没有改到别人的目录？        git status 看一遍文件名
④ 我有没有把 Key、视频、权重加进去？  git status 里不该有 .env / *.mp4 / *.ckpt
```

四条全过再 `git push`。**第 ② 条最容易漏**——AI 生成的字段名经常自作主张，比如把 `eta_min` 写成 `eta`。

## 10. 测试

一期**不要求写单元测试**（团队不具备这个能力，硬要求只会变成走过场）。**但要求两件事**：

| 要求 | 口径 |
|---|---|
| **可复现** | 同一输入连续跑三次，输出**完全一致**。不一致就是有随机性没固定，必须修 |
| **留证** | 自测报告写明：跑的是什么输入、输出了什么、结论是什么 |

**验收不靠单测，靠技术手册第 17 章的 14 条用例 + 7 条 DoD**，由"验收与测试"位置独立执行。

## 11. 密钥与授权（**public 仓库，红线**）

> ⚠️ **`hubflow` 是公开仓库。** 任何提交上去的东西都是公开的、可被搜索引擎抓取的、**删掉也可能已被缓存**。

### 11.1 什么绝对不能进仓库

| 绝对不能进 | 说明 |
|---|---|
| 高德 / 百度地图的 **Key**（Web 服务 Key、JS API Key） | 泄露会被盗用配额，且可能违反服务条款 |
| 任何 `.env` 文件 | 已由 `.gitignore` 拦住 |
| `*_key.txt`、`*_token*` | 已由 `.gitignore` 拦住 |
| 服务器密码、数据库口令 | 一期不涉及，二期也不许进代码仓 |

### 11.2 Key 放哪里

```text
本地开发：  复制 .env.example 为 .env，把 Key 填进 .env
             .env 已被 .gitignore 拦住，不会进仓库
演示现场：  同样读 .env；现场机器单独填一份，不走仓库
```

**`.env.example` 是模板，只写变量名和占位符，永远不填真 Key。** 它在仓库里，是给所有人看"要配哪几个变量"的。

### 11.3 代码里怎么读 Key

```python
import os

# 只从环境变量读，不写默认值——缺 Key 时应当明确失败，而不是静默用错值
AMAP_KEY = os.environ["AMAP_WEB_KEY"]
```

**三条硬规则**：

1. **不得在代码里写 Key 的字符串字面量**（哪怕是"临时的"、"待会删的"）；
2. **不得把 Key 拼进 URL 后打印或写进日志**——地图 API 的 Key 就在 URL 参数里，日志一提交就泄露；
3. **拉取结果必须落盘**（`stations/network.json`），不得每次运行都调 API——既省配额，也保证演示可复现（技术手册 8.3）。

### 11.4 万一误提交了 Key

**立刻找队长，不要自己折腾 `git filter-branch`。** 正确处理顺序：

1. 到高德 / 百度控制台**把那个 Key 作废并重新申请**（**这一步最重要**——只要 Key 作废了，泄露就没有实际损失，仓库历史里留着也无所谓）；
2. 告诉队长，由队长决定是否清理历史；
3. 把 Key 移到 `.env`，重新提交。

> **顺序不能反。** 先清历史再作废 Key 是本末倒置：清理历史很麻烦且未必彻底，而**作废 Key 只要点一下**。

### 11.5 授权状态登记

Key 申请到哪一步了，**登记在 [`work/engine/README.md`](../work/engine/README.md)**（决策线维护），写清：申请了哪家、什么类型、批没批、额度多少、什么时候到期。

## 12. 与本文件冲突时怎么办

本文件与技术手册冲突 → **以技术手册为准**，并提 Issue 说明本文件哪一条需要改。

技术手册没写到的细节 → **按本文件的默认口径实现，再提出来讨论，不要停下来等**（技术手册开篇的纪律）。
