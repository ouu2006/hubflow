# 开发规范 · V2.0

> **这份文档只讲一件事**：**3 名开发各自让 AI 生成代码，怎么保证拼起来能跑。**
>
> [`协作规范.md`](协作规范.md) 管"怎么不打架"（目录、分支、PR、共享盘）；**本文件管"代码长什么样"**；[`表格模板说明.md`](表格模板说明.md) 管"协作成员填的表格怎么变成 `stations/` 配置"。三者都是硬约束，不是建议。

## 1. 为什么必须有这份文档

团队的真实开发方式是"**让 AI 生成代码并跑起来**"（总纲 D9）：**3 个人主写代码**（核心引擎与双端）；另外 4 名**协作成员**以表格、数据、测试、文档为主，**同时参与部分技术开发**（补画路网、拾取控制点、写检查与转换脚本、配置因素与场景、生成演示物料）。业务数据仍只从表格进，表格由开发写的转换脚本变成 `stations/` 下的配置文件。

AI 每次生成的命名、结构、风格都不一样，而我们的模块之间是**按字段名对接**的——字段名一改，下游直接读不到。

**所以：约定字段名比约定代码风格重要得多。** 本文件第 2 节最硬，第 6、7 节是 V2.0 新增的两条硬约定，其余依次递减。

## 2. 字段命名（**最硬的一条，违反即返工**）

**所有 JSON 字段一律 `snake_case`，单位写进字段名后缀。** 三个数据文件的字段以 [`数据契约.md`](数据契约.md) 为唯一准绳，**不得自行增删改名**。

| 规则 | 正例 | 反例 |
|---|---|---|
| 小写下划线 | `segment_id` | `segmentId` / `SegmentID` |
| 单位进后缀 | `v_kmh`、`L_q_m`、`eta_min`、`window_sec` | `speed`、`queue_length`、`eta` |
| 布尔量加 `is_` 前缀 | `is_simulated` | `simulated`、`simFlag` |
| **契约已冻结的例外名** | `no_alternative`、`capacity_shortage` | —— 这两个是写死的名字，**照抄，不要改名** |
| 时间戳统一 `ts`，ISO-8601 带时区 | `"2026-10-12T17:32:00+08:00"` | 时间戳毫秒数、`time` |
| 数组用复数 | `segments`、`alternatives`、`factors_applied` | `segmentList`、`alt` |

> **为什么 `no_alternative` 不加 `is_`**：它是**状态标记**（"没有备选"这个事实），不是"某个东西是不是某某"。
> 新起的布尔字段**一律加 `is_`**；上表两个例外是已冻结的名字，改它们会直接破坏契约。

**每个数值必须带 `is_simulated`**（一期恒为 `true`）。这不是可选字段，是写死的约定。

### 2.1 契约 v2.0 新增字段（**照抄，别自己起名**）

| 文件 | 新增字段 | 说明 |
|---|---|---|
| `segments.json` | `source` | `"twin"` / `"video"`；**一期恒为 `"twin"`** |
| | `c_base_vph` | 因素修正**前**的通行能力（辆/小时） |
| | `factors_applied` | 数组：`factor_id` / `name` / `target`（`c` / `v_f` / `demand` / `lanes` / `confidence`）/ `multiplier` / `until`（ISO 时间） |
| | `pred` | 可选：`{"h15": {"q_vph": …, "level": …}, "h30": {…}, "model": "L0"}`；**一期只 L0**，标 `is_simulated` |
| `routes.json` | `session_id` | 一次行程的**匿名会话号**（不含身份；行程结束即删） |
| | `location` | `segment_id` / `offset_m` / `match_confidence` / `source`（`twin` 或 `app_gnss`） |
| | `reservation` | `slots_reserved` / `lease_expire_s` / `harm_check`（`max_eta_increase_s` / `max_slot_x` / `passed`） |
| | `reroute` | `count` / `reason` |
| | `factors_note` | 引用的因素说明（可空） |
| | `quota` | **保留**，含义改为"**各候选路径剩余可预约量**" |
| `vehicles.json` | 新文件（**仅一期演示用**，孪生内部数据） | `vehicle_id` / `driver_type` / `segment_id` / `offset_m` / `lon` / `lat` / `state` / `guided` / `is_demo_bound`；**二期不存在此文件** |

**必填字段也变了**：`segments.json` 必填增加 `source`；`routes.json` 必填增加 `session_id`、`reservation`。

> **要加字段怎么办**：先在 Issue 里说，由**开发B**（`segments` / `routes` / `vehicles` 字段的**唯一裁定人**）裁定并**当天**更新 [`数据契约.md`](数据契约.md)，**其他人不得先改代码再补文档**。

| 目录 / 文件 | 归属 | 里面放什么 |
|---|---|---|
| `work/twin/` | **开发A** | SUMO 路网转换、场景、司机行为体、虚拟检测器、因素注入、主循环 `loop.py`、`run_all.py` 入口 |
| `work/perception/` | **开发A** | 一期：虚拟检测器数据 → 四项指标 → 判级 `level.py` → `segments` 快照；二期：真实视频感知、标定、视觉微调 |

| `work/frontend/` | **开发C** | Vue 管理端 + 鸿蒙 App |
| `work/assembly/` | **开发C** | 接口层 `traffic.py`、压力测试脚本、演示一键脚本 `.bat`、日志 |
| `stations/` | **开发B 定结构 + 脚本产物；N1 / N2 填数据** | 见 3.2 |
| **公共文件** | **开发C 改、队长复核** | 根 `README.md`、`.gitignore`、`.github/`、`docs/数据契约.md`、路由注册 |
| `docs/` 计划类文档 | **队长维护**（可请开发C 代提交） | 全流程计划、分工表、协作规范、手册、表格模板说明 |

| 规则 | 说明 |
|---|---|
| 只改自己目录 | 见 [`协作规范.md`](协作规范.md) 第 1 节 |
| **禁止跨目录 import** | `work/engine/` 里**不得** `from work.twin import …`。模块之间**只通过 JSON 文件传递** |
| 每个模块有独立入口 | `work/<目录>/run.py`，**加 `--sample` 就能用样例文件单独跑**（见第 6 节） |
| 公共文件只由开发C 改 | 根 `README.md`、`.gitignore`、`.github/`、`docs/数据契约.md`、路由注册 |
| 站点包路径 | `stations/`（根目录）。**引擎代码里不得出现站点名、坐标、路名硬编码** |

**为什么禁止跨目录 import**：目录边界就是人的边界。一旦 A 的代码 import 了 B 的模块，B 改个函数签名 A 就跑不起来，而 A 可能不知道。**文件当接口，谁都不依赖谁的代码。**

## 4. 命名与结构（Python）

| 对象 | 规则 | 例 |
|---|---|---|
| 文件 / 目录 | `snake_case` | `level.py`、`locate.py`、`network_ingest.py` |
| 函数 / 变量 | `snake_case` | `classify_congestion`、`data_age_s` |
| 类 | `PascalCase` | `SegmentMetrics`、`LevelConfig` |
| 常量 | `UPPER_SNAKE_CASE` | `DEFAULT_WINDOW_SEC`、`X_SAFE`、`EPS_HARM` |

**每个模块顶部写 docstring**，三行说清：**输入是什么文件、输出是什么文件、关键口径。**

> 一期 demo 假设值（如 `X_SAFE` = 0.85【待标定】、`EPS_HARM` = 30 s【待标定】）**常量名要能看出是什么，值要带注释写清"待标定"**，别把假设值写成硬编码的魔法数字。

## 5. 编码与换行（**Windows 上最容易踩**）

| 项 | 规定 | 为什么 |
|---|---|---|
| 文件编码 | **UTF-8，不带 BOM** | 带 BOM 会让 `json.load` 在某些工具里首字符报错 |
| 换行符 | **LF**，由 `.gitattributes` 强制 | 大家都在 Windows 上，不统一就会出现"整个文件都是改动"的假 diff |
| 读写 JSON | 显式 `encoding="utf-8"` | 不写会跟随系统默认编码，换机器就乱码 |
| 输出中文 | 允许；`json.dump(..., ensure_ascii=False)` | 保证 `level_name: "拥堵"` 可读 |
| 用 PowerShell 写文件 | **不要用 `Set-Content -Encoding utf8`** | Windows PowerShell 5.1 会写 BOM；用 Python 写（`open(p,'w',encoding='utf-8',newline='\n')`） |

## 6. 样例数据（**V2.0 新增硬约定**）

**为什么要有**：模块之间靠文件契约对接，但上游没做完时下游不能停工等（总纲 D8、第 3 节）。**所以每个模块都必须能在没有上游的情况下，用 `samples/` 里的样例文件单独跑起来。**

| 项 | 约定 |
|---|---|
| **放哪** | `work/<目录>/samples/`（如 `work/engine/samples/`） |
| **叫什么** | `<文件名>_sample.json`（如 `segments_sample.json`、`routes_sample.json`、`vehicles_sample.json`） |
| **进不进仓库** | **进**（都是小文本），并且**必须带 `is_simulated: true`** |
| **字段要求** | 与 [`数据契约.md`](数据契约.md) **逐字段一致**——样例就是契约的镜子，样例错下游全错 |
| **怎么跑** | `python work/<目录>/run.py --sample`；输出写到 `out/` 或 `samples/out/`，**不许覆盖样例输入** |
| **契约改了怎么办** | **改字段的那一方当天同步更新所有受影响的样例文件**，并在 PR 描述里写清 |
| **数值长什么样** | 用**一眼能看出是样例**的整数（如 `q_vph: 1000`），**不许做成"看起来像真实数据"的样子** |
| **三条纪律** | ① 上游没做完**不许停工等**，先用自己的样例顶；② 样例不许当验收证据（验收一律用真实跑出来的数据）；③ 样例里**不许出现真实个人信息** |

## 7. 表格转换脚本（**V2.0 新增硬约定**）

**`stations/` 下的配置文件由表格生成，不手改。**（表格列定义与"谁写脚本"见 [`表格模板说明.md`](表格模板说明.md)）

| 项 | 约定 |
|---|---|
| **谁写** | T1 / T2 → **开发B**（放 `work/engine/`）；T3 / T4 / T5 / T6 → **开发A**（放 `work/twin/`）；T9（二期）→ **开发B** |
| **读什么** | 表格导出的 CSV / 单 sheet，**表头固定**（就是模板里的列名），**行顺序无关** |
| **必须幂等** | **同一张表跑两次结果完全一样**；重跑不产生无意义 diff |
| **必须可重跑** | 表格升版本 → 重跑 → 生成新的 `stations/*.json`；**不许手工补 JSON** |
| **不许猜** | 必填列缺失 / 空白 → **报错退出并指出行号**，**不许用默认值悄悄补上** |
| **要报数** | 打印：读了多少行、生成多少条、跳过几行（跳过要写原因） |
| **来源留痕** | 生成物里带来源记录（**表格文件名 + 版本 + 转换时间**）；`network.json` 的来源写在 `map_source.json` |
| **进 PR 的规矩** | 脚本进 PR，**转换前后的 diff 一并贴进 PR 描述**；契约字段有变化由**开发B 当天更新 `docs/数据契约.md`** |
| **验收方式** | 作者**当 N1 / N2 的面跑一次** → 条数对得上 → **N3 随机抽 10 行对照 JSON 字段** |

> **为什么强调"不手改 JSON"**：手改过一次以后，**没人知道那个数是谁改的、下次重跑会不会被覆盖**。要改就改表格、升版本号、重跑脚本。

## 9. 注释

**只写代码本身表达不出的约束**，不写"这一行在做什么"。

| 该写 | 不该写 |
|---|---|
| 为什么降档要连续 2 个周期（防抖动） | `# 遍历 segments` |
| 这个阈值来自哪次标定、标了什么、**是不是【待标定】** | `# 把 x 加到 total` |
| 为什么 `factors_applied` 要按 `target` 分别相乘、合成后不低于原值的 40%【待标定】 | `# 计算因素` |
| 为什么 `vehicles.json` 只在一期存在（二期摄像头不认车） | `# 写文件` |

**不要写"本次修改了什么"**——那是提交信息的事，代码注释里写它，下一个人读到就是噪音。

| **前端** | 开发C · `work/frontend/` | `前端：管理端态势总览页接入 segments.json` |
| **接口** | 开发C · `work/assembly/` | `接口：新增 locate / vehicles / factors / predict 四个端点` |

## 11. 提交前自检（**四条 + 门禁，1 分钟**）

```text
① 我能单独跑通我这个模块吗？        python work/<目录>/run.py --sample
② 我的输出 JSON 字段名对得上契约吗？  对照 docs/数据契约.md 逐字段看一眼
③ 我有没有改到别人的目录？          git status 看一遍文件名
④ 我有没有把 Key、视频、权重加进去？  git status 里不该有 .env / *.mp4 / *.ckpt
⑤ 门禁过了吗？                     python scripts/doc_gate.py     ← 与 CI 同一条命令
```

四条自检 + 门禁全过再 `git push`。**第 ② 条最容易漏**——AI 生成的字段名经常自作主张，比如把 `eta_min` 写成 `eta`、把 `c_base_vph` 写成 `capacity`。

**push 之后开 PR 时，有两件事（2026-10-10 增补）**：

1. **AI 预审（自查）**：把 `git diff` 贴给 AI，按上面四条自检 + "有没有动契约字段 / 别人的目录"过一遍，**把预审意见贴进 PR 的「审查记录」栏**；
2. **快速独立审查（目标 ≤ 5 分钟）**：起一个**全新上下文**的审查者（新会话 / 新子代理 / 另一个工具），**只给它"改动范围 + 4 个问题"**（4 问见 [`协作规范.md`](协作规范.md) 第 4 节），**不给**实现思路、可疑点、既有结论、预期结果；它只读 `git diff`，结论 **≤ 10 行**，**填进「审查记录」栏**。然后等 **CI 全绿**。

> **为什么两件都要**：AI 预审是**自查**——同一个上下文里 AI 已经知道你的意图，它的"审查"只会确认你的取舍；独立审查的价值全在"**审查者不知道你是怎么想的**"。但它**必须限时**：**5 分钟做不完说明这个 PR 太大，拆 PR**，不要开更长的审查。

## 12. 测试

一期**不要求写单元测试**（团队不具备这个能力，硬要求只会变成走过场）。**但要求两件事**：

| 要求 | 口径 |
|---|---|
| **可复现** | 同一输入连续跑三次，输出**完全一致**。不一致就是有随机性没固定，必须修（**M1-1、M1-3 的判定就靠这条**） |
| **留证** | 自测报告写明：跑的是什么输入（文件名 + 版本）、输出了什么、结论是什么 |

**验收不靠单测，靠 TC-01 ~ TC-20 与 M1-1 ~ M1-10（手册第 17.1~17.3 节）**，由 **N3（测试验收员）独立执行**，**N3 不得由开发兼任**。

**CI 与本地同口径（2026-10-10 增补）**：仓库里唯一的自动门禁是 `python scripts/doc_gate.py`（工作流 [`.github/workflows/ci.yml`](../.github/workflows/ci.yml)，检查名 `ci`；CI 里写 `python3`，同一脚本）。它**不判业务逻辑**，只管文档与契约的机械口径：编码与换行、相对链接、JSON 可解析、大文件与密钥、字段命名。本地跑同一条命令，**红 check 必须自己修到绿**。以后加了代码，在同一个 workflow 里**按目录追加 job**（如 `python work/<目录>/run.py --sample`），**不要改 `ci` 这个 job 名**。**2026-10-10 调整后，`ci` 已经是 `main` 的必需检查**——红 check 不再是"建议修"，而是**合不了**（见 [`仓库设置清单.md`](仓库设置清单.md)）。

## 13. 密钥与授权（**public 仓库，红线**）

> ⚠️ **`hubflow` 是公开仓库。** 任何提交上去的东西都是公开的、可被搜索引擎抓取的、**删掉也可能已被缓存**。

### 13.1 什么绝对不能进仓库

| 绝对不能进 | 说明 |
|---|---|
| 高德 / 百度地图的 **Key**（Web 服务 Key、JS API Key） | 泄露会被盗用配额，且可能违反服务条款 |
| 任何 `.env` 文件 | 已由 `.gitignore` 拦住 |
| `*_key.txt`、`*_token*` | 已由 `.gitignore` 拦住 |
| 服务器密码、数据库口令 | 一期不涉及，二期也不许进代码仓 |
| **视频 / 权重 / 数据集** | 一律放共享盘，把路径写进对应目录的 README |

### 13.2 Key 放哪里

```text
本地开发：  复制 .env.example 为 .env，把 Key 填进 .env
             .env 已被 .gitignore 拦住，不会进仓库
演示现场：  同样读 .env；现场机器单独填一份，不走仓库
```

**`.env.example` 是模板，只写变量名和占位符，永远不填真 Key。**

### 13.3 代码里怎么读 Key

```python
import os

# 只从环境变量读，不写默认值——缺 Key 时应当明确失败，而不是静默用错值
AMAP_KEY = os.environ["AMAP_WEB_KEY"]
```

**三条硬规则**：

1. **不得在代码里写 Key 的字符串字面量**（哪怕是"临时的"、"待会删的"）；
2. **不得把 Key 拼进 URL 后打印或写进日志**——地图 API 的 Key 就在 URL 参数里，日志一提交就泄露；
3. **拉取结果必须落盘**（`stations/network.json`），不得每次运行都调 API——既省配额，也保证演示可复现。

### 13.4 万一误提交了 Key

**立刻找队长，不要自己折腾 `git filter-branch`。** 正确处理顺序：

1. 到高德 / 百度控制台**把那个 Key 作废并重新申请**（**这一步最重要**——只要 Key 作废了，泄露就没有实际损失，仓库历史里留着也无所谓）；
2. 告诉队长，由队长决定是否清理历史；
3. 把 Key 移到 `.env`，重新提交。

> **顺序不能反。** 先清历史再作废 Key 是本末倒置：清理历史很麻烦且未必彻底，而**作废 Key 只要点一下**。

### 13.5 授权状态登记

Key 申请到哪一步了，**登记在 [`work/engine/README.md`](../work/engine/README.md)**（**开发B** 维护，因为 `stations/` 结构与数据源由他 owner），写清：申请了哪家、什么类型、批没批、额度多少、什么时候到期。
