# 方案：路段箭头方向重做 + 起点错位修正（2026-10-29）

> 业主诉求（Issue 口径）：前端箭头**直接画在路段中间、随路段缩放**；现在箭头乱、**分辨率不同会错位**；后端箭头标向难以分辨；**已知 bug：前端把起点标在了 `SZ-004` 段末尾**。要求全部检查一遍，并给一个**确认箭头标向的方案**。

## 1. 根因（已实测确认）

### 1.1 起点错位 —— 引擎把 coords 序里程当行进序读

**方向语义的权威定义**在 `work/twin/netpack/topology.py:240-241`：

> `"reverse"` → `OSM oneway={value!r} → 反向单行（几何 from/to 与行车方向相反）`

真网 61 个路段里有 **14 条 `direction = "reverse"`**。重建遍历边的地方是 `work/engine/realnet_topology.py:174-216` 的 `traversal_specs()`：

| `direction` | 遍历边 | `from` / `to` 与 `coords` 的关系 |
|---|---|---|
| `forward` | `edge_id = segment_id` | 同序 |
| `bidirectional` | `segment_id` + **`segment_id_rev`** | `_rev` 那条**反序** |
| `reverse` | `edge_id = segment_id` | `from = edge["to"]`、`to = edge["from"]`，**反序** |

**`coords` 一律原样透传**。但 `offset_m` 的口径必须单独钉死 —— 实测结论：**twin 真值 `offset_m` 是 `coords` 顺序弧长，从 `coords[0]` 量起**，不是行进序。

**证据 A（决定性）**：`work/twin/sumonet.py:342-344`

```
342:  from_node, to_node = str(edge["from"]), str(edge["to"])
344:  shape = _edge_shape_xy(edge, proj, reverse=False)
```

`_edge_shape_xy`（`work/twin/sumonet.py:280-288`）就是把 `edge["coords"]` 顺序投影，`reverse=True` 才倒序。所以 **SUMO 车道 shape 首点 = `coords[0]`**，而 `traci.vehicle.getLanePosition()` 量的正是从车道 shape 首点起的里程。且 `edge_meta.direction` 恒为 `"forward"`（`work/twin/sumonet.py:362`），反向段**不另建 `_rev` 边**（`work/twin/sumonet.py:374-376`：`if oneway in ONEWAY_VALUES: continue`）。现场复算（`work/engine/tools/audit_segment_direction.py --prove-offset`）：真网 **61/61 段** shape 首点 ↔ `from` 节点坐标最大偏差 **0.000000 m**；`SZ-004` 的 `shape_first_to_from_node_m = 0.0`、`shape_first_to_to_node_m = 120.847`（shape 首点在 `N-022`，不在 `N-040`）。

**证据 B**：`work/twin/loop.py:1066-1071`

```
1066:  elif row["direction"] == "forward":
1067:      offset_m = float(traci.vehicle.getLanePosition(vehicle_id))
1068:  else:  # 反向补边：换算回原段起点起算的里程
1069:      offset_m = max(0.0, float(row["length_m"]) - float(traci.vehicle.getLanePosition(vehicle_id)))
```

两条分支都折向 `coords[0]` 口径；注释原文就写着「换算回**原段起点**起算的里程」。

**证据 C（辅证）**：点位注册表抽样 `GZ-ZONE-03 @ GZ-076`（reverse）：`offset_m = 288.2` ↔ `coords_order_m = 288.2` ↔ `travel_order_m = 15.2`。注册表本身投票样本太少（zhaoqingdong 0 条、guangzhounan 2 条），只作旁证。

#### 于是真正的 bug 在引擎侧

- `SZ-004` 实测：`from = N-022`、`to = N-040`、`direction = "reverse"`、`length_m = 120.7`、`coords[0] = N-022`、`coords[-1] = N-040`；
- 遍历边按行进方向建成 `from = N-040`（= `coords` 末点）、`to = N-022`；
- 旧 `route_service._start_from` 把 **coords 序的 `offset_m`** 直接当**行进序**读（`offset_m ≤ 0.5 → 起点 = edge["from"]`）。
  ⇒ 真值 `offset_m = 0` 时车实际在 `N-022`，引擎却认为它在 `N-040`，**整个行程从段的反端出发、并把整段当成未走过的前缀**。
- 前端 `DashboardView.vue` 的 `pointAtOffset(seg.coords, offset_m)` 按 `coords` 序插值 —— **一直是对的**。它把起点画在 `N-022`（正确），但画出来的那条路线是**从 `N-040` 起头的**，于是正确的点落在「线尾巴」上 = 业主看到的"起点标在 `SZ-004` 段末尾"。

**修法**（已落地）：`work/engine/route_service.py:133-142` 新增 `coords_offset_to_travel()` / `travel_offset_to_coords()`；`_start_from`（`route_service.py:561-582`）与 `_end_at`（`route_service.py:585-598`）只读 `offset_travel_m`，缺失时回退折一次；`offset_travel_m` 由 `resolve_endpoint`（`route_service.py:418` 起）算出。对外（`/route/snap`、`/route/plan` 回显、`start_point`）统一 coords 序，并并列 `offset_travel_m`。

**同类 bug 还有一处**：`snap_to_segment()` 按 `coords` 顺序算出的 `offset_m`，被 `_start_from()` 按行进顺序解读 → 自定义起终点落在这 14 条反向段（或任一 `_rev` 遍历边）上时，起点镜像、路径长度错误（同一修法已覆盖）。

#### 1.1.1 裁切量口径倒置（第二处，已修）

`_start_from()`（`work/engine/route_service.py:596-617`）返回的 `"m"` 是 `remaining = length_m - offset_travel_m`，而 `route_plan()`（`work/engine/route_service.py:878`）直接把它当 `trim_head_m` —— **裁剪量应该是「车后方未走过的行进里程」= `offset_travel`，不是「剩余里程」**；`_end_at()`（`:620-633`）同样倒置（返回 `offset`，而 `trim_tail` 应为 `length - offset`）。两端互为倒数，所以**正向段也一起错**，不只是反向段。判据：`trim_head_m` 必须等于 `dist(start_point, steps[0].geometry[0])`。

修前实测（`POST /route/plan`）：

| 段 | 方向 | 段长 | `offset_m` | `trim_head_m`（修前） | `dist(start_point, geo0)` | 结论 |
|---|---|---|---|---|---|---|
| SZ-004 | reverse | 120.7 | 10 | 10.0 | **110.7** | 首段裁错 100 m，画面表现为"路线从车后方 100 m 处起头" |
| SZ-004 | reverse | 120.7 | 40 | 40.0 | 80.7 | 错 40 m |
| SZ-023 | forward | 63.4 | 20 | **43.4** | 20.0 | 错 23.4 m（正向也错） |
| SZ-023（作终点） | forward | 63.4 | 40 | `trim_tail=40` | 应 23.4 | 错 16.6 m |

**为什么 L1 门禁当时没抓到**：`routes.json` 的路线起终点全是**边界节点**（`offset_m = 0`），`trim_head`/`trim_tail` 恒为 0，该 bug 对 E/F 项完全不可见 —— 这是门禁的覆盖漏洞，已补 H 项（见 §4）。

修后复验：`trim_head_m` 与 `dist(start_point, steps[0].geometry[0])` 最大偏差 **0.03 m**（SZ-004 三个 offset + SZ-023 两个 offset），`length_m ≈ Σsteps.length_m − trim` 五条全对，终点侧 `trim_tail_m = 23.4`（= 63.4 − 40）。dev-C 的 12 条矩阵（2 段 × 3 个 offset × 起点/终点）独立跑出 0/12 失败。

**分布实测**（`work/verify/direction_snapshot.json`）：61 段 = forward 14 + **reverse 14** + bidirectional 33；14 条 reverse 是 `SZ-001…SZ-013` + `SZ-061`，**合计 1468.6 m，占全站 4593.6 m 的 32.0%**，且互相连通成一片（1 个连通分量 / 15 个节点）。⇒ 业主「箭头很乱、分不清对不对」不是几个箭头歪，而是**一整片占 1/3 里程的道路同时反向**。

### 1.2 静态方向箭头"乱" —— 三个与分辨率/视口耦合的实现
`MapLibreViewer.vue` 方向层：

| 问题 | 现状 | 后果 |
|---|---|---|
| 朝向用**弦向** | `rotate = bearingDeg(coords)`（首→末整体方位角） | 弯道/两端弯曲段箭头明显歪 |
| 双向段横向偏移换算 | `metersPerPixel(fitZoom)` + 法向 ±12px → 米 | `fitZoom` 随**视口大小**变、公式按 256px 瓦片推（MapLibre 默认 512px 瓦片时**偏大一倍**）、纬度写死 22.99° → **换个窗口分辨率箭头就跑位** |
| 尺寸用 `setLayoutProperty` 按 zoom 桶 | 每段另有 `icon_scale` | 缩放时跳变，与"随路段缩放"不符 |

### 1.3 路线本身没有箭头
`MapLibreViewer` 只画**全网点**的 OSM 单行方向，路线（`arrival_route` / `/route/plan`）没有行进箭头。所以"后端标向对不对"在图上**无法验证** —— 这是"分不清对错"的根源。

## 2. 接口契约（本次新增，非业主契约字段，仅前端展示用）

**业主契约 `arrival_route` 的必填字段一个不动；契约响应里也不出现 `steps`。**

`steps` / `start_point` 的投放位置：
1. **产物**：`work/engine/run.py` 的 `attach_route_steps()` 给 `work/engine/out/{real,sample,compare}/routes.json` 里每条路线补 `steps`（real/sample/compare 三条产出路径共用）。
2. **`/route/plan`**（非契约只读端点）：每条路线带 `steps`，并新增 `start_point`；`/route/snap` 回显 `direction`。
3. **新增非契约只读端点** `GET /api/traffic/route/{request_id}/steps`（`work/assembly/traffic.py`，紧接 `/route/options` 之后）：按 `request_id` 返回该请求各条路线的 `steps`，未知 id 返回 404。
4. **`/route/recommend`（业主契约端点）继续不透传 `steps`** —— 由 `_route_body_without_steps()` / `_strip_route_steps()`（`work/assembly/traffic.py:2746` 前）显式剥离，`selfcheck_ikmf1t.py` 有硬断言守着，**任何整包透传的回退都会被这条断言打红**。

```jsonc
{
  "start_point": { "node_id": "N-022", "segment_id": "SZ-004", "edge_id": "SZ-004",
                   "offset_m": 0.0,          // ★ coords 序（与前端 pointAtOffset 同口径）
                   "offset_travel_m": 120.7,  // 行进序，仅供需要沿行进方向算距离的调用方
                   "direction": "reverse",
                   "lon": 112.6580882, "lat": 23.2135346 },
  "steps": [
    { "segment_id": "SZ-004", "edge_id": "SZ-004", "direction": "reverse",
      "from_node": "N-040", "to_node": "N-022",
      "length_m": 120.7,
      "trim_head_m": 0.0, "trim_tail_m": 0.0,      // 首/末段起终点落在段中时，各有多少米不该画
      "geometry": [[lon,lat], ...] }   // ★ 已按行进顺序排列，前端不许再猜方向
  ]
}
```

规则：
1. `geometry` 的**首点必须等于 `from_node` 的坐标、末点必须等于 `to_node` 的坐标**（容差 1e-9）——由后端自检强制。
2. `direction`：`"forward"` = 与 `coords` 同序；`"reverse"` = 反向。`"bidirectional"` 的路段在路线里**必须**给出确定的 `"forward"` / `"reverse"`（路线是链，方向唯一）。
3. 相邻 `steps` 满足 `steps[i].to_node == steps[i+1].from_node`。
4. `trim_head_m` / `trim_tail_m` 只出现在首段/末段：起终点在段中时告诉前端这两端各有多少米不该画。前端裁完若剩余长度 < `DIR_MIN_DRAW_LEN_M`（30 m）就**整段不画箭头**（宁可缺一个，也不要在极短残余段上放大切线噪声）。
5. **口径分工**：`offset_m` 一律 coords 序（twin 真值口径）；需要行进序的地方一律读 `offset_travel_m`，不许自己折。

## 3. 前端渲染规则（杜绝分辨率依赖）

1. **位置**：箭头画在该 `geometry` 的**50% 弧长**点，**不做任何横向像素偏移**。
2. **朝向**：该点的**局部切线方位角**（取该点前后 N 米内的线段，N = min(15 m, 1/4 段长)），不用弦向。
3. **尺寸**：用 `icon-size` 的 **zoom 插值表达式**（数据驱动，不调 `setLayoutProperty`），例如 `["interpolate",["linear"],["zoom"], 13,0.45, 16,0.75, 19,1.1]` × 路段自身 `icon_scale`（仅保留"主/次干道"这类业务差异，上限 1.3）。**禁止** `metersPerPixel`、`fitZoom`、写死纬度。
4. **双向段（单行标志为假、两向都能走的 33 段）**：画**一支共轴双头箭头**（0.5 弧长点、零横向偏移）。理由：本包双向段仅 16.3~19.2 m，两支 34 px 图标必然叠；MapLibre 的 `icon-offset` 是屏幕空间偏移、不随 `icon-rotate` 旋转，做法向偏移必然回到米/像素换算（正是要删掉的那类依赖）；双头箭头语义直白，可省掉 `icon-offset` 这一路几何。
5. **路线箭头只认 `steps`**：不再用 `segmentDirections` 推断路线朝向；`/route/recommend`（契约端点，无 `steps`）回退到"按链式连通性定向"（用 `edges` 的 `from/to` 链推方向），**不允许**直接按 `coords` 顺序画。
6. **起点标记**：优先取 `start_point.lon/lat`；拿不到时（如 `/route/recommend`）用 `location.offset_m` 按 **`coords` 序**折（`pointAtOffset(coords, offset_m)`），**不许**折行进序 —— 见 §1.1。

## 4. 确认箭头标向的方案（三层，从机器到人眼）

| 层 | 做法 | 判定 |
|---|---|---|
| **L1 拓扑自检**（机器，秒级） | `work/engine/tools/audit_segment_direction.py`：对 61 段 + 每条路线每个 step 断言 —— `geometry` 首末点 == `from_node`/`to_node` 坐标；相邻 step 节点相接；`direction` 与 `coords` 序一致；反向段 `length_m` 与 `coords` 累计长度同值；`coords_offset_to_travel` ↔ `travel_offset_to_coords` 互逆；reverse 段 `offset_m = 0` 的 `start_point` == `coords[0]`；SUMO shape 首点 == `from` 节点（`--prove-offset`） | 全绿（10 项）才算后端"标向正确"，任何一条不过直接打印段 id |
| **L2 数值快照**（机器，可 diff） | 同一脚本 dump `work/verify/direction_snapshot.json`：`{segment_id: {from, to, direction, bearing_coords_order, bearing_travel}}`，进 git → 方向一旦被改错，**diff 立刻现形** | 快照 diff 为空 |
| **L3 人眼对照**（图纸 + 真机，可验收） | `scripts/verify_arrow_direction.py` 生成**北向上、带指北针与比例尺**的 SVG 图版：同一路段并排画 `coords` 顺序（灰）与**行进顺序**（彩色 + 箭头），并标注 `from/to` 节点名；再叠真实前端三档视口截图（1440×900 / 1920×1080 / 2560×1440） | 箭头锥尖一致朝 `to_node`；三档视口下箭头几何落在路段弧长中点（位置差 < 段长 3%）、切线朝向误差 < 5° |
| **L4 偏移口径往返**（机器，防镜像） | `work/verify/verify-offset-caliber.mjs`：对 reverse 段取非零 `offset_m` 的 demo 车，走 `POST /api/traffic/route/snap` 往返（后端用**自己的**几何和自己的偏移口径吸附），回显 `segment_id / offset_m / lon / lat` | 段号一致、`offset` 往复误差 ≤ 0.1 m、两轮经纬度距离 < 2 m。若 `offset_m` 被当行进序读，输入 20 会回显 ~`length-20`，一眼可辨 |

> **注**：`/api/traffic/locate` 不返回 `lon/lat`（只有 `segment_id / offset_m / match_confidence / source`），所以起点标记的正确性**不能**用 `/locate` 直接对坐标，必须走 L4 的 snap 往返判据。

**验收口径**：L1 十项全绿 + L2 diff 空 + L3 三档截图箭头都落在路段中线中点、锥尖朝行进方向 + L4 往返误差达标（起点标记落在 `start_point`，或在 `start_point` 缺席时按 `coords` 序折出的点上）。
