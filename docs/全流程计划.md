## 1. 本版裁定（V2.0 的九条硬口径）

| 编号 | 裁定 | 一句话说明 | 详见 |
|---|---|---|---|
| **D1** | **一期车流量全部来自数字孪生；摄像头视频感知整体归二期** | 一期在 SUMO 里布"虚拟检测器"（放在二期真摄像头将来的位置），只输出"这段路有多少车、多快、排多长"，字段与二期视频感知**完全一样**，二期换数据源不改下游 | 手册第 5、10 章 |
| **D2** | **定位分两期：一期直接知道车辆位置；二期靠 App 定位 + 地图匹配** | 一期车辆就在孪生里，后端直接读到"它在哪条路、离路口多远"；二期才需要 App 上报定位、由后端判断"你在哪条路上的哪个位置" | 手册第 9 章 |
| **D3** | **摄像头只数车，不认车；App 定位只用来帮你规划路线** | 摄像头（一期是虚拟检测器）只给路段级聚合数（有多少车、堵不堵），**不知道哪辆车是哪位用户**；App 定位只用于"你在这条线路的哪个位置 → 帮你匹配最省时最不拥挤的路线"。**两条数据线不做任何关联** | 手册第 9.2 节 |
| **D4** | **分流决策必须"前后车都不受影响"** | 不是只把第一辆车送进最佳路线、后车再挤进去又堵；而是给每辆车**预约它将来经过各路段的时段容量**，新车的安排**不得让已安排的前车变慢**，前车遇堵还会被提前疏导，给后车腾路 | 手册第 7.6 节 |
| **D5** | **拥堵因素按"因素登记表"统一管理** | 天气、停车、事故、施工、列车到达、信号、节假日、大型活动等 14 类因素，每类写清**数据从哪来、改的是什么（容量 / 速度 / 需求 / 封路）、谁填、谁实现** | 手册第 19 章 |
| **D6** | **二期判级与决策"按路段定制参数 + 定期自动重标定"，并新增车流量预测** | 固定阈值换到真实数据上会失准，所以每条路用自己的真实数据定参数，并持续复查；新增 5/15/30/60 分钟车流量预测，预测结果直接喂给 D4 的时段预约 | 手册第 20 章 |
| **D7** | **路网拓扑走 OSM + netconvert，高德 / 百度做底图、POI 与核对** | 高德 / 百度开放平台主要提供底图、POI、路径规划与路况，**一般不提供可下载的车道级路网拓扑**，且条款可能限制提取道路数据（阶段 0 核实条款）。SUMO 能直接读 OSM，再由人按高德底图逐条核对补录 | 手册第 8.3 节 |
| **D8** | **一期运行方式：孪生驱动的单进程主循环 + 文件快照当契约** | 孪生每秒走一步，每 60 秒算一次指标、判级、重分配；各模块仍可拿样例文件单独开发和测试。**不要求任何人会前后端分离** | 手册第 4.3 节 |
| **D9** | **团队按"3 名开发 + 4 名非技术成员 + 队长"重新分工；非技术成员通过"填表格"参与开发** | 只有 3 人会用 vibe coding 写代码；其他人填 Excel 模板、标注、测试、写文档、对外联络。表格由开发写的转换脚本变成配置文件 | 本文第 9、10 节，[`分工表.md`](分工表.md) |

> **D1 带来的口径变化**：一期**不再**有"视频识别 → 车流量"这一段，演示中出现的所有车流量、拥堵等级都是孪生算出来的（`source: "twin"`，`is_simulated: true`）。
> 已经做完的 `.ckpt` 权重转换与识别链路**保留为二期资产**，一期不再投入；一期答辩时不讲"视频识别已用于路况判定"。

## 3. 一期运行架构（D1 + D8）

```text
            ┌──────────── 站点包 stations/（路网、点位、因素、场景、阈值）────────────┐
            ↓                                                                      ↓
┌──────────────────── 主循环 work/twin/loop.py（单进程，开发A） ────────────────────┐
│ 每 1 秒：SUMO 走一步（跟驰、排队、信号）←→ 自研司机行为体（TraCI：改路线/停靠/候客）│
│          ↑ 因素注入：天气降速、违停占道、事故封道、停车场满位、列车到达放量……     │
│ 每 60 秒：虚拟检测器聚合 → 四项指标 → 判级 → segments 快照         （开发A）       │
│          → 决策引擎：时段预约表更新 + 前车再疏导 + 新请求分配 → routes 快照（开发B）│
│ 有车进入站前围栏：车辆位置（孪生真值）→ 定位匹配 → 引擎推荐 → 行为体决定是否采纳  │
└────────────────────────────────────────────────────────────────────────────────────┘
            ↓ 快照文件（segments.json / routes.json / vehicles.json，见数据契约 v2.0）
┌──────────── 接口层 work/assembly/traffic.py（开发C）────────────┐
│ 只读快照 → /api/traffic/* + SSE 推送                             │
└──────────────────────────────────────────────────────────────────┘
            ↓                                   ↓
     管理端（Vue，开发C）               司机端鸿蒙 App（开发C，绑定演示车）
```

三条要点：

1. **只有一个时钟**：孪生的仿真时钟。所有指标、判级、推荐都按仿真时间打时间戳，所以**同一场景可以完整回放**（TC-13）。
2. **模块之间仍然靠文件契约**：每个模块都能拿样例文件单独跑（如 `python work/engine/run.py --sample`），主循环只是按顺序调用它们的函数。**不需要开两个服务联调。**
3. **二期替换点只有两个**：虚拟检测器 → 视频感知；孪生里的车辆真值位置 → App 定位 + 地图匹配。其余模块不改。

## 4. 定位：怎么知道"你在哪条路上"（D2 + D3）

### 4.1 两期对照

| 项 | 一期（虚拟） | 二期（真实） |
|---|---|---|
| 车辆位置从哪来 | 孪生里直接读（TraCI：所在路段、车道、离路段起点多少米） | App 定位（北斗/GNSS），进入站前围栏后每 5–10 秒上报 |
| 坐标系 | 孪生内部米制坐标，可换算 WGS-84 | 统一转 WGS-84；与高德 GCJ-02、百度 BD-09 的互转离线内置 |
| "在哪条路上"怎么判断 | 直接已知（真值） | **地图匹配**：把一串定位点吸附到路网，得出路段 ID + 路段内位置 + 行驶方向（隐马尔可夫匹配） |
| 精度 | 真值 | 站前高楼区误差 10–30 m，靠地图匹配与行驶方向纠正 |
| 一期为二期做的准备 | 用孪生真值**加噪声**（σ = 10–30 m）生成假定位，提前测试地图匹配模块 | 直接换成真实定位输入 |

### 4.2 统一接口（一期就按这个形状做，二期只换输入）

```text
locate(session_id, position, heading, ts) → {
    segment_id, offset_m, direction, route_progress, match_confidence
}
```

- 一期输入是孪生真值，`match_confidence = 1.0`；
- 二期输入是 App 定位，`match_confidence < 0.6`【待标定】时不用于重新规划，提示"定位不稳定，请确认所在道路"。

### 4.3 隐私口径（写进 App 告知文案与答辩口径）

1. **摄像头 / 虚拟检测器只数车不认车**：只输出路段级聚合数，不输出车牌、人脸、车辆身份；
2. **App 定位只为用户本人的这次行程服务**：用来判断他在线路的哪个位置、帮他匹配路线；**不与摄像头数据关联**、不给其他司机看、不入库（只保留本次会话，行程结束即删）；
3. **用户主动同意**才开启定位；拒绝时降级为"手动选所在道路 / 只看路况"，流程不中断（TC-05）。

## 5. 前后车协同分流（D4）

### 5.1 要解决的问题（大白话）

普通导航：A 路最快 → 告诉所有人走 A 路 → 前几辆车很快，后面的车涌进去，A 路堵死，**前车也被后车拖慢**。

旧方案的"配额发号"解决了"别都往一条路挤"，但**只按路线计数**，没考虑"前车什么时候到哪一段"，也没有"前车遇堵再疏导"。

### 5.2 新机制：三件事一起做

| 机制 | 做什么 | 效果 |
|---|---|---|
| **① 时段容量预约** | 把每条路段按 1 分钟切成时段；给一辆车推荐路线时，按它的预计到达时间，**在它将经过的每段路、每个时段上各登记一个占用** | 后车看到的是"前车将来会在哪"，不是只看"现在哪条路空" |
| **② 不伤害前车约束** | 新车只能放进"加上它之后，所有已登记车辆的预计耗时增加都不超过 30 秒【待标定】、任何路段时段饱和度不超过 0.85【待标定】"的路线；在满足约束的路线里选**对它自己最快**的 | 后车进来不会把前车拖慢；后车自动分流到其他道路 |
| **③ 前车再疏导** | 每 60 秒检查一次在途车辆：前方路段因突发情况变堵时，在下一个可分岔路口前给出改道建议（每车最多改 2 次，10% 滞回防抖）；送完客的车优先引导离开落客区 | 前车被及时疏散，给后车腾出容量 |

**都放不下时**：输出 `capacity_shortage`，建议"外围等待 / 延后 N 分钟 / 换停车场"，**不硬塞**。

**没装 App 的车**：它们是"背景车流"，由检测器（一期虚拟、二期摄像头）测出、由预测模型（二期）推到未来时段；预约表在背景车流之上再叠加 App 用户的预约。

### 5.3 怎么证明做到了（TC-17，演示场景二的核心画面）

同一份输入跑两遍：

- **对照组**：所有司机都拿"此刻最快"的路线（普通导航做法）；
- **实验组**：时段预约 + 不伤害约束 + 前车再疏导。

判定：实验组中**先进入的车的到达时间不因后车进入而变长超过 30 秒**（前车不受影响）；**没有新增橙 / 红路段**（拥堵没被转移）；全网总行程时间低于对照组。

## 6. 多因素（D5）

一期全部因素**在孪生里模拟注入**，二期逐项换成真实数据源。完整登记表见手册第 19 章，这里是总览：

| # | 因素 | 作用在哪 | 一期来源 | 二期来源 |
|---|---|---|---|---|
| F01 | 天气（雨、雾、台风、高温） | 通行能力 ↓、畅通速度 ↓、服务时长 ↑ | 因素表手填 | 气象数据接口 |
| F02 | 昼夜 / 能见度 | 检测置信度、车速 | 时段表 | 日出日落 + 摄像头画质 |
| F03 | 列车到发（班次、晚点、客流） | 到站车流需求 | 12306 公开时刻表手填 | 铁路部门数据 |
| F04 | 落客区占用 | 落客区服务能力、排队 | 孪生模拟 | 摄像头 |
| F05 | 停车场 / 蓄车区余位 | 停靠点选择、入口排队溢出 | 孪生模拟 | 停车场管理系统接口 |
| F06 | 路边违停 / 占道 | 车道数 −1 → 通行能力按比例降 | 场景注入 | 摄像头事件检测 + 人工上报 |
| F07 | 交通事故 / 故障车 | 封闭车道或路段，触发红档 | 场景注入 | 摄像头事件 + 管理端人工置位 |
| F08 | 施工 / 临时管制 | 封闭车道 / 禁止转向，带生效时间窗 | 因素表手填 | 交警 / 城管通告，人工录入 |
| F09 | 信号配时 | 交叉口通行能力 c = s₀·g/C | 1 路口 2 方案手填 | 交警配时方案 |
| F10 | 时段 / 日历（工作日、周末、节假日、春运） | 需求倍率 | 日历表手填 | 历史数据统计 |
| F11 | 大型活动（演唱会、展会） | 需求倍率 + 时间窗 | 场景注入 | 活动日历人工录入 |
| F12 | 车型构成（私家车 / 出租 / 网约 / 大巴） | 当量换算、服务时长 | 需求表手填 | 摄像头车型识别 |
| F13 | 外围路网路况 | 进入站前区域的边界车流 | 孪生边界车流 | 高德路况接口（条款核实后） |
| F14 | App 渗透率 / 采纳率 | 能被引导的车流比例 | 参数 | App 实际数据 |

**合成规则**：各因素对通行能力、畅通速度分别**相乘**，合成后不低于原值的 40%【待标定】；每条路段输出 `factors_applied` 字段，写明"这一刻哪些因素在起作用、各改了多少"，推荐理由 `why` 可以引用（如"大雨，A 路通行能力已按 0.75 折减"）。

## 7. 二期：为什么还要"调模型"，以及车流量预测（D6）

### 7.1 先回答一个担心

> "如果按固定指标判拥堵，接入真实数据后会不会因为数据差异判断失败？"

**会。** 一期的阈值、通行能力、行程时间参数全部是 demo 假设值，换到真实路上一定会偏。应对分三层：

| 层 | 做法 | 大白话 |
|---|---|---|
| **① 每条路自己的标准** | 判级本来就用相对口径（实测速度 ÷ 这条路的畅通速度）；二期给**每条路段**用它自己的真实数据定畅通速度、通行能力、各档边界 | 不拿主干道的标准去量落客通道 |
| **② 定期自动复查** | 每周用最近 4 周数据重算参数；非技术成员每周抽 50 段画面人工判"堵不堵"，系统判级与人工一致率低于 85% → 自动触发重标定，管理端提示"参数待更新" | 参数不是定一次就不管 |
| **③ 数据驱动的模型** | 车流量预测模型、司机选择行为参数，用真实数据训练和校正；规则保留为"安全底线"，模型异常时退回规则 | 能学的交给模型，不能错的留给规则 |

所以："按路段定制参数"之后，判级规则本身基本不用改，需要持续调的是**参数**和**预测模型**。

### 7.2 车流量预测（二期新增）

| 项 | 口径 |
|---|---|
| 预测什么 | 每条路段未来 5 / 15 / 30 / 60 分钟的流量、平均车速、拥堵等级；落客区、蓄车区未来占用 |
| 用什么预测 | 该路段历史车流 + 上下游路段 + 列车到达（未来 60 分钟班次与客流）+ 天气 + 日历 + 活动 + 停车场余位 |
| 模型阶梯 | **L0** 历史同期均值（第一天就能用，保底）→ **L1** 机器学习回归（数据满 4 周）→ **L2** 时空图神经网络，MindSpore 实现（数据满 3 个月）。**下一级必须比上一级误差低 10% 以上才替换** |
| 怎么用 | ① 预测的背景车流填进第 5 节的时段预约表——"前后车都不受影响"在真实场景里靠它；② 管理端显示"15 / 30 分钟后预计等级"，提前预警、提前分流 |
| 验收指标【待标定】 | 15 分钟流量 MAPE ≤ 15%；30 分钟 ≤ 20%；预测等级与实际一致率 ≥ 80%；列车到达高峰时刻误差 ≤ 5 分钟 |
| 防失控 | 每天对比预测与实际；连续 3 天误差超标 → 自动退回 L0 并告警；模型版本可回滚 |
| 一期准备什么 | 只做预测**接口** + L0 保底实现（用孪生数据跑通链路，标 `is_simulated`，**不报任何精度数字**） |

### 9.2 开发工作量平衡

旧分工里"后端一人背 6 章 + 数字孪生"是全表最重的一格，且开发实际只有 3 人。V2.0 的处理：

- 数字孪生（最高风险）给开发A；开发A **一期不再做视频识别**（D1），腾出的工作量正好接住孪生；
- 开发B 的算法最密集，手册第 7.6 节给出**可直接投喂 AI 的伪代码**，降低 vibe coding 难度；
- 开发C 一人做两端：管理端复用现有 Vue 工程，App 只做 P0 四页；
- **所有"填数据"的工作**（点位、路段属性、时刻表、因素、场景参数）从开发手里拿走，交给非技术成员填表（第 10 节）；
- 代码互审：A 审 B、B 审 C、C 审 A；每个 PR 先让 AI 做一遍审查；队长只看"有没有影响别人"和对外口径。
