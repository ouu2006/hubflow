## 1. 本版裁定（V2.0 的九条硬口径）

| 编号 | 裁定 | 一句话说明 | 详见 |
|---|---|---|---|
| **D1′** | **一期是"双数据源"：视频感知链路（YOLO 跑 6 段真实样本视频）+ 孪生链路（虚拟检测器）** | 两条链路**字段逐字段一致、共用同一套下游判级与决策**，只有 `source` 取值不同（`"video"` / `"twin"`）。孪生链路在 SUMO 里布"虚拟检测器"（放在二期真摄像头将来的位置），给出**会演化的世界**与**同一输入跑三遍的开关对照实验**；视频感知链路跑**6 段真实样本视频**（检测 → 跟踪 → **透视标定** → 四项指标 → 判级），让**项目核心的 YOLO 在一期就当众在算路段拥堵**。两条互为校验，且**用视频实测去标定孪生的边界条件**（手册 10.13）。**二期只有两处替换**：① 视频源：6 段离线样本视频 → **现场实时摄像头流**（`source` 仍是 `"video"`，**字段不变**，点位由 池·S 现场订正）；② 车辆位置：孪生真值 → **App 定位 + 地图匹配**。其余一字不改 | 手册第 5.0.1、10.13 节 |
| **D2** | **定位分两期：一期直接知道车辆位置；二期靠 App 定位 + 地图匹配** | 一期车辆就在孪生里，后端直接读到"它在哪条路、离路口多远"；二期才需要 App 上报定位、由后端判断"你在哪条路上的哪个位置" | 手册第 9 章 |
| **D3** | **摄像头只数车，不认车；App 定位只用来帮你规划路线** | 摄像头（一期是**样本视频与虚拟检测器**）只给路段级聚合数（有多少车、堵不堵），**不知道哪辆车是哪位用户**；App 定位只用于"你在这条线路的哪个位置 → 帮你匹配最省时最不拥挤的路线"。**两条数据线不做任何关联** | 手册第 9.2 节 |
| **D4** | **分流决策必须"前后车都不受影响"** | 不是只把第一辆车送进最佳路线、后车再挤进去又堵；而是给每辆车**预约它将来经过各路段的时段容量**，新车的安排**不得让已安排的前车变慢**，前车遇堵还会被提前疏导，给后车腾路 | 手册第 7.6 节 |
| **D5** | **拥堵因素按"因素登记表"统一管理** | 天气、停车、事故、施工、列车到达、信号、节假日、大型活动等 14 类因素，每类写清**数据从哪来、改的是什么（容量 / 速度 / 需求 / 封路）、谁填、谁实现** | 手册第 19 章 |
| **D6** | **二期判级与决策"按路段定制参数 + 定期自动重标定"，并新增车流量预测** | 固定阈值换到真实数据上会失准，所以每条路用自己的真实数据定参数，并持续复查；新增 5/15/30/60 分钟车流量预测，预测结果直接喂给 D4 的时段预约 | 手册第 20 章 |
| **D7** | **路网拓扑走 OSM + netconvert，高德 / 百度做底图、POI 与核对** | 高德 / 百度开放平台主要提供底图、POI、路径规划与路况，**一般不提供可下载的车道级路网拓扑**；且条款**已明文限制**存储 / 缓存 / 截图 / 衍生数据（见 [`条款核实.md`](条款核实.md)），所以路网必须自带。SUMO 能直接读 OSM，再由人按高德底图逐条核对补录（**核对不落盘、不截图**） | 手册第 8.3 节 |
| **D8** | **一期运行方式：孪生驱动的单进程主循环 + 文件快照当契约** | 孪生每秒走一步，每 60 秒算一次指标、判级、重分配；各模块仍可拿样例文件单独开发和测试。**不要求任何人会前后端分离** | 手册第 4.3 节 |
| **D9** | **团队按"3 名开发 + 3 名任务池（许愿池）协作成员 + 队长（由 7 人中 1 人兼任）"重新分工；协作成员以"填表格 + 数据/测试/文档"为主，同时参与一部分技术开发** | 3 人主写代码（核心引擎与双端）；另外 3 人以数据、标注、测试、文档、对外联络为主，**认领任务池四个系列（V / S / P / Q）的任务，无锁角色**，**并在开发组带教下承担部分技术开发**（`netedit` 补画路网、控制点拾取、转换与检查脚本、场景与因素配置、演示物料生成）。表格由开发写的转换脚本变成配置文件 | 本文第 9、10 节，[`分工表.md`](分工表.md) |

> **D1′ 带来的口径变化**：一期**同时跑两条链路**，`segments.json` 的 `source` 取 **`"video"`**（视频感知链路：6 段真实样本视频 → YOLO → 透视标定 → 四项指标 → 判级）或 **`"twin"`**（孪生链路：虚拟检测器）。**两条链路的 `is_simulated` 都恒为 `true`**——视频虽是真实拍摄，但**不是肇庆东站现场**，指标由算法算出，对外一律标"演示数据（模拟）"。
>
> **为什么要两条，不能只留一条**：① **只留视频**——样本视频是固定录像，**推荐改变不了它**，"我们的推荐让总行程时间下降 X%"这个核心结论无从证明，"世界会自己演化"的效果也没有；② **只留孪生**——**项目核心的 YOLO 就看不见了**，答辩会被追问"到底用没用视觉模型"；③ **两条一起**——视频给**真实路段的实测值**，孪生给**可对照可回放的演化**，且**用视频实测标定孪生的边界条件**，两条互为校验。
>
> **口径纪律**：视频是**真实拍摄的样本视频，但不是肇庆东站现场**；站点几何来自 OSM + 人工核对。一期**可以讲**"视频识别正在算路段拥堵"、可以讲"**MindSpore 链路已验证**"；**不得**说成"现场实测"或"已在肇庆东站上线"，**不得**讲"昇腾部署已验证"。
>
> **数据同化**：把视频链路的实测流量 / 车速通过 SUMO `calibrator` **回灌到孪生的边界断面**（每 60 s 一次，带置信度门控）；**站前内部路段不灌**（否则孪生变成录像回放、对照实验失效）。详见手册第 10.14 节与 **TC-20 / M1-10**。
>
> 已经做完的 `.ckpt` 权重转换与识别链路**一期即投入使用**（视频感知链路），**不是二期资产**。
>
> > **旧口径（V2.0，已被 D1′ 取代，仅作历史留档）**：V2.0 曾裁定"**一期车流量全部来自数字孪生；摄像头视频感知整体归二期**"（D1），并称 `.ckpt` 链路"保留为二期资产、一期不再投入"、一期答辩不讲"视频识别已用于路况判定"。**以上一律作废，以 D1′ 为准。**

## 3. 一期运行架构（D1′ + D8）

```text
   ┌─ 视频感知链路（开发A，一期就跑真实样本视频）────────────────────────────────┐
   │ 6 段真实样本视频（traffic-core-mindspore/video/）                          │
   │   → YOLO 检测 → 跟踪 → 像素轨迹 → 透视标定（控制点由 池·V 拾取）            │
   │   → 米制轨迹 + 车道归属 → 四项指标 → 判级（source: "video"）                │
   └──────────────────────────────────┬──────────────────────────────────────────┘
                                      │  ┌─ 视频实测值标定孪生边界（手册 10.13）
                                      │  │  到达流率 / v_f / s₀ / 排队阈值 / 服务时长
                                      ↓  ↓
                                      │  ┌─ 数据同化（手册 10.14，每 60 s，带门控）
                                      │  │  视频实测（边界断面）→ calibrator.setFlow → SUMO 边界来车
                                      │  │  ⚠ 只灌 boundary 断面；internal 断面不灌
            ┌──────────── 站点包 stations/（路网、点位、因素、场景、阈值、标定）────────────┐
            ↓                                                                      ↓
┌──────────────────── 主循环 work/twin/loop.py（单进程，开发A） ────────────────────┐
│ 每 1 秒：SUMO 走一步（跟驰、排队、信号）←→ 自研司机行为体（TraCI：改路线/停靠/候客）│
│          ↑ 因素注入：天气降速、违停占道、事故封道、停车场满位、列车到达放量……     │
│ 每 60 秒：虚拟检测器聚合 → 四项指标 → 判级 → segments 快照（source: "twin"）（开发A）│
│          → 决策引擎：时段预约表更新 + 前车再疏导 + 新请求分配 → routes 快照（开发B）│
│ 有车进入站前围栏：车辆位置（孪生真值）→ 定位匹配 → 引擎推荐 → 行为体决定是否采纳  │
└────────────────────────────────────────────────────────────────────────────────────┘
            ↓ 两条链路都汇到 segments 快照（同一份契约，只有 source 不同）
            ↓ 快照文件（segments.json / routes.json / vehicles.json，见数据契约 v2.0）
┌──────────── 接口层 work/assembly/traffic.py（开发C）────────────┐
│ 只读快照 → /api/traffic/* + SSE（可并排展示 video / twin 两个来源）│
└──────────────────────────────────────────────────────────────────┘
            ↓                                   ↓
     管理端（Vue，开发C）               司机端鸿蒙 App（开发C，绑定演示车）
```

三条要点：

1. **只有一个时钟**：孪生的仿真时钟。所有指标、判级、推荐都按仿真时间打时间戳，所以**同一场景可以完整回放**（TC-13）。**视频链路按视频帧时间戳对齐到同一根时间轴**。
2. **模块之间仍然靠文件契约**：每个模块都能拿样例文件单独跑（如 `python work/engine/run.py --sample`），主循环只是按顺序调用它们的函数。**不需要开两个服务联调。**
3. **二期替换点只有两个**：① **视频源**——6 段离线样本视频 → **现场实时摄像头流**（`source` 仍是 `"video"`，**字段不变**）；② **车辆位置**——孪生真值 → **App 定位 + 地图匹配**。其余模块不改。

> **判级归属（2026-10-10 裁定）**：上图两条链路里「**四项指标 → 判级**」这一步，**四项指标 `metrics.py` 归开发A，判级 `work/perception/level.py` 归开发B**（`thresholds.json` 的**判级参数组**与**决策参数组**都归开发B，该文件**只有一个写手**）。因此 `work/perception/` 是全仓唯一的「**一目录两写手**」目录：**除 `level.py` 外全部归开发A**；**例外的是文件，不是"同一文件两组"**。

**架构层职责表：已定稿并生效。**

> **架构层职责表（架构分层 + 对应职责与分工）已生效**，正式落点 = [`分工表.md`](分工表.md)——即 PR #20《中心文档① 分工与验收表》，**2026-10-10 业主 / 队长拍板直接作为项目分工表**（原「角色 × 周」版分工表同时停用，留档 [`分工表_已停用_角色×周任务表.md`](分工表_已停用_角色×周任务表.md)）。

## 4. 定位：怎么知道"你在哪条路上"（D2 + D3）

### 4.1 两期对照

| 项 | 一期（虚拟） | 二期（真实） |
|---|---|---|
| 车辆位置从哪来 | 孪生里直接读（TraCI：所在路段、车道、离路段起点多少米） | App 定位（北斗/GNSS），进入站前围栏后每 5–10 秒上报 |
| 坐标系 | 孪生内部米制坐标，可换算 WGS-84 | 统一转 WGS-84；与高德 GCJ-02、百度 BD-09 的互转离线内置 |
| "在哪条路上"怎么判断 | 直接已知（真值） | **地图匹配**：把一串定位点吸附到路网，得出路段 ID + 路段内位置 + 行驶方向（隐马尔可夫匹配） |
| 精度 | 真值 | 站前高楼区误差 10–30 m，靠地图匹配与行驶方向纠正 |
| 一期为二期做的准备 | 用孪生真值**加噪声**（σ = 10–30 m）生成假定位，提前测试地图匹配模块 | 直接换成真实定位输入 |

### 4.2 统一接口（一期就按这个形状做，二期只换输入）

```text
locate(session_id, position, heading, ts) → {
    segment_id, offset_m, direction, route_progress, match_confidence
}
```

- 一期输入是孪生真值，`match_confidence = 1.0`；
- 二期输入是 App 定位，`match_confidence < 0.6`【待标定】时不用于重新规划，提示"定位不稳定，请确认所在道路"。

### 4.3 隐私口径（写进 App 告知文案与答辩口径）

1. **摄像头 / 虚拟检测器只数车不认车**：只输出路段级聚合数，不输出车牌、人脸、车辆身份；
2. **App 定位只为用户本人的这次行程服务**：用来判断他在线路的哪个位置、帮他匹配路线；**不与摄像头数据关联**、不给其他司机看、不入库（只保留本次会话，行程结束即删）；
3. **用户主动同意**才开启定位；拒绝时降级为"手动选所在道路 / 只看路况"，流程不中断（TC-05）。

## 5. 前后车协同分流（D4）

### 5.1 要解决的问题（大白话）

普通导航：A 路最快 → 告诉所有人走 A 路 → 前几辆车很快，后面的车涌进去，A 路堵死，**前车也被后车拖慢**。

旧方案的"配额发号"解决了"别都往一条路挤"，但**只按路线计数**，没考虑"前车什么时候到哪一段"，也没有"前车遇堵再疏导"。

### 5.2 新机制：三件事一起做

| 机制 | 做什么 | 效果 |
|---|---|---|
| **① 时段容量预约** | 把每条路段按 1 分钟切成时段；给一辆车推荐路线时，按它的预计到达时间，**在它将经过的每段路、每个时段上各登记一个占用** | 后车看到的是"前车将来会在哪"，不是只看"现在哪条路空" |
| **② 不伤害前车约束** | 新车只能放进"加上它之后，所有已登记车辆的预计耗时增加都不超过 30 秒【待标定】、任何路段时段饱和度不超过 0.85【待标定】"的路线；在满足约束的路线里选**对它自己最快**的 | 后车进来不会把前车拖慢；后车自动分流到其他道路 |
| **③ 前车再疏导** | 每 60 秒检查一次在途车辆：前方路段因突发情况变堵时，在下一个可分岔路口前给出改道建议（每车最多改 2 次，10% 滞回防抖）；送完客的车优先引导离开落客区 | 前车被及时疏散，给后车腾出容量 |

**都放不下时**：输出 `capacity_shortage`，建议"外围等待 / 延后 N 分钟 / 换停车场"，**不硬塞**。

**没装 App 的车**：它们是"背景车流"，由检测器（一期虚拟、二期摄像头）测出、由预测模型（二期）推到未来时段；预约表在背景车流之上再叠加 App 用户的预约。

### 5.3 怎么证明做到了（TC-17，演示场景二的核心画面）

同一份输入跑两遍：

- **对照组**：所有司机都拿"此刻最快"的路线（普通导航做法）；
- **实验组**：时段预约 + 不伤害约束 + 前车再疏导。

判定：实验组中**先进入的车的到达时间不因后车进入而变长超过 30 秒**（前车不受影响）；**没有新增橙 / 红路段**（拥堵没被转移）；全网总行程时间低于对照组。

## 7. 二期：为什么还要"调模型"，以及车流量预测（D6）

### 7.1 先回答一个担心

> "如果按固定指标判拥堵，接入真实数据后会不会因为数据差异判断失败？"

**会。** 一期的阈值、通行能力、行程时间参数全部是 demo 假设值，换到真实路上一定会偏。应对分三层：

| 层 | 做法 | 大白话 |
|---|---|---|
| **① 每条路自己的标准** | 判级本来就用相对口径（实测速度 ÷ 这条路的畅通速度）；二期给**每条路段**用它自己的真实数据定畅通速度、通行能力、各档边界 | 不拿主干道的标准去量落客通道 |
| **② 定期自动复查** | 每周用最近 4 周数据重算参数；协作成员每周抽 50 段画面人工判"堵不堵"，系统判级与人工一致率低于 85% → 自动触发重标定，管理端提示"参数待更新" | 参数不是定一次就不管 |
| **③ 数据驱动的模型** | 车流量预测模型、司机选择行为参数，用真实数据训练和校正；规则保留为"安全底线"，模型异常时退回规则 | 能学的交给模型，不能错的留给规则 |

所以："按路段定制参数"之后，判级规则本身基本不用改，需要持续调的是**参数**和**预测模型**。

### 7.2 车流量预测（二期新增）

| 项 | 口径 |
|---|---|
| 预测什么 | 每条路段未来 5 / 15 / 30 / 60 分钟的流量、平均车速、拥堵等级；落客区、蓄车区未来占用 |
| 用什么预测 | 该路段历史车流 + 上下游路段 + 列车到达（未来 60 分钟班次与客流）+ 天气 + 日历 + 活动 + 停车场余位 |
| 模型阶梯 | **L0** 历史同期均值（第一天就能用，保底）→ **L1** 机器学习回归（数据满 4 周）→ **L2** 时空图神经网络，MindSpore 实现（数据满 3 个月）。**下一级必须比上一级误差低 10% 以上才替换** |
| 怎么用 | ① 预测的背景车流填进第 5 节的时段预约表——"前后车都不受影响"在真实场景里靠它；② 管理端显示"15 / 30 分钟后预计等级"，提前预警、提前分流 |
| 验收指标【待标定】 | 15 分钟流量 MAPE ≤ 15%；30 分钟 ≤ 20%；预测等级与实际一致率 ≥ 80%；列车到达高峰时刻误差 ≤ 5 分钟 |
| 防失控 | 每天对比预测与实际；连续 3 天误差超标 → 自动退回 L0 并告警；模型版本可回滚 |
| 一期准备什么 | 只做预测**接口** + L0 保底实现（用孪生数据跑通链路，标 `is_simulated`，**不报任何精度数字**） |

## 10. 任务池（许愿池）怎么用：表格为主 + 技术活也有一份

**原则：协作成员以"填表格 + 交数据/测试记录/文档"为主，同时参与一部分技术开发。** 业务数据只从表格进（开发不得绕过表格改 JSON）；开发写转换脚本，把表格转成 `stations/` 下的配置文件。表格放共享盘，文件名带日期与版本，永不覆盖。各模板的列定义见 [`表格模板说明.md`](表格模板说明.md)。

**任务板 = GitHub Issues**：**区域 owner**（**开发A 孪生与路况 / 开发B 决策与定位 + 判级 / 开发C 接口与双端**）把自己区域的活**拆到"半天可完成、独立可验"的小任务**后发布，协作成员**认领**（**无锁角色**；谁认领谁干，**可单人可多人组队**）；**owner 只发布、不点名、不指派**。**vibecoding 类任务必须挂齐三件 prerequisite（输入样例 / 输出样例 / 自检脚本），缺一不得发布**；**发布必打难度标签 L0 / L1 / L2，L1 必附骨架与断点拆分**（细则见 [`hubflow-plan/04-协作任务池规程.md`](hubflow-plan/04-协作任务池规程.md)）。

> ⭐ **底层框架固定；后面拆分出来的工作给推荐方式，不锁死做法**（2026-10-10 定）：**固定（不能自选）**= 架构分层与模块边界、总体链路与口径、技术栈与选型、契约（字段名/类型/必填/接口形状/版本）、确定性与可回放、完成判定与数值、对外口径纪律、许可与合规红线、协作边界（一个文件一个写手 / 目录归属 / 业务数据只从表格进）；**推荐（可自选）**= 模块**内部**怎么实现（算法与模型细节、栈内库与工具选择、命令与脚本写法、文件组织、伪代码路径）以及任务拆分粒度与排期。**换了推荐做法必须在 Issue / PR 的「实现方式」栏说明“用了什么方式 + 契约与判定不变”，并写进 `work/<模块>/DESIGN.md`**（完整清单见 [`开发规范.md`](开发规范.md) 文首总原则）。

**四个系列**：

| 系列 | 内容 | 类型 |
|---|---|---|
| **V 视频线**（池·V） | CVAT 标注、控制点拾取、人工计数对账、断面适配器运行 | 操作 |
| **S 站点 / 踏勘**（池·S） | 踏勘四合一、点位表维护、12306 → demand、netconvert 执行 | 操作 + vibecoding |
| **P 参数 / 调研**（池·P） | 参数工作表、问卷、竞品记录、文档与演示物料（队长复核） | 操作 |
| **Q 独立验收**（池·Q） | 校验器复跑、金样例回放、判定复跑、缺陷登记、总验收署名 | 验收（回避规则） |

**状态流转**：待领 → 进行中 → 待审（Issue 附产物 / PR）→ 完成（owner 审过关闭）。

**三条认领规则**：

1. **验收回避**：系列 Q 任务的认领者 ≠ 该产物的生产者 / 运行者；**开发不得认领 Q**；
2. **系列续领权**：同系列任务优先由首启者续领，换人须留交接记录（要点 + 坑）；
3. **WIP ≤ 2 + 30 分钟上报**：每人同时进行中任务至多 2 个；卡住 30 分钟在 Issue @队长。

**组队认领**：一条任务**可单人认领，也可多人组队认领**——组队在 Issue 评论里写明**成员与分工**；**验收类（Q 系列）组队同样适用回避规则**，开发不得认领 Q。**不预设谁干哪件活：谁认领谁干。**

**交接留痕**：认领者在 Issue 评论里写「**交了哪个文件、对着哪条判定、过没过**」。

**他们参与的技术开发（不是"只填表"）**：
