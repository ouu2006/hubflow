# 自动审查（每次提交自动运行）

> **这份文档回答一个问题**：每次有人推代码，谁来审、审什么、不通过会怎样。
>
> 一句话：**机器审硬规则（不通过挡住合并），AI 审口径（只提示），人签最后一笔。**

## 1. 为什么不能"由 AI 直接批准"

GitHub 的 `Approve` 必须由一个**有 write 权限的真实账号**的 token 发出。AI 没有 GitHub 账号，也没有 token 身份，所以：

- **AI 不能当 Reviewer，不能点 Approve，不能合并 PR。**
- 分支保护要求 `require_code_owner_reviews = true`，这一笔只能由人签。

所以本项目的做法是**把审查拆成两层**：机器和 AI 把能判的都判掉，人只需要看结论。**人签字前的阅读量从"读完 2500 行 diff"降到"看一屏结论"。**

## 2. 三层结构

```text
① 静态门禁（硬性 · 不通过挡住合并）      ← 机器，秒级，永不漏
        ↓ 通过
② AI 审查（建议性 · 只提示不挡）          ← 模型，读 diff 给口径意见
        ↓ 提示
③ 人工 Approve（code owner 签最后一笔）   ← 人，看结论 + 判断"会不会影响答辩口径"
```

**第 ① 层不通过，PR 根本合不了**（已配为 required status check）。第 ② 层只发评论，不挡——模型会误报，不能当门禁。

## 3. 第①层：静态门禁查什么

实现：`tools/ci/review.py`。跑得比人快，而且**这五类错误人眼最容易漏**：

| # | 检查项 | 为什么必须机器查 |
|---|---|---|
| 1 | **禁入文件**：`.env` / `*.ckpt` / `*.pt` / `*.mp4` / 压缩包 | 本仓库是 **public**，权重和视频传上去 clone 会变很慢，且 GitHub 有大小限制 |
| 2 | **密钥特征**：`sk-` / `ghp_` / `AKIA` / 阿里云 `LTAI` / 腾讯云 `AKID` / 地图 Key 硬编码 / URL 带 `key=` | **Key 泄露是 public 仓库最严重的事故**，绝不能靠人眼。人看 diff 时最容易忽略一行常量 |
| 3 | **目录归属**：按分支判定——`feat/perception` 只能改 `work/perception/`，动了别人的目录直接 FAIL | 目录边界就是人的边界，越界改文件会撞车 |
| 4 | **公共文件**：根 `README.md`、`.gitignore`、`.env.example`、`run_all.py` 等，非 `feat/backend` 分支修改即 FAIL | 公共文件只由后端一人改 |
| 5 | **跨目录 import**：`work/<位置>/` 之间禁止互相 import | 模块之间**只走 JSON 文件**。一旦互相 import，A 改函数签名 B 就跑不起来 |
| 6 | **JSON 可解析性**：改动过的 `.json` 必须能解析 | 站点包字段错一个字符，下游全线挂，而且报错点离现场很远 |
| 7 | **契约文档变更提醒** | `docs/数据契约.md` 是冻结件，改了必须在 PR 描述里写明影响谁 |

> 第 2 条有个**例外情况**：`stations/` 里的示例数据如果确实需要写一个假 Key，用 `example`、`your_key_here` 这种明显占位符，不要写 32 位十六进制串（会被判为真 Key）。

## 4. 第②层：AI 审查看什么

模型读整个 diff，按项目口径给意见。**提示词写死了七类关注点**：

1. **契约字段命名**：必须 `snake_case` + 单位进后缀（`eta_min` 不是 `eta`、`v_kmh` 不是 `speed`）、布尔加 `is_` 前缀；
2. **`is_simulated`**：一期所有数值必须带，且恒为 `true`；
3. **备选条数**：`routes.json` 的 `alternatives` 必须 **≥2 条**；
4. **目录边界**：同第①层第 5 条，AI 从语义层面再判一次；
5. **口径纪律**：不得把模拟数据说成实测、不得把旁路说成"MindSpore 已验证"、不得把单站说成"可复制"；
6. **既有接口零改动**：`host-fastapi` 既有 8 个端点不得改，只能新增路由注册；
7. **降级链**：数据不可用必须显示灰色，绝不能显示成蓝色。

提示词里明确写了 **"不要为了显得认真而编造问题"**，最多 8 条、600 字以内——**这是防 AI 审查最常见的失败模式：凑数式报错让人干脆不看。**

## 5. 什么时候触发

工作流：`.github/workflows/review.yml`

| 事件 | 说明 |
|---|---|
| `opened` | 新建 PR |
| **`synchronize`** | **PR 有新提交** —— 这就是"每次有新提交就审查" |
| `reopened` | 重新打开 |
| `ready_for_review` | 草稿转正式 |
| `workflow_dispatch` | 手动触发（调试用） |

同一 PR 连续推送时 `cancel-in-progress: true`，上一轮未跑完的直接取消，省额度。

**审查结果以 PR 评论呈现**，且**同一条评论原地更新**（不是每次追加一条）——避免刷屏。

## 6. 不通过会怎样

| 层 | 结果 |
|---|---|
| 静态门禁 FAIL | 工作流失败 → PR 状态变 `BLOCKED` → **合不了**，必须先改掉 |
| AI 审查有意见 | 只是评论，**PR 仍可合并**（由人判断是否采纳） |
| 人未 Approve | 合不了（`require_code_owner_reviews = true`） |

## 7. 需要在仓库里配的东西

| 名称 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `AI_REVIEW_API_KEY` | **Secret** | 否 | 不配也能跑——静态门禁照常，只是报告里写"AI 审查未运行" |
| `AI_REVIEW_BASE_URL` | Variable | 否 | 默认 `https://api.deepseek.com/v1`（已配） |
| `AI_REVIEW_MODEL` | Variable | 否 | 默认 `deepseek-chat`（已配） |

配置命令（由队长执行，**Key 不要贴进任何文件或聊天**）：

```bash
gh secret set AI_REVIEW_API_KEY -R ouu2006/hubflow
# 会提示交互式输入，粘贴后回车
```

> **换模型**：任何兼容 OpenAI `/chat/completions` 的服务都行，改 `AI_REVIEW_BASE_URL` 与 `AI_REVIEW_MODEL` 两个 Variable 即可，**不用改代码**。

## 8. 本地自己跑一遍（推之前先自查）

不必等 CI，本地就能跑：

```bash
# 只跑静态门禁（快）
python tools/ci/review.py --base origin/main --head HEAD --no-ai

# 连 AI 一起跑（要本地有 key）
AI_REVIEW_API_KEY=sk-xxx python tools/ci/review.py --base origin/main --head HEAD

# 只看某个分支
python tools/ci/review.py --base origin/main --head origin/feat/engine --branch feat/engine
```

**退出码**：`0` 通过 · `1` 有 FAIL（门禁不通过）· `2` 工具自身出错。

**建议**：`git push` 之前先跑一次 `--no-ai`，30 秒内就知道自己有没有越界、有没有把 Key 带进去。

## 9. 与"人审"的分工（**不要互相依赖**）

| 谁 | 负责什么 | 不该指望他做什么 |
|---|---|---|
| 静态门禁 | 硬规则、机械检查 | 判断不了设计好坏 |
| AI 审查 | 语义层面的口径与一致性问题 | **会误报，不能当门禁** |
| **人（code owner）** | **"这个改动会不会影响答辩口径"**、设计取舍、验收判断 | **不必再逐个查 Key、查目录、查字段名**——机器已经查过了 |

**这一层的意义**：人的时间花在只有人能判断的事上，而不是花在找硬编码 Key 上。

> 谁审谁见 [`协作规范.md`](协作规范.md) 第 4 节；路径级的 reviewer 指派见 [`.github/CODEOWNERS`](../.github/CODEOWNERS)。
