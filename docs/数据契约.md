> **版本 v2.0 · 冻结日期：2026-10-10**（冻结人：队长；**字段裁定人：开发B**）
>

> **本文档的定位**：《技术方案与实施手册》第 12 章是**详细规格**，本文件是**开工时对照抄的一页纸**。口径冲突时以 [`全流程计划.md`](全流程计划.md) 第 1 节的九条裁定为准，并提 Issue 修正本文件。

## 主链路

```text
数字孪生 work/twin/（虚拟检测器：车流量 / 车速 / 排队长度）
        │  一期：车流量 100% 来自孪生（source = "twin"，is_simulated = true）
        ↓
感知与判级 work/perception/ → segments.json
        │
孪生车辆真值 → vehicles.json（**仅一期演示用**，二期不存在此文件）
        ↓
决策引擎 work/engine/（时段容量预约 + 不伤害前车 + 前车再疏导）→ routes.json
        ↓
接口层 work/assembly/traffic.py → 管理端页面 / 司机端鸿蒙 App
```

> **二期只换两个数据源，字段一个不改**：
> ① **虚拟检测器 → 真实视频感知**（`segments.source` 由 `"twin"` 变 `"video"`）；
> ② **孪生真值位置 → App 定位 + 地图匹配**（`location.source` 由 `"twin"` 变 `"app_gnss"`）。
> **下游模块一行都不用改**——这是一期就把字段定成这个形状的唯一理由。

## 一、`segments.json`（感知与判级产出 → 引擎 / 前端消费）

每条路段的**指标 + 拥堵等级**。一期由**虚拟检测器**（孪生，与二期真摄像头同位置、同字段）出数。

```json
{
  "ts": "2026-10-10T17:32:00+08:00",
  "window_sec": 900,
  "is_simulated": true,
  "segments": [
    {
      "segment_id": "SEG-003",
      "source": "twin",
      "q_vph": 590,
      "v_kmh": 14.2,
      "v_f_kmh": 40.0,
      "k_vpk": 41.5,
      "L_q_m": 210,
      "L_seg_m": 380,
      "T_d_min": 6.4,
      "x": 0.91,
      "c_base_vph": 1288,
      "c_vph": 647,
      "factors_applied": [
        {
          "factor_id": "F01",
          "name": "大雨",
          "target": "c",
          "multiplier": 0.75,
          "until": "2026-10-10T18:10:00+08:00"
        },
        {
          "factor_id": "F06",
          "name": "路边违停占道",
          "target": "lanes",
          "multiplier": 0.67,
          "until": "2026-10-10T17:50:00+08:00"
        }
      ],
      "ci": 68.5,
      "level": 3,
      "level_name": "拥堵",
      "triggered_by": ["x", "L_q"],
      "confidence": 0.83,
      "data_age_s": 12,
      "pred": {
        "h15": { "q_vph": 640, "level": 3 },
        "h30": { "q_vph": 520, "level": 2 },
        "model": "L0"
      },
      "is_simulated": true
    }
  ]
}
```

**必填字段**：`segment_id`、`ts`、`level`、`source`、`is_simulated`。其余缺失时下游按 0 处理并降级。

### 1.1 v2.0 新增字段（**每个字段的含义写死，不要各写各的**）

| 字段 | 类型 | 含义 | 一期取值 |
|---|---|---|---|
| `source` | string | 这段路的车流量**从哪来** | 一期**恒为 `"twin"`**（虚拟检测器）；二期为 `"video"`（真实视频感知） |
| `c_base_vph` | number | **因素修正前**的通行能力（辆/小时），站点包给出的基准值 | 来自 `stations/network.json` |
| `factors_applied` | array | 这一刻**实际生效**的因素清单，逐项写明改了什么 | 一期由孪生模拟注入；未受影响时为空数组 `[]` |
| `pred` | object | 未来 15 / 30 分钟流量与等级预测（**可选**） | 一期只做 **L0**（历史同期均值），标 `is_simulated`，**不报任何精度数字** |

**`factors_applied` 每一项的字段**：

| 子字段 | 取值 | 说明 |
|---|---|---|
| `factor_id` | `"F01"` ~ `"F14"` | 对应《全流程计划》第 6 节的因素登记表 |
| `name` | 中文短名 | 如 `"大雨"`、`"事故封道"`，管理端直接显示 |
| `target` | `"c"` / `"v_f"` / `"demand"` / `"lanes"` / `"confidence"` | 这个因素**改的是哪个量**：通行能力 / 畅通速度 / 需求 / 车道数 / 检测置信度 |
| `multiplier` | number | 乘法系数（如 `0.75` = 打七五折）。`target = "lanes"` 时表示车道数按比例折算 |
| `until` | ISO 时间 | 该因素的**失效时刻**；长期因素给远期时间，不留空 |

> **合成规则（与手册一致）**：各因素对 `c`、`v_f` **分别相乘**，合成后**不低于原值的 40%**【待标定】。
> 即 `c_vph = c_base_vph × ∏(target ∈ {c, lanes} 的 multiplier)`。上例：`1288 × 0.75 × 0.67 ≈ 647`。
> 未生效的因素**不写进数组**，不要写 `multiplier: 1.0` 占位——管理端要靠"有没有这一项"判断"这一刻到底哪些因素在起作用"。

**`pred` 的子字段**：

| 子字段 | 说明 |
|---|---|
| `h15` / `h30` | 未来 15 / 30 分钟的 `{ "q_vph": 预测流量, "level": 预测等级 }` |
| `model` | 模型档位：一期 `"L0"`；二期可为 `"L1"` / `"L2"`（阶梯上线，见《全流程计划》第 7.2 节） |

> `pred` 是**可选**字段：一期没有预测就不写这个键，**不要写 `null` 占位**。
> 一期只跑通链路，**不得对外报精度**；精度指标（MAPE 等）属二期验收（M2-4）。

### 1.2 沿用 v1.0 的字段（含义不变）

`q_vph` 流量（辆/小时）、`v_kmh` 平均车速、`v_f_kmh` 自由流速度（站点包给出）、`k_vpk` 密度（辆/公里）、`L_q_m` 排队长度、`L_seg_m` 路段长度、`T_d_min` 排队消散时间、`x` 饱和度（= `q_vph / c_vph`）、`c_vph` 通行能力（**因素修正后**）、`ci` 拥挤指数（四项加权，默认权重 0.40/0.25/0.25/0.10）、`level` 等级 1~4、`level_name`、`triggered_by` 触发的判据项、`confidence` 数据置信度、`data_age_s` 数据年龄。

> `window_sec` 是**指标统计窗口**长度（可配置）；主循环**每 60 秒触发一次**计算与判级——**触发周期与统计窗口是两件事**，别混。
> 管理端"拥挤指数视图"用 `ci`；"为什么堵"用 `factors_applied` + `triggered_by`。

## 二、`routes.json`（决策引擎产出 → 前端消费）

每次请求的**推荐路线 + 备选 + 离站路线 + 时段预约与不伤害判定**。

```json
{
  "request_id": "REQ-20261010-173200-0007",
  "session_id": "S-9f2c41a7",
  "driver_type": "D1",
  "parking_mode": "S2",
  "location": {
    "segment_id": "SEG-002",
    "offset_m": 85,
    "match_confidence": 1.0,
    "source": "twin"
  },
  "arrival_route": {
    "path_id": "P-2",
    "segments": ["SEG-001", "SEG-004", "SEG-007"],
    "eta_min": 6.4,
    "dropoff_point": "DROP-03",
    "walk_min": 2.1
  },
  "departure_route": {
    "path_id": "P-5",
    "segments": ["SEG-007", "SEG-009"],
    "eta_min": 4.2
  },
  "pickup_route": null,
  "alternatives": [
    { "path_id": "P-1", "eta_min": 7.8, "reason": "多经过 1 个信号路口" },
    { "path_id": "P-3", "eta_min": 8.6, "reason": "需绕行掉头，但落客通道无排队" }
  ],
  "reservation": {
    "slots_reserved": 9,
    "lease_expire_s": 90,
    "harm_check": {
      "max_eta_increase_s": 12,
      "max_slot_x": 0.81,
      "passed": true
    }
  },
  "reroute": { "count": 0, "reason": null },
  "factors_note": "SEG-004 大雨，通行能力按 0.75 折减（F01）",
  "why": "当前推荐路线比备选少 1.4 分钟，且未加重落客通道排队；后车进入不会让前车变慢（最大增加 12 秒）",
  "quota": { "P-2": 12, "P-1": 9, "P-5": 15 },
  "is_simulated": true
}
```

**必填字段**：`request_id`、**`session_id`**、`arrival_route`、`departure_route`、`alternatives`（**≥2 条备选**）、**`reservation`**、`why`、`is_simulated`。

### 2.1 v2.0 新增字段

| 字段 | 类型 | 含义 | 一期怎么来 |
|---|---|---|---|
| `session_id` | string | **一次行程的匿名会话号**（如 `S-9f2c41a7`）。**不含任何身份信息**，行程结束即删 | 进入站前围栏时生成 |
| `location` | object | 这辆车**现在在哪**（路段 + 路段内位置 + 匹配置信度 + 来源） | 一期 = 孪生真值，`match_confidence = 1.0` |
| `reservation` | object | 这次推荐**在时段预约表上占了哪些格、租约多久、有没有伤到前车** | 由决策引擎的预约与不伤害约束产出 |
| `reroute` | object | 这辆车**被再疏导过几次、为什么** | 每 60 秒检查一次在途车辆后回写 |
| `factors_note` | string / null | 推荐理由里引用的**因素说明**（可空） | 由 `segments.factors_applied` 摘出 |

**`location` 子字段**：

| 子字段 | 取值 | 说明 |
|---|---|---|
| `segment_id` | `"SEG-002"` | 定位到的路段 |
| `offset_m` | number | 距该路段起点的米数 |
| `match_confidence` | 0~1 | 定位匹配置信度。一期恒 `1.0`；二期 `< 0.6`【待标定】时**不用于重新规划**，提示"定位不稳定，请确认所在道路" |
| `source` | `"twin"` / `"app_gnss"` | 位置来源。一期 `"twin"`，二期 `"app_gnss"` |

**`reservation` 子字段**：

| 子字段 | 取值 | 说明 |
|---|---|---|
| `slots_reserved` | number | 本次推荐**预约了多少个"路段 × 1 分钟时段"格子** |
| `lease_expire_s` | number | 租约秒数，默认 **90 s**；未确认采纳即释放 |
| `harm_check.max_eta_increase_s` | number | 加入本车后，**已登记前车**预计耗时的最大增加量（秒）。上限 **30 s**【待标定】 |
| `harm_check.max_slot_x` | number | 本车路径上**所有时段**的最大饱和度。上限 **0.85**【待标定】 |
| `harm_check.passed` | bool | 两个约束是否都通过。**`false` 的路线不会出现在推荐里** |

> **确认采纳怎么算**：一期 = 孪生行为体选择跟随推荐路线；二期 = 地图匹配显示车辆已进入推荐路线的首段。

**`reroute` 子字段**：`count` 改道次数（**每车最多 2 次**，超过不再改）、`reason` 改道原因（未改道时写 `null`）。

**`quota` 的含义（v2.0 改口径）**：

> **`quota` = 各候选路径的"剩余可预约量"**——即这条路径在预约表上**还能塞进多少辆车**，由时段容量与已预约量算出。
> **不再是** v1.0 的"配额发号计数"。字段名保留只为兼容，语义按本节为准。

### 2.2 沿用 v1.0 的结构（含义不变）

`request_id`、`driver_type`（D1 送客 / D2 接客 / D3 往返）、`parking_mode`（S1 门口即停即走 / S2 路边或停车场）、`arrival_route`（含 `path_id` / `segments` / `eta_min` / `dropoff_point` / `walk_min`）、`departure_route`（**送完人之后怎么走**，本项目独有）、`pickup_route`（只有 D3 才有）、`alternatives`、`why`。

> **备选条数口径（v2.0 沿用）**：**备选 ≥2 条**（+ 推荐 1 条 = 合计 ≥3 条方案），与候选生成 K=3 一致。唯一候选时按下面的例外处理。

**两条硬规则**（v1.0 起冻结，v2.0 不变）：

- 只有一条候选可用时输出 `no_alternative: true` + 原因，**不得为凑数返回等价路径**（这是 `alternatives ≥2` 的唯一例外）；
- **所有候选都放不下时**输出 `capacity_shortage`，建议"外围等待 / 延后 N 分钟 / 换停车场"，**不得硬塞**。

### 2.3 请求体（`POST /api/traffic/route/recommend`）

v2.0 在 v1.0 的基础上**新增两个可选入参**：

| 入参 | 必填 | 说明 |
|---|---|---|
| `session_id` | 可选 | 有则用于租约登记与"前车再疏导"的识别 |
| `location` | 可选 | 与上文 `location` 同构。**一期传孪生真值**，二期传 App 定位结果 |

其余入参（起终点、`driver_type`、`parking_mode`）不变。

## 三、`vehicles.json`（**新 · 仅一期演示用**，孪生内部数据）

> **这是"孪生内部数据"，不是感知产物。**
> 一期车辆就在孪生里，所以后端能直接读到"每辆车在哪条路、离路段起点多远"。
> **二期不存在这个文件**——摄像头**只数车、不认车**（不知道哪辆是哪位用户），App 只有用户自己的会话位置。**两条数据线不做任何关联。**

> **顶层形状（v2.0 冻结，与手册 12.5 一致）**：带 `ts` 与 `is_simulated` 的信封，车辆列表放在 `vehicles` 数组里——与 `segments.json` / `routes.json` 同一形状，**不要写成裸数组**：

```json
{
  "ts": "2026-10-08T17:32:00+08:00",
  "is_simulated": true,
  "vehicles": [
    {
      "vehicle_id": "twin-0123",
      "driver_type": "D1",
      "segment_id": "SEG-004",
      "offset_m": 40,
      "lon": 112.4312,
      "lat": 23.0621,
      "state": "行驶",
      "guided": true,
      "is_demo_bound": false
    },
    {
      "vehicle_id": "twin-0456",
      "driver_type": "D2",
      "segment_id": "SEG-007",
      "offset_m": 118,
      "lon": 112.4327,
      "lat": 23.0614,
      "state": "候客",
      "guided": true,
      "is_demo_bound": true
    }
  ]
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `vehicle_id` | string | 孪生内部车辆编号，**不是车牌、不是用户身份** |
| `driver_type` | string | `D1` 送客 / `D2` 接客 / `D3` 往返（三类虚拟司机行为体） |
| `segment_id` | string | 所在路段 |
| `offset_m` | number | 距该路段起点的米数 |
| `lon` / `lat` | number | 经度 / 纬度（**WGS-84**，见第五节坐标系口径） |
| `state` | string | `行驶` / `排队` / `落客服务` / `候客` / `违停` / `已离开` |
| `guided` | bool | 是否已被引导（用于算采纳率与"前后车协同"举证） |
| `is_demo_bound` | bool | 是否是**演示车**（鸿蒙 App 一期绑定的那一辆，管理端与 App 要能对上） |

> **`is_simulated` 写在顶层**（信封里那一个，恒为 `true`）。车辆元素里不再重复放该字段——**一个文件一个来源标记**，别让下游不知道该信哪一个。

> **纪律**：`is_demo_bound` 同一时刻**最多一辆为 `true`**（App 一期只绑一辆演示车）。`state` 的取值集合是**封闭的**，新增状态要改契约。

## 四、`render.json`（前端产出，供页面渲染）

前端把上面几个文件聚合成页面需要的样子，字段由前端自己定，**但必须能追溯回 `segments.json` / `routes.json` / `vehicles.json` 的原始字段**（双端同源举证要用）。

> **同源举证口径**：管理端与 App 上同一个数值，必须能指回同一个快照文件、同一个 `ts`。**不允许两端各算一遍。**

## 五、站点包（`stations/`）

**换一个站只改配置、不改引擎代码。** 完整清单（v2.0 按《全流程计划》第 1 节 D7 与站点包口径重列）：

| 文件 | 内容 | 谁填 |
|---|---|---|
| `network.json` | 路网拓扑：节点 / 边 / 属性（车道数、限速、通行能力）。**由 OSM + netconvert 生成**，再按 T2 核对表补录 | 结构：开发B；数据：N1（T2） |
| `points.json` | 点位标签：落客点 / 上客点 / 候客区 / 路口 / **检测断面** | N1（T1） |
| `signal_plan.json` | 信号配时（demo：1 个路口、2 套方案：平峰 / 高峰） | N1 |
| `demand.json` | **新**：列车时刻 + OD 需求 + 车型 / 司机类型比例 | N2（T3 / T4） |
| `factors.json` | **新**：因素登记与时间窗（F01~F14） | N2（T5） |
| `scenarios.json` | 场景：四个演示场景的开关、注入事件、随机种子 | N2 + N4（T6） |
| `thresholds.json` | 判级阈值与权重（一期 demo 值；二期**按路段**重标定） | 开发A（换站必须重新标定） |
| `calibration.json` | **【二期】**摄像头标定：单应矩阵、控制点、有效标定带 | 开发A（二期现场） |
| `sumo/` | netconvert 产出的 `.net.xml` 等**小文本**，**由脚本生成、可重建** | 开发A（脚本） |
| `map_source.json` | 溯源记录：provider / 拉取时间 / 坐标系 / 缺失字段清单 | 开发B（`map_ingest.py` 产出） |

> **检测断面点位口径（一期与二期同点位）**：`points.json` 里的 `detector` 类点位就是**检测断面**——**一期放虚拟检测器、二期放真摄像头**，位置一一对应。这是 D1"二期换数据源不改下游"能成立的前提。

> **`calibration.json` 一期不存在**（摄像头标定属二期）；一期目录里**不要放空文件占位**。

> **`map_source.json` 引擎不读它**——它只用于复核"这个站的路网是哪天从哪家拉的、哪些字段是人工补的"。地图 API 的数据质量要能追溯。

**硬要求**：引擎代码里**不得出现任何站点名、坐标、路名硬编码**。

## 六、HTTP 端点（接口层 `work/assembly/traffic.py`）

> 一期主链路**不依赖 HTTP**（文件快照当契约）；这一层只在演示前包给双端调用。**端点只读快照，不写快照。**

## 七、数据源标记（技术强制）

**每个数值都要带 `is_simulated` 标记。** 一期**恒为 `true`**，一律标「演示数据（模拟）」。

- 一期全部车流量来自**数字孪生**（`source: "twin"`），**不是**视频识别结果；
- 一期**没有**任何真实数据授权，所有指标、等待时长、告警**不代表任何真实时段的实测值**；
- 演示物料（截图 / 录屏 / PPT）必须带角标「**演示数据（模拟）· 车流量来自数字孪生**」（M1-7）；
- **不得**在答辩中说"视频识别已用于站前路况判定"——视频感知属**二期**。
