# 数据契约（一页纸）

> **版本 v1.0 · 冻结日期：2026-10-09**（冻结人：队长 / 后端复核）
>
> **开工第一天定死，之后任何改动必须当天在 Issue 里说，并升版本号。**
>
> 一期**不用前后端分离联调**——模块之间用 **JSON 文件**传递，不用 HTTP 接口。跑一个脚本就能把全链路串起来。
>
> **本文档的定位**：`技术方案与实施手册` 第 12 章是**详细规格**，本文件是**开工时对照抄的一页纸**。两者冲突时以手册为准，并提 Issue 修正本文件。

## 主链路

```text
视频 → 感知线 → segments.json
                    ↓
         决策线 → routes.json
                    ↓
         前端 → 管理端页面 / 司机端 App
                    ↓
         后端 → run_all.py 一键跑完全链路
```

## 一、`segments.json`（感知线产出 → 决策线 / 前端消费）

每条路段的**指标 + 拥堵等级**。

```json
{
  "ts": "2026-10-08T17:32:00+08:00",
  "window_sec": 900,
  "segments": [
    {
      "segment_id": "SEG-003",
      "q_vph": 1120,          // 流量，辆/小时
      "v_kmh": 14.2,          // 平均车速，km/h
      "v_f_kmh": 40.0,        // 自由流速度，km/h（站点包给出）
      "k_vpk": 78.5,          // 密度，辆/公里
      "L_q_m": 210,           // 排队长度，米
      "L_seg_m": 380,         // 路段长度，米
      "T_d_min": 6.4,         // 排队消散时间，分钟
      "x": 0.87,              // 饱和度 = q / c
      "c_vph": 1288,          // 通行能力，辆/小时
      "ci": 68.5,             // 拥挤指数，四项加权
      "level": 3,             // 拥堵等级 1~4
      "level_name": "拥堵",
      "triggered_by": ["x", "L_q"],   // 触发的判据项
      "confidence": 0.83,     // 数据置信度 0~1
      "data_age_s": 12,       // 数据年龄，秒
      "is_simulated": true    // 一期恒为 true
    }
  ]
}
```

**必填字段**：`segment_id`、`ts`、`level`、`is_simulated`。其余缺失时下游按 0 处理并降级。

> `k_vpk`（密度）与 `ci`（拥挤指数）见手册 12.2 与 6.4。**`ci` 是四项加权合成量**（权重默认 0.40/0.25/0.25/0.10），管理端"拥挤指数视图"要用。

## 二、`routes.json`（决策线产出 → 前端消费）

每次请求的**推荐路线 + 备选 + 离站路线 + 配额状态**。

```json
{
  "request_id": "REQ-20261008-173200-0007",
  "driver_type": "D1",              // D1 送客 / D2 接客 / D3 往返
  "parking_mode": "S2",             // S1 门口即停即走 / S2 路边或停车场
  "arrival_route": {
    "path_id": "P-2",
    "segments": ["SEG-001", "SEG-004", "SEG-007"],
    "eta_min": 6.4,
    "dropoff_point": "DROP-03",
    "walk_min": 2.1                 // S2 才有；从停车位走到站口
  },
  "departure_route": {              // 送完人之后怎么走（本项目独有）
    "path_id": "P-5",
    "segments": ["SEG-007", "SEG-009"],
    "eta_min": 4.2
  },
  "pickup_route": null,             // 只有 D3 往返车才有
  "alternatives": [                 // 备选 ≥2 条（+ 推荐 1 条 = 合计 ≥3 条方案）
    { "path_id": "P-1", "eta_min": 7.8, "reason": "多经过 1 个信号路口" },
    { "path_id": "P-3", "eta_min": 8.6, "reason": "需绕行掉头，但落客通道无排队" }
  ],
  "why": "当前推荐路线比备选少 1.4 分钟，且未加重落客通道排队",
  "quota": { "P-2": 12, "P-1": 9, "P-5": 15 },
  "is_simulated": true
}
```

**必填字段**：`request_id`、`arrival_route`、`departure_route`、`alternatives`（**≥2 条备选**）、`why`、`is_simulated`。

> **备选条数口径（v1.0 冻结）**：手册 11.1 与 12.3 都要求**备选 ≥2**，领导版表 2 也承诺"至少两条备选"，候选生成 K=3 恰好给出 1 推荐 + 2 备选——**以 ≥2 为准**。

**两条硬规则**：
- 只有一条候选可用时输出 `no_alternative: true` + 原因，**不得为凑数返回等价路径**（这是 `alternatives ≥2` 的唯一例外）；
- 全部候选配额都满时输出 `capacity_shortage`，转需求侧，**不得硬塞**。

## 三、`render.json`（前端产出，供页面渲染）

前端把上面两个文件聚合成页面需要的样子，字段由前端自己定，**但必须能追溯回 `segments.json` 与 `routes.json` 的原始字段**（两端同源举证要用）。

## 四、站点包（`stations/`）

换一个站**只改配置、不改引擎代码**。六个文件：

| 文件 | 内容 |
|---|---|
| `network.json` | 路网拓扑：节点 / 边 / 属性（车道数、限速、通行能力） |
| `points.json` | 点位标签：落客点 / 上客点 / 候客区 / 检测断面 / 路口 |
| `calibration.json` | 每个摄像头的单应矩阵、控制点、有效标定带 |
| `signal_plan.json` | 信号配时（demo：1 个路口、2 套方案） |
| `scenarios.json` | 情景参数（时段 / 日历 / 天气系数、OD 需求矩阵） |
| `thresholds.json` | 判级阈值与权重 |

**硬要求**：引擎代码里**不得出现任何站点名、坐标、路名硬编码**。

## 五、数据源标记（技术强制）

**每个数值都要带 `is_simulated` 标记。** 一期恒为 `true`，一律标「演示数据（模拟）」。
